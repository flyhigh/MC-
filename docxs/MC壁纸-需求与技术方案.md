## 一、技术选型:用 Rust 合适吗?

**结论:合适,而且是这个场景里最合适的一档。** 但要说清楚:Rust 本身不保证「占用小」,真正吃内存的是 **WebView2 和 GPU 上下文**,所以「用什么写 UI」比「用什么语言」更决定内存。

推荐组合:

| 层 | 推荐方案 | 理由 |
| --- | --- | --- |
| 常驻核心(托盘 / 壁纸宿主 / 桌宠 / 调度) | Rust + `windows-rs` | 无 GC、无运行时、空闲 CPU 极低,可精确控制内存与线程 |
| 壁纸渲染 | `wgpu`(WGSL 着色器) | 跨后端(DX12/Vulkan),着色器可热重载,渲染几乎不占 CPU |
| 桌宠渲染 | `winit` + 分层透明窗口 + `wgpu` 精灵图 | 与壁纸共用同一 GPU 栈,不额外引入 UI 运行时 |
| 控制面板 | **Slint(已定)** | 纯 Rust、无 WebView2,内存比 Tauri 低 80-150 MB;单文件部署,不需要额外运行时 |
| 数据存储 | SQLite(`rusqlite`)+ 文件目录 | 单文件、零运维、易备份迁移 |
| AI 接入 | `reqwest` + Provider 抽象层 | 云端 OpenAI 兼容接口优先,本地模型可选 |
| 进程通信 | 命名管道 / Tauri command(JSON-RPC) | 面板与核心解耦,面板崩溃不影响壁纸 |

三条重要提醒:

- **不要把所有东西塞进一个进程**。壁纸渲染建议独立进程 + 看门狗,坏着色器/坏壁纸最多闪退一个子进程,自动回退「最后可用壁纸」。
- **不引入 WebView2**(已定 Slint)。连带影响:「Web 壁纸」形态在 MVP 直接砍掉(C 方案),只保留程序化着色器 + AI 单图两种;桌宠与面板全部走原生渲染。
- **Slint 面板放核心进程内**:窗口按需创建、关闭即析构(释放窗口与纹理),不做独立进程——Slint 没有动态代码执行,崩溃风险远低于 WebView,不值得为它多一个进程。若后续面板复杂度暴涨,再拆进程。
- **壁纸预览用像素回读**:面板里的"实时预览"把渲染目标缩到 480×270,以 1-2 fps 回读成 Slint `Image`(约 0.5 MB/帧),避免做 GPU 纹理共享,省事且够用。
- **GPU 上下文也不便宜**(首次初始化 30-60 MB 显存 + 几十毫秒)。单例 `wgpu::Device` 全程序共享。

### 性能预算(建议写进验收标准)

| 指标 | 目标 | 备注 |
| --- | --- | --- |
| 常驻内存(面板未开) | ≤ 100 MB | 壁纸 50-70 MB + 桌宠 10-20 MB + 核心 15-25 MB(Slint 替换 Tauri 后下调) |
| 空闲 CPU | ≤ 1% | 静态/微动壁纸 |
| 动画壁纸 CPU | ≤ 3-5%(单核) | 帧率上限可选 30/60 |
| 冷启动到托盘 | ≤ 800 ms | 壁纸异步加载 |
| 换壁纸首帧 | ≤ 300 ms | spec 渲染本就在 GPU 上毫秒级 |
| 安装体积 | ≤ 15 MB | 不含本地模型;无 WebView2 运行时依赖 |

## 二、总体架构与进程模型

```
┌──────────────────────────────────────────────────────────────┐
│ mcwp-core.exe  常驻,Rust,唯一「长期活着」的进程              │
│  tray │ scheduler │ signals │ spec │ library │ ipc │ config  │
└──┬──────────────┬────────────────┬───────────────────────────┘
   │              │                │
┌──▼───────┐ ┌────▼─────────┐ ┌────▼──────────────┐
│ 壁纸宿主  │ │  桌宠宿主     │ │ 面板窗口(同进程)   │
│ WorkerW  │ │ 透明置顶窗口  │ │ Slint             │
│ wgpu     │ │ wgpu 精灵图   │ │ 按需创建 / 关闭析构 │
└──────────┘ └──────────────┘ └───────────────────┘
                     │
       云端 AI 调用(HTTP,核心进程内直连)
             ┌───────▼──────────┐
             │ AI Worker(可选)  │ 仅本地模型 / 文生图时才起,用完退出
             └──────────────────┘
```

核心模块职责:

- **signals**:亮度、前台应用、空闲时长、时间、电源、全屏状态采集(见第四节)
- **spec**:壁纸规格 JSON 的定义、校验、修复、版本迁移
- **library**:SQLite 壁纸库 + 缩略图/缓存文件
- **scheduler**:生成任务队列(T0-T3 分级)、冷却、电源策略、失败重试
- **ipc**:面板/桌宠/渲染器与核心的通信契约
- **pet**:桌宠状态机 + 动画映射 + 交互事件
- **render**:wgpu 场景图与着色器库(预设场景 + 参数化)
- **panel**:Slint 控制面板(同进程,按需建窗;关闭即释放窗口与纹理)

## 三、壁纸怎么「AI 生成」(本项目最核心的设计)

### 3.1 关键决策:不让 AI 直接画图,而是让 AI 写「壁纸规格」

让 LLM 输出一份结构化的 `WallpaperSpec`(JSON),由本地**参数化渲染器**实时渲染。对比:

| 方案 | 出图耗时 | 单张体积 | 可微调 | 花费 | 结论 |
| --- | --- | --- | --- | --- | --- |
| LLM 直接生成图片(文生图) | 3-20 s | 1-5 MB | 只能重画 | 每次都有成本 | 只用在「显式创作」档 |
| **LLM 生成 spec + 本地渲染** | **10-50 ms** | **1-3 KB** | 滑杆随便调 | 近乎为零 | **主力方案** |
| AI 单图 + 2.5D 动效 | 3-20 s | 1-5 MB + 深度图 | 半可调 | 按需 | 作为「高级观感」可选 |

spec 方案的好处是连锁的:毫秒级切换、KB 级存储、可撤销、可分享(一张壁纸就是一个 JSON)、可确定性复现、GPU 开销低、风格统一不容易崩。

### 3.2 三种壁纸形态(按优先级)

- **A. 程序化场景着色器(WGSL)— MVP 主打**
  预设场景库 + 参数调优:雨夜城市、深林晨雾、极简几何、星云、像素房间、流体、粒子场、昼夜光照。
  参数量控制在 20-40 个(调色板、动势、密度、模糊、视差强度、光源方向、噪波尺度…),LLM 只填这些数值,渲染结果就不会难看。
- **B. AI 单图 + 2.5D 动效 — 观感最「AI」**
  文生图得到一张主图 → 轻量深度估计模型(Depth-Anything 小模型 / MiDaS,ONNX 运行)生成深度图 → 视差位移 + 体积光 + 粒子 + 呼吸式缩放。
  一张静态图立刻变成有纵深的动态壁纸,这是差异化卖点。
- **C. Web 壁纸 —— MVP 砍掉(因面板已选 Slint,不引入 WebView2)**
  原设想是 LLM 生成 HTML/Canvas 跑在沙箱 WebView2 里。为了内存与体积,这个形态推迟到 v1.x 再评估,不作为路线图承诺。

### 3.3 生成管线

```
[对话 / 桌面亮度 / 工作状态 / 时间]
        ↓  (提取与压缩,本地)
   情绪 + 意图向量(mood vector)
        ↓  (可选,仅 T2/T3 触发)
   LLM 结构化输出(strict JSON schema)
        ↓
   Schema 校验 → 修复重试 → 与「用户风格档案」合并
        ↓
   wgpu 渲染 → 交叉淡入应用(1.5-3 s)→ 缩略图 + spec 入库
        ↓ 失败 / 信息不足
   环境降级渲染(3.4)
```

### 3.4 信息不足时的四级降级(回答「提不出元素怎么办」)

| 级别 | 条件 | 做法 | 用户感知 |
| --- | --- | --- | --- |
| L0 纯环境 | 完全没有对话输入 | 只按时间/亮度/季节/电源挑预设场景与配色 | 壁纸随昼夜自然变化 |
| L1 局部微调 | 有效信息很少 | 不换场景,只平移调色板/亮度/动势(基于当前壁纸) | 氛围变了,构图没变 |
| L2 档案约束 | 有情绪但无视觉意象 | 用「我的风格档案」(主色、题材偏好、禁用元素),LLM 只输出修饰项 | 仍是用户喜欢的风格 |
| L3 主动询问 | 连续沉默后用户又激活桌宠 | 桌宠气泡问一次「要不要换个氛围?」,最多一次,不追问 | 可选,可永久关闭 |

**原则:LLM 超时(默认 3 s)或失败,直接走 L1/L0,绝不卡住、绝不让壁纸黑屏。**

### 3.5 生成节奏:不是「聊一句生成一次」

| 级别 | 触发条件 | 产物 | 成本 | 频率上限 |
| --- | --- | --- | --- | --- |
| **T0 实时** | 每帧 | 调色板/动势插值 | ≈0 | 连续 |
| **T1 环境** | 亮度/时间/工作状态变化超阈值 | 同一 spec 重渲染 | < 50 ms,纯本地 | 每 5-15 min |
| **T2 指令** | 用户明确下指令:「暗一点」「换冷色调」「别动那么快」 | **只改当前 spec 的参数,不新建库条目** | 1 次 LLM 调用,或纯本地规则匹配 | 冷却 ≥ 30 s |
| **T3 显式创作** | 用户说「替换壁纸 / 生成一张壁纸 / 我要赛博朋克」 | **新 spec → 壁纸库新条目 + 应用** | 1 次 LLM 调用(可选文生图) | 手动,高频时合并请求 |

**核心原则(按你的选择):只有用户明确说「替换 / 生成壁纸」时才产生新壁纸,其余时间壁纸只随工作状态与环境变化。**

- 闲聊与情绪表达**不再触发**新壁纸生成,只更新内部情绪向量(留作以后可选功能),避免"聊两句桌面就变天"。
- 状态驱动的变化走 T1 / 状态主题组(见 3.7),不产生库条目、不调 LLM、也不改文件,随时可回滚。
- T3 应用后一定给**可解释提示**:气泡显示提取到的关键词(如 `雨 / 夜 / 蓝紫`),并提供一键撤销、一键锁定。
- 全屏游戏/会议投屏/电池模式下,自动变化全部静默(只保留亮度跟随),避免投屏时桌面突变。

### 3.6 WallpaperSpec 示例

```json
{
  "schema": 1,
  "id": "auto-20261014-0031",
  "title": "深夜实验室 · 雨",
  "source": "conversation",
  "keywords": ["雨", "夜", "专注", "蓝紫"],
  "mood": { "calm": 0.7, "focus": 0.8, "energy": 0.3 },
  "palette": ["#0B1020", "#1B2A4A", "#4F7CFF", "#9BB8FF", "#E6ECFF"],
  "scene": { "preset": "rainy_window_city", "params": { "rain": 0.7, "blur": 0.35, "parallax": 0.25 } },
  "motion": { "intensity": 0.45, "speed": 0.6 },
  "lighting": { "mode": "auto_ambient", "keyLight": 0.5, "followDesktopBrightness": true },
  "elements": [{ "type": "particles", "count": 120 }, { "type": "grid", "opacity": 0.08 }],
  "overlay": { "clock": true, "quote": "今天先跑通 MVP" },
  "seed": 87123
}
```

要点:`seed` 保证确定性复现;`lighting.followDesktopBrightness` 让壁纸亮度跟随桌面环境;`params` 全部有取值范围与默认值(校验器负责夹紧,LLM 输出越界也不会出事)。

### 3.7 状态主题组(「根据工作状态改变」的具体落地)

不靠 LLM,纯本地配置 + 着色器参数,做到「壁纸跟着状态走」:

- 定义若干**状态槽位**:`专注 / 阅读 / 休闲 / 夜间 / 会议 / 离开`,每个槽位绑定「场景预设 + 参数偏移 + 调色板」。
  - 例:专注 → `rainy_window_city` 冷蓝、低动势、暗背景;阅读 → `minimal_paper` 暖色低饱和、近乎静止;夜间 → 跟随亮度并压暗、减少蓝光;会议 → 极简、低动势、关气泡。
- 状态切换由感知层事件驱动(见第四节),带 1.5-3 s 交叉淡入,并在气泡里说明原因(「检测到你在写代码,已切到专注氛围」),可在设置里关掉提示。
- 每个槽位的场景与参数**全部由用户在面板里改**,并支持「用当前壁纸填充该槽位」;未配置的槽位继承默认表。
- 状态变化只在槽位间切换,**不产生壁纸库条目**;想留住某一刻的状态,面板上有「存为壁纸」按钮,把当前运行时参数快照成一条库记录。
- 亮度联动优先级最高:无论处于哪个槽位,`followDesktopBrightness` 都在生效(见第四节「亮度联动策略」)。
要点:`seed` 保证确定性复现;`lighting.followDesktopBrightness` 让壁纸亮度跟随桌面环境;`params` 全部有取值范围与默认值(校验器负责夹紧,LLM 输出越界也不会出事)。

## 四、感知层:亮度 / 工作状态 / 上下文

| 信号 | 采集方式 | 频率 | 隐私处理 |
| --- | --- | --- | --- |
| **桌面亮度/色调** | DXGI Desktop Duplication 抓帧,降采样到 64×36 求平均亮度、对比度、主色 | 1 fps,变化 > 5% 才处理 | 只保留统计值,原始帧只在内存,不落盘、不上传 |
| 物理亮度(可选) | DDC/CI 读显示器亮度,或环境光传感器 | 30 s | 本地 |
| 工作状态 | 前台窗口**进程名** + 空闲时长(GetLastInputInfo)+ 输入速率 | 1-5 s | 默认不读窗口标题,可选 |
| 时间/季节 | 系统时间 | 60 s | 本地 |
| 电源/全屏 | 电源状态、前台是否全屏独占 | 事件驱动 | 本地 |
| 对话上下文 | 与桌宠的聊天内容 | 事件驱动 | 见第九节 |

用途映射(状态 → 壁纸倾向):

| 状态 | 判定 | 壁纸倾向 |
| --- | --- | --- |
| 深度专注/编码 | 前台为 IDE/编辑器,输入密集 | 低动势、冷色、低对比、暗背景 |
| 阅读/文档 | 浏览器/文档类 | 暖色低饱和、大留白、几乎静止 |
| 影音/休闲 | 播放器类 | 动势可高、色彩丰富 |
| 游戏 | 全屏独占 | **暂停渲染**(省电省 GPU) |
| 会议/投屏 | 摄像头/会议类进程 或 日历 | 静默、极简、低动势,不弹气泡 |
| 离开 | 闲置 > 5 min 或锁屏 | 降帧;锁屏时可选展示「屏保模式」 |
| 夜间 | 22:00 后 | 降蓝光、降亮度,配合 `followDesktopBrightness` |

亮度联动策略(避免「白天瞎、晚上刺眼」):

1. 壁纸整体亮度 = 桌面平均亮度平滑目标值 × 用户强度系数(默认 0.6),用 2-3 s 缓动,不做突变。
2. 只调「明度/对比/光源强度」,不动构图与配色倾向,否则会显得脏。
3. 提供「跟随亮度」总开关与手动基线,敏感用户可关。

## 五、壁纸库设计

- **条目 = spec(JSON,1-3 KB)+ seed + 缩略图(≤512 px WebP)+ 来源标签 + 时间戳 + 收藏/锁定**
- **什么会进库(按已定决策)**:只有 ① 用户显式生成的壁纸 ② 导入的 spec/图片 ③ 收藏 ④ 手动「存为壁纸」的状态快照。状态切换与亮度联动都是**运行时状态,不落库**,所以库不会被自动行为污染。
- 生成的位图只作为**缓存**,可随时重建;spec 才是「真相源」。因此:壁纸库极轻、可导出分享(一个 `.mcwspec` 文件即一张壁纸,换台机器也能复现)。
- SQLite 表:`wallpapers`(spec, hash, source, keywords, created_at)、`tags`、`assets`、`history`(应用记录,支持撤销/回到某天的氛围)、`settings`、`mood_log`。
- 去重:spec 规范化后取 hash,重复则只更新引用与时间,不重复占用空间。
- 缓存回收:LRU,收藏/锁定的条目永久保留。
- 多显示器预留:`wallpapers` 与 `displays` 多对多,同一壁纸可配不同显示器参数。

## 六、桌宠设计:形态、交互与「对话→壁纸」协议

### 6.1 状态机(MVP 用内置精灵图,帧动画 ~200 KB)

`idle / wander / sleep(闲置 > 10 min) / busy(前台是工作类应用) / listening / thinking(生成中) / speak / notify / error`

状态由「感知层 + 调度器」驱动:生成中会真的切到 thinking 动画,壁纸换好再 speak 一句——**桌宠是系统的可视状态机**,不是装饰。

### 6.2 鼠标交互映射(推荐默认,回答「单击还是双击」)

| 操作 | 行为 | 为什么这样设计 |
| --- | --- | --- |
| 悬停 | 眼神/身体跟随鼠标,轻微呼吸 | 有生命感,零打扰 |
| 单击 | 轻交互:打招呼、随机动作、或展示 1 条待办 | 误触成本低,**不弹窗** |
| **双击** | **打开对话面板**(聊天 + 输入框) | 明确意图才开窗,符合桌面软件直觉 |
| 右键 | 上下文菜单:换壁纸 / 撤销 / 锁定 / 暂停 / 设置 / 退出 | 惯例位置 |
| 拖拽 | 移动位置,松手吸附屏幕边缘或任务栏 | |
| 长按(可选) | 语音输入 | |
| 全局热键 | `Alt+Space` 或 `Ctrl+Alt+M` 呼出输入框 | 键盘流用户 |
| 托盘图标 | 兜底入口(打开面板 / 暂停 / 退出) | 桌宠被隐藏时也要能用 |

补充:提供「点击穿透模式」(壁纸区可穿透,桌宠区不可)与「自动隐藏(鼠标靠近才出现)」,避免桌宠挡住图标。

### 6.3 信息交互的三个层级

1. **气泡(toast)**:非打断,3-5 s 自动消失。用于「已换成偏暖的壁纸」「生成中…」「已撤销」这类状态通知。
2. **对话面板**:完整聊天 + 快捷动作按钮(换一张 / 撤销 / 锁定 / 再冷一点)。可脱离桌宠独立停靠。
3. **控制面板**:设置、壁纸库、创作器(见第七节)。

### 6.4 对话怎么变成壁纸(协议细节)

每条消息先做**意图分类**(本地小模型或规则 + 云端 LLM,几百毫秒):

| 意图 | 例子 | 处理 |
| --- | --- | --- |
| 闲聊 | 「今天好累」 | 只回话,不动壁纸(情绪值可驱动桌宠表情) |
| 情绪表达 | 「有点烦,想静一静」 | 记录情绪 + 回复安慰话术;除非你接着说「换个氛围」,否则不动壁纸 |
| 视觉描述 | 「像雨夜里的霓虹街道」 | 只是描述 → 回应一句「这个意象不错」;带请求语气才走 T3 |
| 指令 | 「换成冷色调」「暗一点」 | **T2**:直接改当前 spec 参数,不新建库条目 |
| 创作请求 | 「替换壁纸」「给我生成一张赛博朋克」 | **T3**:新 spec 入库 + 应用(可含文生图) |

触发规则(已按你的决策收敛):**只有「指令」和「创作请求」会改变壁纸**;闲聊、纯情绪表达、单纯视觉描述一律不动壁纸,只做对话回应。桌宠可以主动建议一句(「要不要换成雨夜?」),但必须等你点头才执行——保留惊喜感,同时不会失控。

## 八、性能与功耗策略

- **遮挡暂停**:壁纸窗口被最大化窗口完全遮挡 → 降到 1 fps 或暂停(比对前台窗口矩形)。
- **全屏/游戏**:暂停渲染;电池供电:降帧或静态化,恢复到交流电时自动恢复。
- **GPU 复用**:单例 device,切换壁纸只重载场景资源,不重建设备;着色器预编译并缓存。
- **资源池化**:精灵图/纹理复用;桌宠与壁纸共用纹理上传队列。
- **启动优化**:托盘先可用,壁纸异步加载;适配器能力探测结果缓存到配置。
- **失败隔离**:渲染子进程看门狗,崩溃 2 次自动降级为静态壁纸并提示用户。

## 九、隐私与合规(必须在 MVP 就定,后面改很贵)

- **屏幕采样**只产出亮度/主色统计量,原始帧不落盘、不上传;设置里可完全关闭。
- **对话内容**:默认「本地提取摘要 + 情绪向量」,云端只发送用于生成壁纸的摘要文本(不含原始聊天记录);提供「全本地模式」(接本地模型)。原始对话是否留档由用户决定,默认不长期保存。
- **素材版权**:不内置任何受版权保护的素材(例如 Wallpaper Engine 创意工坊内容、动漫角色形象);内置壁纸均为自研着色器或明确许可素材;用户导入的素材责任自负,但需在协议里写明。
- **AI 输出合规**:调用云端模型时遵守其内容条款;提供敏感内容过滤开关。

先验证最 risky 的三件事,再往上堆功能:

| # | 验证项 | 做法 | 通过标准 |
| --- | --- | --- | --- |
| 1 | 壁纸挂载 | 用 `windows-rs` 向 Progman 发 `0x052C`,找到 `WorkerW` 并把自建窗口 reparent 上去 | 壁纸在桌面图标之下、任务栏之上;重启 explorer 后自动恢复 |
| 2 | 渲染与开销 | `wgpu` 写一个参数化雨夜场景(WGSL),接 30/60 fps 上限与遮挡暂停 | 动画时单核 CPU ≤5%、显存 <100 MB、切换场景无设备重建 |
| 3 | 亮度采样 | DXGI Desktop Duplication 抓帧 → 降采样 64×36 → 算平均亮度,驱动场景亮度参数 | 亮度变化 1-2 s 内平滑跟随,且不拖慢前台应用 |

### 11.1 实测结论(2026-10-14,本机 Win11 25H2 / Intel UHD + RTX 4060 混显)

**结论 1 —— 挂载:发 `0x052C` 已经不够,必须自己按尺寸挑那一层。**
本机桌面结构是 `Progman → SHELLDLL_DefView →(图标层)`,壁纸层是 Progman 那个铺满屏幕的 WorkerW 子窗口;同时系统里还有约 15 个 136×39 的 IME 宿主也叫 WorkerW。所以不能只按类名找,要**按「是否覆盖主屏矩形」过滤**。

| 挂载模式 | 实测结果 |
| --- | --- |
| `auto`(推荐) | 命中 `Progman 背景层 WorkerW`;图标在最上层、两块屏互不影响 |
| `below-defview` / `progman-worker` | 同样可用,作为兜底 |

**结论 2 —— 呈现:必须走 DirectComposition。**
`CreateSwapChainForHwnd`(`DxgiFromHwnd`)在壁纸子窗口上会「Present 成功但上不了屏」;改成 `CreateSwapChainForComposition` + `IDCompositionVisual`(`DxgiFromVisual`)才稳定上屏。A/B 实测工作集 195 MB → 125 MB。

**结论 3 —— 帧延迟等待对象在本机是性能陷阱。**
`Dx12UseFrameLatencyWaitableObject::Wait` 会让每次取帧固定卡满约 1 秒超时(表现 1 fps);改为 `None` 后稳定 59 fps。已写死。

**结论 4 —— 内存:私有工作集 82 MB,总工作集 120 MB。**

口径说明:程序日志里印的「私有」是 `GetProcessMemoryInfo` 的 `PagefileUsage`(私有提交),和任务管理器的「专用工作集」不是一个口径 —— 同一时刻前者约 119 MB、后者约 83 MB。**验收看后者。**

| 阶段 | 工作集 |
| --- | --- |
| 进程启动 | 7 MB |
| 建 wgpu Instance + Surface | 12 MB |
| 选定适配器 | 46 MB |
| 创建设备 + 管线 + 交换链 | 120 MB |

关键发现:wgpu 的 `Adapter::expose` 会**为每一块适配器创建一个临时 D3D12 设备**来查询能力,本机因此同时加载 Intel 与 NVIDIA 两套驱动,光 `request_adapter` 就吃掉约 33 MB。而裸 D3D12 探针(单设备 + 交换链)只要 66 MB。结论:

- **任务管理器口径(私有工作集)82.4 MB,已达成 ≤100 MB 目标**;
- 总工作集 120 MB 的差额主要是两块 GPU 的驱动 DLL(共享页,并非本进程私有);
- 要再往下压只有一条路:**绕开 wgpu、自绘 D3D12 后端**(预估 70~90 MB),代价是失去 WGSL/跨平台,列为 M2 可选优化,不阻塞功能推进。

已落地的三处内存/性能改动:

1. `MemoryHints::Manual { 4 MB..16 MB }` —— 默认 `Performance` 一上来就开 128~256 MB 显存堆;
2. `desired_maximum_frame_latency = 1` —— 交换链缓冲 3 张降到 2 张(1080p 每张约 8 MB);
3. 只在设置 `MCWP_GPU_INDEX` 时才显式 `enumerate_adapters()` —— 否则每块 GPU 多建一套 DXGI/D3D12 工厂对象,多吃约 35 MB。

### 11.3 M1 面板实测(2026-10-14,同一台机器)

Slint 控制面板按「独立线程 + 独立事件循环 + 关窗即释放」实现,面板进程内不开第二个 GPU 设备。实测(Task Manager 口径的专用工作集):

| 状态 | 专用工作集 | 总工作集 |
| --- | --- | --- |
| 无面板(基线) | 83.0 MB | 116.3 MB |
| 面板打开 | **90.9 MB** | 128.3 MB |
| 关窗后 | 85.4 MB | 123.1 MB |

结论:面板净增约 8 MB,关窗后基本回落到基线(残留 ~2 MB 是 Slint/winit 的堆碎片),**常驻 ≤100 MB 的目标仍然达成**。

**踩到的坑:字体是内存杀手,必须内嵌子集字体。**
Slint 的软件渲染器用 `fontdue` 把 fontdb 查到的那个字面**整份**解析成每个字形的轮廓(不是按用到的字符懒加载)。所以「默认字体是哪个」直接决定内存:

| 面板字体 | 实测专用工作集 |
| --- | --- |
| 不指定(回落到系统 Arial,中文全是方框) | 144 MB |
| `SLINT_DEFAULT_FONT=simhei.ttf`(9.3 MB) | 254 MB |
| `SLINT_DEFAULT_FONT=msyh.ttc`(18.8 MB) | 447 MB |
| **内嵌子集字体(135 KB)** | **90.9 MB** |

做法:`tools/subset-panel-font.py` 从 Noto Sans SC(OFL,可自由内嵌;微软雅黑许可不允许)抽出面板用到的字符,子集化成 135 KB 的 ttf(607 字形,族名改成 `MCWP Sans`,避免和用户机器上已装的 Noto 撞名),由 `panel.slint` 的 `import "*.ttf"` + `build.rs` 的 `EmbedFiles` 直接编进 exe,运行时用 `register_font_from_memory()` 注册,并在窗口上设 `default-font-family: "MCWP Sans"`。

两个附带结论:

- `load_system_fonts()` 本身只建元数据,**约 1 MB**,不是元凶;真正吃内存的是 fontdue 对选中字面的解析。
- 面板字体是子集,动态文案(预设名、以后的 AI 生成标题)冒出表外字符会**静默缺字**。所以 Rust 侧加了 `mcwp_ui::missing_chars()`,启动和刷新状态文字时把缺字打 WARN,提醒重跑子集化脚本。

### 11.4 液态玻璃改版(2026-10-14 同日)

面板视觉从第一版的「深色科技风」改成 **iOS 26 液态玻璃**。依据是 Apple HIG 的 *Materials / Liquid Glass* 和 WWDC25 §219《Meet Liquid Glass》,落到 Slint 软件渲染器上只剩三条能做的:

1. **玻璃是「功能层」,浮在内容层上。** 窗口里先铺一整层「环境底」(由当前壁纸调色板推出来的斜向渐变 + 两团彩色光斑),一整块玻璃铺满窗口盖在上面;
2. **没有 backdrop-blur,折射(lensing)只能伪造**:半透明染色 + 顶部镜面高光 + 左右边缘反光 + 底部内缘暗线,拼出「玻璃有厚度」的错觉;
3. **不做 glass on glass**:玻璃内部只用薄填充(卡片)、白纱和发丝线,不再叠第二层玻璃。

实测(任务管理器口径):

| 状态 | 专用工作集 | 总工作集 |
| --- | --- | --- |
| 无面板(基线) | 84.1 MB | 117.2 MB |
| 面板打开 | **92.2 MB** | 129.7 MB |

改版没把面板做大:玻璃铺满窗口换来了一点绘制面积,净增约 8 MB,和改版前(83.0 → 90.9 MB)持平,**≤100 MB 的验收线仍然守住**。

**这次踩到的两个坑,都值得记:**

1. **`import "*.ttf"` 掉了 = 中文整片消失,而且不报错。**
   `default-font-family: "MCWP Sans"` 只是「请求」,字体真正编进 exe 靠的是 `panel.slint` 顶部的 `import "../fonts/*.ttf"`:build.rs 的 `EmbedFiles` 把它变成内嵌资源,再生成初始化代码里的 `register_font_from_memory()`。重写 `panel.slint` 时漏了这两行,现象是**拉丁字母和数字正常、CJK 全部不画**(不是方框,是空白),编译期只有一条极易漏看的告警。同一时刻私有提交还从 121 MB 涨到 144 MB —— 回落系统字体后,软件渲染器会用 fontdue 把选中字面**整份**解析(见 11.3),所以「中文没了 + 内存暴涨」是同一个原因的两张脸。
   补了这条防线:Rust 侧的 `mcwp_ui::missing_chars()` 只查「字符在不在子集里」,查不出「字体压根没注册」,以后改 `panel.slint` 的字体相关行要附带跑一次截图回归。

2. **`Window::window_handle()` 在 `show()` 之后立刻调拿不到 HWND。**
   winit 后端的窗口是**事件循环第一次迭代**才创建的,`show()` 只是把「要显示」排进队列。所以 DWM 圆角和无边框拖动一起静默失效(只留一条 WARN)。做法:在 UI 线程的事件循环里用 `slint::Timer::single_shot` 退避重试取句柄,拿到后缓存起来给拖动逻辑复用。

另外两条设计约束:

- **窗口圆角只能用 DWM 的(约 8px)。** 软件渲染器走 softbuffer(32bpp DIB + BitBlt),窗口没有逐像素 alpha,自己画的圆角只能画在窗口**内部** —— 画得比 DWM 的大,窗口里就会露出一小块背景色拼成的「墙角」。所以面板每一层都对齐 8px,不再追求「28px 窗口圆角」。
- **玻璃极性固定为深色,且环境底的亮度是归一化过的。** 只压不抬的话,深色壁纸(如「雨夜城市」底色 `#0B1020`)会得到一块纯黑面板 —— 玻璃背后没东西可「透」,叠上去就是一片死黑。现在底色 / 亮部 / 暗角各自落到设计亮度档位(0.15 / 0.28 / 0.06),面板的气色跟着壁纸**色相**变,但不跟着壁纸一起沉下去。

**桌面入口(同日):** 图标由 `tools/make-icon.py` 用 Pillow 画(4 倍超采样后 LANCZOS 缩到 16/24/32/48/64/128/256 七档),配色沿用面板的环境底色系,产物两份:`assets/mcwp-icon.ico` 给桌面快捷方式、`assets/mcwp-icon-256.png` 由 `panel.slint` 的 `icon:` 内嵌当窗口图标(任务栏 / Alt-Tab 生效)。`tools/install-shortcut.ps1` 在桌面放一个「MC 壁纸」快捷方式,目标是 `target\release\mcwp-wallpaper.exe --panel`(cargo 产物路径重建后不变,快捷方式不用更新)。exe 文件自身的图标资源需要 `rc.exe` 写资源,本轮没做,列在待办里。

顺带补了**单实例守卫**:桌面快捷方式很容易被连点两下,第二个进程再挂一次壁纸宿主会去抢同一个 WorkerW 把桌面搞花。现在用命名互斥体拦下来,第二个进程只把已运行实例的控制面板叫到前台(`FindWindowW` + `SetForegroundWindow`,跨进程,不需要 IPC)然后退出;`--dump` / `--window` 这类排查参数不挂桌面,不受限制。

### 11.5 面板拖动「不灵敏」的根因与修法(2026-10-14 同日)

现象:拖面板标题栏,窗口跟手一段就**停在原地不再动**(顺原路拖回去还会「跳」一下)。

**根因是 Slint 的 `TouchArea.pressed` 语义,不是窗口句柄、也不是渲染慢。** 原来的标题栏拖动区写的是
`pointer-event(e) => { root.drag-state(drag.pressed); }` —— 而 `pressed` 只在指针**位于这个 TouchArea 的几何范围里**才为真。指针一旦离开标题栏那条 30px 窄带(`i-slint-core` 的 `send_exit_events` 按几何包含关系判 `contains`,**不看鼠标抓取**),TouchArea 立刻把 `pressed` 置 false 并补发一个 `PointerEventKind.Cancel`,同时连内部的 `grabbed` 也清掉 —— 之后**移动、抬起都不再送给它**。Rust 侧收到 false 就把 `WindowDrag` 丢了,拖动到此为止;若指针又回到标题栏,`pressed` 转真,`WindowDrag::begin` 重新记起点,于是「跳一下」而且丢掉中间那段累计位移。
带时间戳的实测(合成鼠标慢速拖 40 步 × 6px / 20ms):窗口位移与光标位移**在事件流动期间是 1:1 的**(光标 +191,+26 时窗口也正好 +191,+26),然后在拖到一半时**事件整段断掉**,窗口停在原地不动 —— 这就是手感上的「不灵敏」。

**修法:把拖动交给 Windows 自己的标题栏模态移动循环** —— `slint` 开 `unstable-winit-030` feature,在 Slint 的回调里 `window.with_winit_window(|w| w.drag_window())`,winit 内部就是 `ReleaseCapture()` + `PostMessageW(WM_NCLBUTTONDOWN, HTCAPTION)`,DefWindowProc 之后接管采样光标。跟手性最好,没有每帧 `SetWindowPos` 的开销,还自带贴边吸附。Slint 侧相应改成**只认左键 `down` / `up` 两个动作**(`drag-start` / `drag-move` / `drag-end` 三条回调),Rust 侧不再依赖「按住」状态,拿不到 winit 窗口时才退回落成手动的 `WindowDrag`(并加了「位置没变就不搬窗口」的节流)。

顺带纠正一个之前的误判:`WM_EXITSIZEMOVE` 里 winit 会补一条 `WM_LBUTTONUP`,所以拖动结束后 Slint 侧的状态是干净的,**连续拖动不会卡在「dragging」里**——这一点也实测过(见下表)。

实测(`tools/drag-probe.ps1` / `drag-probe2.ps1` / `drag-probe3.ps1`,真实 `mouse_event` 注入):

| 用例 | 期望位移 | 实际位移 |
| --- | --- | --- |
| 慢速拖 40 步 × 6px | (240, 80) | **(240, 80)** |
| 连续三次快速拖(每次 25 步 × 4px) | 每次 (100, 50) | **每次 (100, 50)** |
| 甩动 8 步 × 40px / 5ms | (320, 0) | **(320, 0)** |
| 甩到屏幕上边缘 | 不最大化 | 未最大化,位置贴到 y=0,尺寸不变 |

注意:这条路径依赖 winit 的 `drag_window()`,属于 `slint` 的 **unstable API**(`unstable-winit-030`),升级 Slint 时要复验。

### 11.6 托盘 + 面板页签(2026-10-14 同日)

**托盘**(`mcwp-platform::tray`)。关掉面板之后应用就没有任何可见入口了,托盘补的就是这个洞。

- **不引入线程,也不引入第二个消息循环。** 宿主窗口的 `pump_pending()` 用的是
  `PeekMessageW(None, 0, 0, PM_REMOVE)`,取的是**整条线程**的消息队列;托盘窗口只要跟宿主
  建在同一个线程上,它的回调就会被那个循环顺带派发。主循环的节奏一行没改(仍 59 fps)。
- **图标是 `.ico` 里的一条 PNG 码流,不做解码。** `tools/make-icon.py` 出的 `.ico` 每条都是
  PNG 压缩的 32bpp;`load_icon()` 只解析 6 字节文件头 + 16 字节目录项,取出 32×32 那条,
  直接交给 `CreateIconFromResourceEx`(Vista 起支持 PNG 图标)。不用 `ExtractIconW`
  (它按序号取第一张,等于白丢码流),也没为托盘拖进 `image` / `png` 之类的依赖。
- **菜单用 `TPM_RETURNCMD`,不走 `WM_COMMAND` 路由**:返回值本身就是命令 id。弹菜单前后按
  微软文档的固定套路来(`SetForegroundWindow` → `TrackPopupMenu` → 补一条 `WM_NULL`),
  否则菜单点到外面不会自动关。
- **动作只入队,落地在主循环**(`TrayAction`,与面板的 `UiEvent` 同一套路):
  `OpenPanel` / `NextPreset` / `TogglePause` / `ToggleAutostart` / `Quit`。「换一个预设」走的是
  和面板同一条落地路径,并回填面板(`PanelHandle::refresh`)。
- **开机自启**(`mcwp-platform::autostart`)写在 `HKCU\...\CurrentVersion\Run` 的 `MCWallpaper`
  一条字符串值:不需要提权,关掉就是删掉自己那一条,用户在系统的启动项管理里也看得到。
- **暂停**:动画时钟改成按帧累加(`clock += frame_start - last_tick`),而不是取墙钟 ——
  否则暂停十分钟再继续,画面会直接跳十分钟。

实测(托盘菜单逐项点过,逐项对过日志回显 + 截图):

| 菜单项 | 结果 |
| --- | --- |
| 换一个预设 | 日志 `切换到预设:minimal_paper`;面板同步选中「极简纸感」,参数名 / 参数值 / 摘要 / 指纹全部回填 |
| 暂停渲染 | 日志 `暂停渲染`;60 s 统计窗口里的渲染帧数从 ~59 fps 掉到 21 fps(中间那 36 s 一帧没画) |
| 开机自启 | 打勾后 `HKCU\...\Run` 出现 `"G:\MC壁纸\app\target\release\mcwp-wallpaper.exe"`,再点一次清空 |
| 打开控制面板 | 不带 `--panel` 启动时也能开出来,`FindWindowW` 按标题能找到窗口 |
| 退出 | 进程退出;托盘图标消失(溢出区截图前后对比,`NIM_DELETE` 生效) |

已知:Windows 对新出现的托盘图标一律先收进「隐藏的图标」溢出区,要用户拖出来一次才常驻 ——
这是系统行为,不是本程序的缺陷。想强制常驻得改 `HKCU\Control Panel\NotifyIconSettings` 下的
`IsPromoted`,那是动用户的系统设置,本轮没做。

**面板页签**(`ui/panel.slint`):`壁纸 / 库 / 设置`,iOS 分段控件(胶囊凹槽 + 会平移的染色玻璃滑片)。
**这一版页签已在 11.9 被生图界面取代** —— 下面记的是当时的形态和它踩到的坑。
`page` 是纯界面状态(`in-out property <int> page`),不进 Rust。库 / 设置两页**故意只做占位**
(一条标题 + 一行「待接入」),先把信息架构定下来,下一轮再填真内容。

- **踩到的坑:Slint 的 `visible: false` 不省布局。** 编译器把 `visible` 降级成一个 `Clip` 包裹元素
  (`i-slint-compiler/passes/visible.rs`),元素照样参与布局 —— 第一版用 `visible: root.page == 0`
  切页,结果当前页被挤到窗口底部、上面留一大块空白。切页必须写成
  `if root.page == 0 : Rectangle { ... }`,为假时元素**根本不构造**。
- 面板按 940×648 设计,三段页签每段约 300px。
- 回归工具:`tools/panel-probe.ps1 -Actions 'click:470,78','shot:x.png'`,先把面板临时提到最前
  再点击 / 截图(单纯 `SetCursorPos` + `mouse_event` 会点到压在面板上面的窗口上,页面状态就会
  「莫名其妙」没变)。

### 11.7 「构建怎么这么大?」:10.4 GB 的来历与一次特性裁剪(2026-10-14 同日)

起因:第一次推仓库时 `.gitignore` 排掉 `/app/target/`,顺带看到本机这个目录有 **10.4 GB**。
数字本身没错,但它**不是成品**,而是 cargo 的编译中间产物 —— 删掉随时能重建(本机约 80 秒)。

**实测拆解**(`target/` = 10,428 MB / 15,614 文件):

| 目录 | 体积 | 文件数 | 说明 |
| --- | --- | --- | --- |
| `target/debug` | 6,719 MB | 9,439 | 含 21 个 exe;另有 882 MB `incremental/`、525 MB `build/` |
| `target/release` | 3,709 MB | 6,173 | |

按扩展名:`rlib` 5,043 MB / 1,036 个、`rmeta` 2,299 MB / 1,256 个、`pdb` 1,640 MB / 354 个、
`.o` 约 500 MB、`.exe` 合计 317 MB。单个最大的几个文件是
`debug/deps/mcwp_wallpaper.pdb` 121.7 MB、`libwgpu_core-*.rlib` 113.8 MB(4 份)、
`libnaga-*.rlib` 87 MB(2 份)、`release/deps/libwindows-*.rlib` 77.5 MB。

三条主因,按贡献排序:

1. **依赖的中间产物远大于成品**:每个 crate 都留一份 `.rlib` + `.rmeta`(+ debug 的 `.o` / `.pdb`),
   而 `rlib` 是「未做最终链接优化的对象归档」,比 strip 过的 exe 大一个量级。真正的成品
   `mcwp-wallpaper.exe` 只有十几 MB。
2. **同一 crate 存在大量 feature 哈希不同的重复副本**:`libwindows` 20 份、`libmcwp_platform` 16 份、
   `libmcwp_ui` 13 份、`libsyn` 13 份。根因是逐包构建(`-p`)/ 不同 feature 组合各留一份缓存,
   统一 `cargo build --workspace` 能收敛(本轮已全部改用 `--workspace`)。
3. **debug / release / dev-tools 三套产物并存**。其中 `target/debug/build/mcwp-ui-*/` 两个目录
   各 148 MB —— 那是 **Slint 编译器自己**的产物(`libi_slint_compiler` 57.7 MB)。

顺带纠正一个直觉:本项目**自己写的代码**只有 57 个文件 / 0.79 MB,10 GB 里没有一行是我们写的
业务代码,全是依赖树。另外 `libi_slint_compiler` 57.7 MB、`libimage` 21.7 MB、`libravif` 19.4 MB
都是**构建期**依赖(`slint-macros → i-slint-compiler → image` 这条 proc-macro 链),
只占缓存,**不进成品、不影响运行时**。

**这轮实际做的裁剪:关掉 wgpu 用不到的后端**(`app/Cargo.toml` 的 `[workspace.dependencies]`)。
依据是项目在 `crates/mcwp-render/src/lib.rs` 里把后端写死成 `wgpu::Backends::DX12`,
着色器是 WGSL;而 wgpu 默认还开着 `vulkan / gles / metal / webgpu`,其中 vulkan 会把
`ash`(Vulkan 绑定,单是 release rlib 就 68.5 MB)整条拖进依赖树,webgpu 还会给 naga
加一个用不到的 WGSL 输出后端。

```toml
wgpu = { version = "30.0.1", default-features = false, features = ["std", "dx12", "wgsl", "parking_lot"] }
```

实测(在临时目录从零构建,避免污染正式 target):

| 指标 | 裁剪前 | 裁剪后 |
| --- | --- | --- |
| 成品 `mcwp-wallpaper.exe` | 13.3 MB | **11.52 MB** |
| 从零构建后的整个 `target/` | 10,428 MB | **1,566 MB**(3,748 文件) |
| 从零构建耗时 | — | 80 秒 |
| 依赖树里的 `ash` / `glow` / `web_sys` / `wasm_bindgen` | 有 | **全部归零** |

裁剪后重新冒烟: `--attach auto --fps 60` 跑通,`backend: Dx12`、挂载成功、**58.8 fps**;
桌面拖动回归(3 个用例)、面板点击 / 截图、托盘挂载均无回归。

**结论**:10.4 GB 是正常的编译缓存量级,不是「软件很大」;产品真实体积是 **~11.5 MB 单 exe**。
注意 `app/Cargo.toml` 只改了 feature 集,**没动任何代码逻辑**。

### 11.8 圆角不生效的根因 + 滑杆「悬停即改值」(2026-10-14 同日)

**现象**:分段控件的选中滑片是一个**直角矩形的蓝块**,滑杆的旋钮是**方块**、填充条两头也是直的;
但同一块面板上,「当前壁纸」卡片和预设卡片的圆角却是好的。

**根因:软件渲染器只给实色背景画圆角。** `i-slint-core/software_renderer.rs` 的
`process_rectangle_impl` 里,渐变是**单独一条分支**:`Brush::LinearGradient` / `RadialGradient` /
`ConicGradient` 都直接 `processor.process_linear_gradient(act_rect, ..)` 把**整个矩形**刷下去
(`act_rect` 只是个矩形,没有任何 radius 参与),然后返回一个**透明**的 `Color::default()`。
函数末尾那段 `if !radius.is_zero() { process_rounded_rectangle(.. inner_color: color ..) }`
拿到的 inner_color 因此是透明的 —— 该画的圆角什么也没画。

这解释了为什么「有的圆角是好的、有的不是」:实色背景走的是下面
`process_simple_rectangle` + `process_rounded_rectangle` 那条路,圆角正常;只有描边
(`border-color`)是圆的,因为描边一直由 `process_rounded_rectangle` 画 ——
于是表现为「发丝线是圆的、填充是直角」。

**修法**:凡是要圆角的地方一律改用**实色**;渐变只留给圆角不重要的地方(窗口底色、
环境光斑 —— 前者被 DWM 裁、后者的四角本来就是透明的)。液态玻璃的厚度感改由
**发丝高光 + 半透明层**表达。改动点:`SegTabs` 的凹槽与滑片、`GlassSlider` 的凹槽 /
填充 / 旋钮;旋钮里那层「上半部白色弧」镜面被删掉(它在白色旋钮上本来就是白压白看不出来,
又因为是渐变只会画出一个直角浅色块)。文件头的能力边界注释也一并更正。

**顺带抓到的一个真 bug**:滑杆的 `pointer-event` 原本是
`if (e.kind == down || e.kind == move)`。Slint 的 `move` **悬停也会派发**,所以鼠标只是
**从滑杆上划过**(不按键)就会改值 —— 面板上五个滑杆会被一次挥动全部带动。
修法:`down` 保持无条件(它本身就是按下),`move` 加上 `touch.pressed` 这道闸。
实测:悬停横扫「雨量」滑杆,五个值纹丝不动(65/35/25/57/45 → 不变);
按住拖动仍然正常(能从 65% 拖到 100%)。

### 11.9 面板改成生图界面 + 壁纸库改成「从壁纸侧自动获取」(2026-10-15)

**信息架构换掉了。** 面板从「三段页签(壁纸 / 库 / 设置)」改成生图界面:左栏 244px 是历史对话
(顶部「+ 新建对话」,下面是会话列表,底部三个入口),右栏是会话(标题栏 / 消息流 / 输入框)。
参数、库、设置三页的内容没丢,只是从顶部页签挪到左栏底部;`view` 仍是纯界面状态,不进 Rust。

**壁纸库不再写死在面板里,改成从壁纸侧自动获取。** 面板不碰文件系统:`mcwp-wallpaper` 侧扫
`%APPDATA%\MC壁纸\library\*.json`,把每张壁纸的标题 / 关键词 / 指纹 / 主色拼成 `LibraryItem`
整块灌进面板。扫的时机有三个:打开面板、存新壁纸、面板切到库页(回调 `refresh-library`)——
所以手工往库目录里拷 / 删文件也能跟上。库里点一张就是换 spec(`UiEvent::OpenWallpaper`),
和托盘切预设走同一条落地路径。

顺带统一了「一张壁纸的身份」:`library_id()` 把 spec 归一化(source 钉成 snapshot)后取指纹。
存进库时的文件名、库里显示的那串字符、参数页右上角的「指纹」,现在念的是同一个值;坏 JSON
只记一条日志跳过 —— 库目录是用户可写的地方,不能因为一个手工改坏的文件让整块面板打不开。

**字体策略改了(重要)。** 面板上出现了输入框,用户敲什么字都得画得出来,所以:

| 字面 | 覆盖 | 体积 | 用在哪 |
| --- | --- | --- | --- |
| `panel-cjk-regular.ttf` | **GB2312 一级汉字全表 + 面板文案**(3865 字形) | 1088 KB | 一切动态文案:消息、会话名、输入框、壁纸名、状态行 |
| `panel-cjk-bold.ttf` | 只有面板自己的静态文案(759 字形) | 177 KB | 标题 / 标签 / 主按钮 |

**动态文案一律走 regular** 是硬约定:bold 表里没有用户输入的字,`font-weight: 600` 一旦落到
动态文案上就是静默缺字。子集化脚本相应拆成两套字表(`tools/subset-panel-font.py` 的
`charset()` / `static_charset()`),Rust 侧 `missing_chars()` 仍按 regular 的字表查缺字、进日志。

**内存代价**(本机,专用工作集口径,口径说明见 11.3):

| 状态 | 专用工作集 | 总工作集 | 私有提交 |
| --- | --- | --- | --- |
| 无面板(基线) | 84.3 MB | 117.9 MB | 113.2 MB |
| 面板打开(生图界面) | **115.8 MB** | 155.0 MB | 145.4 MB |

对比 11.4 的 92.2 MB,面板净增从约 8 MB 涨到约 31 MB —— 其中约 17 MB 是 regular 那个全字集字面
(fontdue 会把选中的字面**整份**解析进内存,和用到多少字无关;bold 收窄到静态文案就是为了不背
第二个整表)。**常驻(未开面板)仍然达标 ≤100 MB**;「面板打开」这一栏从 90.9 变成 115.8 是生图
界面的必然代价,要压回去只有砍汉字表(常用 1500 字约省 10 MB)—— 见 12.2 待定项 8。

**Slint 布局的第二个坑:`alignment` 只管主轴。**

- `HorizontalLayout` 里写 `alignment: center` 会把**整条内容挤到中间**,横向 stretch 同时失效
  (输入框会塌成文字那么宽并居中)。
- 反过来,HBox 里**定宽高**的元素(胶囊按钮、圆点、色卡)没有「竖直居中」可言,会被摆在行的
  **顶边**;要居中就得套一层 `VerticalLayout { alignment: center; }`(VBox 的主轴才是竖直的)。

现象很典型:「发送」胶囊顶着输入框上沿、右下角戳出胶囊边界;左栏导航的小圆点比文字高 13px。
四处(发送胶囊 / 导航圆点 / 预设卡圆点 / 库页色卡)都已改成套 VBox,规则写进了 `panel.slint`
文件头的踩坑清单。

**这一节写下时还没做的**:AI 那一环。那会儿发消息只在内存里记一条用户消息 + 一条占位回复
(会话落盘见 11.12,模型接入见 11.13)。当初设想的那条管线「文本 → `WallpaperSpec` → 应用」
后来就是照这个走的,面板侧一行都没动 —— 和预期一致。

**回归方式与过程产物**:面板回归一律走「按标题找窗口 → 提到前台 → 按窗口内逻辑坐标点击 / 输入
→ 截图」,本轮三个视图(会话 / 参数 / 库)加「发一条消息」各截了一张。注意:**新起一个进程后的
第一下点击会被焦点激活吃掉**,要在同一个进程里连着点才可靠 —— 否则很容易误判成「那一行点不
动」。截图、日志、一次性探针脚本一律落在仓库外,仓库里只留 `tools/` 下可重跑的脚本;`.gitignore`
补上 `/.shots/` 与 `__pycache__/`,M0 / M1 阶段那批过程产物(`app/shots/`、`.fontcache/`)已经
清出工作区。

### 11.10 面板补上顶部安全区与窗口键(2026-10-15)

**先还一笔债:无边框窗口没有标题栏。** 之前的"标题栏"只是压在玻璃里的一行 30px 内容(左程序名 +
右一颗关闭圆钮),既不成"安全区"也不像系统窗口。现在窗口顶部单独留一条 36px 满宽的**安全区**:
底色 `glass-tint.darker(0.62)` 的实色(比下面那层玻璃暗一档,换壁纸跟着变色),下沿压一条发丝线
分界;右端三颗 46px 宽、满高的窗口键 = 最小化 / 放大·还原 / 关闭,悬停提亮、关闭键悬停变红
`#C42B1C`,图形**全部自己画**(内嵌子集只收面板文案用得上的字形,"最小化""还原"这类符号有没有
全看运气)。整条安全区就是拖动区,双击 = 放大 / 还原(Windows 的老规矩)。玻璃内容层因此让出
`padding-top: 54px`(= 36 + 18)。

**放大不能用 `SW_MAXIMIZE`。** 窗口是 `no-frame`、没有 `WS_THICKFRAME`,系统算"最大化尺寸"的那套
公式(工作区 + 边框)会退化成**整块显示器 —— 放大会连任务栏一起盖住**。所以 `WindowZoom` 自己去量
`MonitorFromWindow(MONITOR_DEFAULTTONEAREST)` 的 `rcWork` 再 `SetWindowPos` 摆过去,顺手把放大前
的矩形记下来当还原点(还原时**不能**带 `SWP_NOSIZE`,宽高要一起写回)。实测:1024×672 @ (114,114)
的窗口点一下放大 → 2560×1528 @ (0,0),正好是任务栏之上那块工作区;再点一下原样摆回。最小化就是
`ShowWindow(SW_MINIMIZE)`(面板窗口本来就有任务栏按钮,能恢复);关闭仍旧走 `close-requested`
(退出面板事件循环即释放)。三颗键都是"点了直接调 Win32",不绕事件循环,面板本身仍然不存业务状态
(`zoom` 那个 `RefCell` 存的是窗口矩形,不是数据)。落点:
`mcwp-platform/src/glass_window.rs`(`minimize` / `WindowZoom`)、`mcwp-ui/src/lib.rs`
(`panel_hwnd` 抽出来给拖动和窗口键共用)、`panel.slint`(`CaptionButton`)。

**第三个布局坑:Window 上写 `width` / `height` 会把根元素钉死。** 这在 Slint 里是**固定约束**
(min = max)。窗口被系统拉大(放大)之后根元素还是 1024×672,内容缩在左上角、右边一大片空玻璃 ——
而 `Window` 的 `background` 照样铺满整窗,所以第一眼不像"没重排",只像"右边多了块底色"。改成
`preferred-width` / `preferred-height` 才是"首选尺寸":初始窗口仍是 1024×672,但窗口拉大时根元素
跟着长。**顺带**:`Window` 的孩子不带 `x` / `y` 会被**居中**摆,不是左上角 —— 铺满整窗的底色看不
出来,一条 36px 的标题栏会直接跑到窗口正中间,贴边的元素一律显式写 `x: 0px; y: 0px;`。

**放大状态下不拖。** Windows 上拖最大化窗口的标题栏 = 还原 + 继续拖,这套我们没做,干脆当成没接住
(否则能把一块铺满屏幕的窗口拖出工作区);双击仍然可以还原。

**回归方式:合成鼠标消息。** 面板回归还是"按标题找窗口 → 按窗口内逻辑坐标点 → 截图",但这轮的
`mouse_event` 点击**打不中**:当时的前台窗口是桌面(`Program Manager`),`SetForegroundWindow` 被前台
锁挡下,**不是前台的窗口收不到合成输入**,现象是"点了跟没点一样",很容易误判成命中测试坏了。换成
`SendMessage(hwnd, WM_LBUTTONDOWN/UP, ..., MAKELPARAM(客户区坐标))` 就都正常了 —— 它绕开前台 /
焦点规则直接进窗口消息队列。两个附带的注意点:客户区坐标要按本机 scale = 1.5 换算;**每次点击前重新
取一次窗口矩形**(放大之后"右上角那颗键"的逻辑坐标已经不是 955 了)。拖动仍旧只能人工验:面板拖动
首选的是 winit 的系统模态移动循环,合成的鼠标消息进不去那个循环。

### 11.11 会话管理:左栏右键菜单(2026-10-15)

**四个动作 + 一份自绘菜单。** 左栏的历史对话行现在支持右键菜单:**重命名 / 置顶 / 标记为未读 / 删除**。
前三个是"行上的状态",第四个是"行的生死",所以列表项(面板侧的 `ConversationItem`)多了 `pinned` /
`unread` 两个字段,行尾让出 34px 画状态标:置顶是两根实色小矩形拼的图钉,未读是一个染色圆点。菜单本身
是**自绘浮层**,不是系统菜单 —— 无边框窗口 + 软件渲染器下弹 Win32 原生菜单要另开线程跑消息循环,而 Slint
侧画一块 176 × 143 的圆角板子只要几十行。代价是尺寸得写两份(面板的 `menu-w` / `menu-h` 与 slint 组件
里的字面量),因为浮层要 clamp 在窗口内就得先知道自己多大。菜单里**不放图标**:内嵌子集只收面板静态
文案,"重命名""置顶"这类符号有没有全看运气(见 11.3)。

**行内注入 `absolute-position` 再发给面板。** `ConversationRow` 是个可复用的行组件,它不知道自己在列表
里的位置,而菜单要贴着鼠标弹。做法是行组件把 `PointerEvent` 的坐标加上自己的 `absolute-position` 得到
**窗口坐标**再回调出去(`menu-requested(x, y)`),面板只负责 clamp(四周留 8px)和显示。右键在 Slint 里
**没有 `clicked` 可用**,必须走 `pointer-event`,判 `e.button == PointerEventButton.right && e.kind ==
PointerEventKind.down`(左键才是 `clicked`)。

**会话的身份从下标改成 `id`。** 之前 `Sessions::active` 存的是下标,一置顶(排序)/ 一删除下标全乱,
"当前会话"会指到别的行上。现在 `Session` 带自增 `id`,`active` 存 id,`active_index()` 现算;对外回调仍
用下标(面板只有下标这一个概念),换算只发生在 `mcwp-wallpaper` 侧。删除的落点规则:**删完空了就补一个
新的空会话**(面板永远至少有 1 行);**删的是当前会话就落到 `index.min(len-1)`**(顶上来的那条),别的
行不动。置顶用 `sort_by_key(|s| !s.pinned)` —— **标准库是稳定排序**,同档位内保持原顺序,连着置顶不会把
先置顶的那条挤到后面。改名先 `trim`:空名字当没改、同名不做任何事。

**面板侧踩的坑:行元素会被 Slint 复用。** 改名输入框的草稿(`draft`)一开始只在 `init` 里从标题灌一次,
于是"置顶重排 / 删掉中间一条"之后,被复用的元素还留着上一次(甚至别的会话)的名字,回车就会把别人的名字
盖过来。修法是盯着 `renaming` 变真时重灌草稿:
`changed renaming => { if (root.renaming) { root.draft = root.heading; } }`。**注意不能在这个 `changed`
里碰 `rename-input`** —— 那个 id 在 `if` 条件块内,块外引用直接 `Cannot access id 'rename-input'`;让输入
框 `text <=> root.draft`,全选和聚焦交给 `init` 就够了。另外输入框必须**声明在行的命中区(`TouchArea`)
之后**(后声明的画在上面、先拿事件),否则刚点开就被行自己的点击抢走并顺手取消掉。

**菜单的三处小坑**:① `Esc` 取消要走 `key-pressed` 判 `e.text == "\u{1b}"`,Slint 里写 `"escape"` 是不
认的;② 浮层里的矩形 `x:` **不能写裸属性名**(会解析成它自己的属性 → 无限递归),要么带前缀要么给常量;
③ 颜色没有 `lighter()`,提亮浅一档是 `brighter(k)`。

**回归方式:合成输入这轮基本不可用。** 合成的 `mouse_event` 点击仍被前台锁挡下(见 11.10),得用
`SendMessage`;合成按键则会被本机中文输入法吞掉字母(候选条会冒出一串 "zzz"),测改名要先 `Ctrl+Space`
切英文,或者干脆只看日志(`RUST_LOG=info,mcwp_wallpaper=debug` 能看到面板发回来的每个事件)。另外那段
"窗口坐标 → 逻辑坐标"的换算系数别再硬编码 1.5 —— 本机 DPI 会漂,改成 `窗口宽 / 1024` 现算。

落点:`mcwp-wallpaper/src/main.rs`(`Session.id` / `pinned` / `unread` + `rename` / `remove` /
`toggle_pin` / `mark_unread`)、`mcwp-ui/src/lib.rs`(四个 `UiEvent` + 转发)、`panel.slint`
(`ConversationMenu` / `MenuRow` / 行尾状态标 / 改名输入框)。

### 11.12 会话落盘(2026-10-15)

**存哪儿 / 存什么。** 会话落到 `%APPDATA%\MC壁纸\sessions.json` —— 和壁纸库同一个目录(方案第五节
早就定了这条)。一个文件装整份:格式版本号、`active`(上次停在哪一条,存的是 id),以及按显示顺序
排好的会话数组;每个会话带 id / 标题 / 置顶 / 未读 / 消息,一条消息是
`{"role": "user" | "assistant", "text": …}`。

**为什么整份一个文件,而不是"一个会话一个文件"。** 列表顺序(置顶组在前)和"停在哪儿"都是这份数据
的属性,拆成多文件就得再引一份清单,两份对不上时最难查;壁纸库那样"一个指纹一个文件"是因为它天生
按内容去重,会话没这个需求。会话是 KB 级文本,整份重写一次也就几毫秒。真长到上千条历史再换
SQLite —— 和壁纸库同一个迁移点(决策 12)。

**写盘:临时文件 + 改名,每帧至多一次。** 直接往 `sessions.json` 上盖,写到一半掉电就只剩半个
JSON,所以先写 `sessions.json.tmp` 再 `rename`(Windows 上 `std::fs::rename` 会覆盖已存在的目标)。
落盘时机不塞进每个动作里,而是改动打个 `dirty` 标记、主循环每帧收一次:一帧里可能连着好几笔改动
(发消息 + 切会话),这样只落最后一次,也不会有哪个动作忘了落。**失败不重试** —— 磁盘满 / 目录只读
这类错每帧重试只会把日志刷满,而改动会在下一次用户操作时整体再落一遍。

**读盘:坏文件只当"这一份读不懂",不当致命错误。** 没文件(第一次跑)= 一份空会话,不报警;
解析失败 = 挪成 `sessions.json.bad` 备份掉、再开一份空的,日志留一笔。**单条消息的 `role` 故意存
字符串而不是枚举**:以后加 `system` 这类新角色时,老版本读到不认识的词不该把整份历史搬进 `.bad`,
认不出的一律当"对方说的"。另外读回来会做两件清理:`title` 全空的补成"新的对话";`id` **一律重新
发号** —— 盘上的 id 只用来找"上次停在哪一条",找完就没用了(手工改过的文件里 id 可能重复、可能
是 0,而内部认人全靠它)。`active` 指不到人时退回第一条。

**验证**(本机,`RUST_LOG=info`):点两次「+ 新建对话」→ 文件立刻出现三个会话、`active` 跟着走;
右键置顶第 1 条、标未读第 2 条 → 文件里 `pinned` / `unread` 同步;杀进程重启 → 面板原样回来
(图钉、未读点、选中的那一条都对得上);把文件写成半截 JSON → `sessions.json.bad` 出现、本次开一份
空的;手写"id 重复 + 空标题 + `active: 999` + `role: "system"`"的文件 → 读回三条、active 退回第一
条,再点一下新建落盘,id 已经重排成 1/2/3/4、空标题补成"新的对话"、认不出的角色当回复;
`"sessions": []` 配 `schema: 9` → 一条"新版本写的"警告 + 一份空会话。**注意本机 `RUST_LOG` 是
`warn`**:info 级的"读回 N 个会话"看不见,验证时得临时把 `RUST_LOG` 设成
`info,mcwp_wallpaper=debug`。

落点:新文件 `mcwp-wallpaper/src/sessions.rs`(会话数据 + 落盘,整体从 `main.rs` 搬出来)、
`main.rs`(`mod sessions`、`Sessions::load()`、每帧与退出前各一次 `flush()`)。

### 11.13 接上模型:一次调用 + 严格 JSON + 本地降级(2026-10-15)

**这一环到底在干什么。** 用户一句话 → 模型返回 `{reply, mode, image_prompt, spec}` → 本地校验 →
换壁纸。**不做"多智能体"**:方案 3.1 已经定了主力是"模型写规格、本地渲染",参数空间被 4 个预设锁死,
再套一层"提示词智能体"只会把成本、延迟、失败点全都翻倍。"先设计提示词、再喂给图像模型"那套是 3.2 的
B 档(文生图)才需要的,而且也得等这一档跑通、发现效果不够之后再上。

**一次调用怎么保证拿到能用的 JSON。** ①system 提示词里塞 `mcwp_spec::presets::catalog()`(预设目录 +
每个参数的范围),把"能填什么"讲死;②明说"只输出一个 JSON 对象,不要解释、不要代码块";③本地提取时先拆
围栏、再取第一个 `{` 到最后一个 `}`,模型开头那句"好的,这是你要的规格:"顺手就被剥掉;④
`WallpaperSpec::parse` + `normalize()` 兜底:越界值夹紧、未知预设拉回默认、非法色值走预设调色板 ——
3.6 那句"模型怎么胡说都不会渲染崩"在这里落地;⑤解析失败就把错误原样丢回去让它重写一遍(比本地"猜着修
JSON"靠谱);⑥两次都不行 → 本地降级:关键词挑预设 + 情绪词调参数(3.4 的 L1),回复里说清楚"模型没接上"。
**`draft()` 永不返回错误**:用户敲了字,桌面必须有反应,不能弹错误框。

**T2 / T3 的区分交给模型自己填。** 同一个 JSON 里多一个 `mode`:`tweak` 只改参数、**不入壁纸库**;
`create` 才是新壁纸 + 入库。少了这个字段,聊两句库里就一堆垃圾(3.5 那条"不是聊一句生成一次"的要求)。

**绝不同步等。** 模型是秒级往返,主循环是 60 fps:发请求丢后台线程,结果从 `ai_rx` 回到主循环落地
(回复进会话、spec 换上去、该入库的入库)。等待时面板显示"正在生成壁纸…";这期间用户切走了会话,回复回来
会**挂个未读点**;把会话删了,那条结果直接丢掉 —— 不然"删了还生效"很怪。超时 45 s(3.4 里那个 3 s 是给
T1 环境联动用的;T3 是用户主动等结果,3 s 太紧)。

**没配模型也得能用。** `ai.json` 不存在时 `Config::load()` 给的是"去哪儿配 + 免费的有哪几家"的人话,
面板把这句话写进会话 —— 而不是弹错误框,也不是发完消息毫无反应。

**配置与试服务商。** 优先级:环境变量(`MCWP_AI_KEY` / `MCWP_AI_BASE_URL` / `MCWP_AI_MODEL` /
`MCWP_AI_THINKING`,给"临时试一家"和自检用) > `%APPDATA%\MC壁纸\ai.json`(日常用,key 不进仓库) >
内置默认(**智谱 GLM-4-Flash**)。全是 OpenAI 兼容的 `/chat/completions`,换服务商只改一行。实测本机
直连可用:智谱 GLM-4-Flash(**免费**,内置默认)、硅基流动(注册送额度)、OpenRouter / Groq(免费档,要能
连外网)、DeepSeek(按量计费);Gemini 的免费档直连不通,得挂代理。

**选型落地:先智谱 GLM-4-Flash(2026-10-15)。** 12.2 待定项 1 到此有了临时答案 —— 免费、国内直连不用
代理、接口就是 OpenAI 那套,先拿它把 T2/T3 跑顺,效果不够再谈付费档。两个具体的坑记在这儿:①模型名
写全 `glm-4-flash-250414`(智谱的定价表、并发表都按这个版本号列,`glm-4-flash` 是别名);②智谱**还有
一个也免费的 `glm-4.7-flash`**,更新更强,但 4.7 系列**默认开深度思考**(官方原话:"GLM-4.7 系列默认
开启 Thinking"),一句"换张壁纸"也要先想十几秒。所以客户端多了一个**可选**的 `thinking` 字段 —— 只在
`ai.json` 里显式写了才序列化进请求体,不写就完全不出现在 body 里;理由和前面不传 `response_format`
一样:别家不认这个字段,传了可能直接 400。至于 4 代的 `glm-4-flash`,它不在支持 thinking 的名单里,
不配这个字段就是最快的那档。

**回归怎么跑(不花钱、不用 key)。** 新增 `tools/fake-ai-server.py` —— 一个假的 OpenAI 兼容服务,专给
这条链路做离线自检,还能演坏:`--mode broken` 先回半截 JSON(验"带错误重试一次",服务端日志里能看到两次
请求)、`--mode bad` 回越界的 spec(验夹紧)、`--mode html` 回一坨 HTML(验报错与降级)、`--mode slow`
慢 3 秒(验等待态)。宿主这侧加了两个入口:`--ai-selftest "…"`(不开窗口,直接打印回复 / 模式 / 指纹 /
完整 spec)和 `--panel --ai-ask "…"`(开面板并替用户把这句话发出去)。后一个是**唯一能整条链路自检的
办法** —— 合成的键盘输入会被本机中文输入法吃掉,打字那条路验不了。

实测(假模型 + 真配置文件两条都跑过):正常一轮 → 回复进会话、spec 换上去、状态行显示"已换壁纸 ·「…」"、
面板玻璃色随新调色板变;`broken` → 两次调用后成功;`bad`(预设名乱写 + 参数 4.2 + 色值 `#GGGGGG`)→
预设拉回 `rainy_window_city`、参数夹到范围内、色值回落到预设调色板;`html` → 降级回复 + 内置预设、
`calls=1`;`mode=create` → 壁纸库多一条(实测 `library\edca2eaf….json`)、`mode=tweak` → 不入库;
没配 key → 一句人话提示。

**顺带修掉的坑**:降级关键词表里原来写了单字"纸" —— 本产品里"壁纸"出现率最高,一个"纸"会把所有请求都
判成极简纸感(假模型自检第一次跑就踩到),Rust 与假模型两边都改成"纸感 / 纸张"。

**真 key 那一轮(2026-10-15 晚):一句都跑不通,根因是"数组写成了字符串"。** 配上真 key 之后第一句
话就降级了。新加的 debug 级"模型原文"日志把真相摆出来了:glm-4-flash 给的整份 spec **只有一处**
不对 —— `"keywords": "雨夜城市"`,契约要的是数组,`from_value` 直接报 `invalid type: string,
expected a sequence`。更要命的是**重试没用**:把错误原样丢回去让它重写,它照抄原来那份(实测两次
一字不差),白等 7 秒还照样降级 —— 也就是说上一个 commit 里"读不懂就让它重写一次"这条,对**形状**
类错误是纯浪费。于是加了 `repair_shape()`:解析前先按"已经踩过"的几种走样就地修一遍(单元素数组写成
裸字符串、单个对象写成裸对象、数字与布尔写成字符串、`scene.params` 的值写成字符串),修完再解析,
并把修了哪几处记进 `info` 日志(3.4 那条"AI 的一切行为都要可见")。同时提示词里写明"凡是「一串
东西」的字段都得写成数组"——**那才是根因**;`repair_shape()` 留着当保险,不再指望它是主路径。

实测:改完连跑三条提示词(`你好?` / `我要赛博朋克的城市夜景` / `把壁纸调冷一点、安静些`)全是
**一次调用、不降级**,6.4~7.8 s(此前是 2 次调用 + 13.8 s + 降级);`mode` 该 create 的 create、
该 tweak 的 tweak,库里因此没有多出垃圾条目。面板里用真 key 走的那一轮(`--panel --ai-ask`)也通了:
回复进气泡、状态行显示换了哪张、玻璃色跟着新调色板变。

一个单测逮到的细节:`repair_shape` 把字符串数字转回来时,`seed` 是 `u32` —— 塞 `20261014.0` 进去
serde 会报 `expected u32`,修形状反而修出个新错。所以整数一律落成整数(`number_value()`)。

落点:`app/crates/mcwp-ai/`(新 crate:配置 + 客户端 + 提示词 + 解析 + 降级;HTTP 用 `ureq` +
native-tls,**不引 reqwest** —— 那会把 tokio 拖进依赖树)、`mcwp-wallpaper/src/main.rs`(后台线程 +
落地用的 `ai_rx` + 两个自检入口)、`tools/fake-ai-server.py`。

### 11.14 模型配置搬进面板设置页 + 保存即生效(2026-10-15)

**这一页为什么非做不可。** 11.13 接上模型之后,"配一次"的动作还是"自己摸到 `%APPDATA%` 手写一份
JSON" —— 开发时自己写没问题,给别人用就是劝退。设置页于是从占位文案换成真表单:接口地址 / 模型名 /
API Key / 「深度思考」三档 + 保存,一屏之内说完"怎么让生图能用"。

**保存之后不用重启程序,这条是硬要求。** 面板是核心进程内的一个窗口(见 11.6),配置落盘之后就地
`Client::new` 换掉主循环里那个 `Option<Client>`,下一句话就走新配置 —— "配完还得重启"是这类设置页最容易
挨骂的地方。写盘失败则**保留旧客户端**:配置没写成,已经有的能力不该跟着一起消失(状态行照实报错)。
另外三种收尾各有各的话,因为用户看到的"没反应"其实是三件事:落盘成功但没填 key → "已保存 · 还没填
API Key"(**不算错误**,先存地址回头补 key 是正常用法);环境变量在生效 → "已写入 ai.json · 但环境变量
在生效,实际用的是它们";真失败 → "保存失败:<原因>"。

**设置页的状态故意不进 `PanelState`。** `refresh()` 会在换壁纸、切会话、改参数时随时整块回填面板,而
设置页那几个输入框里可能就是用户**敲到一半**的 key —— 塞进 `PanelState` 等于每次别处的动静都可能把
正在敲的字冲掉。所以它单独走 `PanelHandle::refresh_ai()`,只在「面板刚打开」和「保存成功」两个时刻灌
一次(`AiConfigState` 的注释里写了理由)。这个是"整块回填"这套投影式 UI 的固有陷阱,和 11.9 里
"切视图必须用 `if`"是同一类问题。

**`Stored` 从私有 `ConfigFile` 提成公开类型。** 面板要回填输入框时多半**还没配 key**,而
`Config::load()` 那种情形直接报错(它是"能不能用",不是"盘上写着什么"),回填不了。于是把落盘的字段
单独定义成 `Stored`,读写共用一份定义免得两边漂移;`Config::stored()` 给回填用(空字段补内置默认,
**故意不合并环境变量** —— 界面显示的是"这份文件的内容",改了才写得回去),环境变量盖没盖住由
`Config::env_override()` 单独告诉界面,页面上就此多一行提醒。落盘沿用会话那套"临时文件 + 改名" +
带缩进输出(见 11.12):这份文件里存着 key,写坏最难查,而用户自己打开看 / 手改也要好看。

**「深度思考」是三档而不是一个开关。** `None`(**字段根本不落、请求体里也不带**)和 `Some(false)`
(发 `disabled`)是两个不同的请求体:不认 `thinking` 的服务商只能走前者,而智谱 4.7 系列想显式关掉它。
一个布尔开关表达不了这三件事,所以界面上是一排小胶囊(`不发` / `开启` / `关闭`),面板传下标、
Rust 侧 `ThinkingChoice` 认不出的按「不发」兜底。

**两个踩在渲染器上的坑(都是静默的)。** ①API Key 这个框**不能用** `input-type: password`:Slint 的打码
字符是 `●`(U+25CF),内嵌子集字体里没有这个字形(见 11.9),缺字是静默不画 —— 用户看到的是一排空框,
比明文还糟(会以为没填进去),所以这里保持明文。②状态行原来写 `height: 14px` 配 11px 的字,**软件渲染器
会把整行裁掉**(不是截断,是一个像素都不画),状态文字于是静默消失 —— 改成 20px 才画出来。

落点:`mcwp-ai/src/lib.rs`(`Stored` / `stored()` / `save()` / `env_override()` / `read_stored()`)、
`mcwp-ui/ui/panel.slint`(新增 `FieldRow` / `ChoiceRow` 两个组件;TextInput 没有 placeholder 属性,
灰字占位得自己补一层,且必须声明在输入框**之前**,否则那层灰字会盖住输入框吃不到点击)、
`mcwp-ui/src/lib.rs`(`AiConfigState` / `ThinkingChoice` / `refresh_ai()`)、
`mcwp-wallpaper/src/main.rs`(`ai_config_state()` / `save_ai_config()`,后者负责落盘 + 就地换客户端)。
实测:空配置打开 → 地址与模型名已填好、API Key 是灰字占位;点保存 → `ai.json` 按默认写出来、状态行
"已保存 · 还没填 API Key";三档挨个保存 → 文件里依次是**无 `thinking` 字段 / `false` / `true`**;
把地址指向本机假服务(8788)保存 → **不重启**下一句就走新服务商,状态行回显新地址与模型名。

### 11.15 对话改成左右交互 + 「暂停 / 继续」这一轮(2026-10-15)

**左右分栏那个 bug 值得记一笔。** `MessageRow` 是 `HorizontalLayout`:靠左的气泡要在气泡**后面**垫一个
`horizontal-stretch: 1` 的填充块,靠右的气泡要把填充块垫在**前面**。原来两个分支的填充块都写在气泡
之前,于是"往左推"和"往右推"同时生效 —— AI 的回复也被顶到了右边,看起来像双方都说在了同一个人的位置。

**「暂停」停的是这一轮,不是整个界面。** 输入区的按钮是三态(`run-state`:0 闲着 / 1 正在跑 / 2 已暂停):
闲时是「发送」胶囊,跑的时候换成一颗**圆钮**(自绘的深色方块),暂停之后变成「继续」胶囊。外层固定
76px 宽,三态切换时按钮不左右跳。

**HTTP 请求掐不断,所以"暂停"只能是"回来就丢"。** `ureq` 没有取消接口,后台线程照样跑完那几秒;于是
Rust 侧把这一轮做成一份可重放的记录 `Mission { session, text }` + 一个自增 `run_id`:

- 发送 / 继续都 `run_id += 1`,结果回来时**认轮次**,对不上直接扔(日志"丢掉过期的一轮");
- 暂停 = `Running` 换成 `Paused`,请求不作废、但结果注定认不上;
- 继续 = 拿那份 `Mission` **原地重跑**,并且**不重新往会话里塞用户那句话**(它已经在会话里了,再塞一遍
  就变成两条 —— 实测确认);会话在暂停期间被删掉就不续了,状态行照实说"这条会话已经删掉了";
- 暂停期间用户又发新消息:按钮先变回「发送」(`draft` 一非空就切),发送即**取代**上一轮,不是排队。

**钉到底部:三个 Slint 坑,全是静默的。**

1. `viewport-y` 是**滚动偏移,往下滚是负值**,"到底"的位置是 `height - viewport-height`。写成正数会被
   Flickable 自己夹回 0(合法区间是 `[height - viewport-height, 0]`,见 `i-slint-core` 的
   `ensure_in_bound`),表现就是"列表永远停在顶部,最新那条得手动滚"。
2. 消息数组变的那一刻布局还没重算,这时候读 `viewport-height`(绑着 `msg-list.preferred-height`)拿到
   的是旧值,算出来的偏移量差一条。而"内容高度一变就去写 `viewport-y`"这条更直接的路会 panic
   (`Recursion detected`,那个通知正好从布局求值中间发出来),绕一层本地属性也一样;`init` 里直接读 / 写
   这两个属性同样 panic。
3. 所以钉底部改成一个 `16ms × 8` 的短命定时器:每次 tick 重新读一遍高度、重钉一次,总有一次读到的是
   布局重算之后的值。停的条件**只能是次数** —— 写"钉到位了没"会让它拿旧值判断,第一次就把自己停掉。

另外:需要图标就自绘(矩形 / 圆),别指望字体字形,也别用 `Path` —— Slint 软件渲染器里 `draw_path` 是
空实现,三角之类会**静默不画**(本来想用三角表示「继续」,实测踩过,最后改用文字胶囊)。

落点:`mcwp-ui/ui/panel.slint`(`MessageRow` 的左右分栏、`RunButton`、输入区三态按钮、`Flickable` 的钉底
逻辑)、`mcwp-ui/src/lib.rs`(`UiEvent::PauseRun` / `ResumeRun`、`RunState` / `set_run_state()`)、
`mcwp-wallpaper/src/main.rs`(`Run` 状态机、`start_run()` / `run_mission()`、`AiOutcome.run`)、
`mcwp-wallpaper/src/sessions.rs`(`exists()`:暂停期间会话被删的判断)。
实测(`--ai-ask` 起一轮,再点圆钮 / 点「继续」):点暂停 → 圆钮变「继续」+ 状态行"已暂停 · 点继续接着跑这
一句";点继续 → 回到圆钮,旧请求落地时被丢掉、新请求正常落壁纸;全程会话里那句话只有一条。
