## 一、技术选型:用 Rust 合适吗?

**结论:合适,而且是这个场景里最合适的一档。** 但要说清楚:Rust 本身不保证「占用小」,真正吃内存的是 **WebView2 和 GPU 上下文**,所以「用什么写 UI」比「用什么语言」更决定内存。

推荐组合:

| 层 | 推荐方案 | 理由 |
| --- | --- | --- |
| 常驻核心(托盘 / 壁纸宿主 / 桌宠 / 调度) | Rust + `windows-rs` | 无 GC、无运行时、空闲 CPU 极低,可精确控制内存与线程 |
| 壁纸渲染 | `wgpu`(WGSL 着色器) | 跨后端(DX12/Vulkan),着色器可热重载,渲染几乎不占 CPU |
| 桌宠渲染 | `winit` + 分层透明窗口 + `wgpu` 精灵图 | 与壁纸共用同一 GPU 栈,不额外引入 UI 运行时 |
| 控制面板 | **Slint(已定)** | 纯 Rust、无 WebView2,内存比 Tauri 低 80-150 MB;单文件部署,不需要额外运行时 |
| 数据存储 | SQLite(`rusqlite`)+ 文件目录 | 单文件、零运维、易备份迁移 |
| AI 接入 | `reqwest` + Provider 抽象层 | 云端 OpenAI 兼容接口优先,本地模型可选 |
| 进程通信 | 命名管道 / Tauri command(JSON-RPC) | 面板与核心解耦,面板崩溃不影响壁纸 |

三条重要提醒:

- **不要把所有东西塞进一个进程**。壁纸渲染建议独立进程 + 看门狗,坏着色器/坏壁纸最多闪退一个子进程,自动回退「最后可用壁纸」。
- **不引入 WebView2**(已定 Slint)。连带影响:「Web 壁纸」形态在 MVP 直接砍掉(C 方案),只保留程序化着色器 + AI 单图两种;桌宠与面板全部走原生渲染。
- **Slint 面板放核心进程内**:窗口按需创建、关闭即析构(释放窗口与纹理),不做独立进程——Slint 没有动态代码执行,崩溃风险远低于 WebView,不值得为它多一个进程。若后续面板复杂度暴涨,再拆进程。
- **壁纸预览用像素回读**:面板里的"实时预览"把渲染目标缩到 480×270,以 1-2 fps 回读成 Slint `Image`(约 0.5 MB/帧),避免做 GPU 纹理共享,省事且够用。
- **GPU 上下文也不便宜**(首次初始化 30-60 MB 显存 + 几十毫秒)。单例 `wgpu::Device` 全程序共享。

### 性能预算(建议写进验收标准)

| 指标 | 目标 | 备注 |
| --- | --- | --- |
| 常驻内存(面板未开) | ≤ 100 MB | 壁纸 50-70 MB + 桌宠 10-20 MB + 核心 15-25 MB(Slint 替换 Tauri 后下调) |
| 空闲 CPU | ≤ 1% | 静态/微动壁纸 |
| 动画壁纸 CPU | ≤ 3-5%(单核) | 帧率上限可选 30/60 |
| 冷启动到托盘 | ≤ 800 ms | 壁纸异步加载 |
| 换壁纸首帧 | ≤ 300 ms | spec 渲染本就在 GPU 上毫秒级 |
| 安装体积 | ≤ 15 MB | 不含本地模型;无 WebView2 运行时依赖 |

## 二、总体架构与进程模型

```
┌──────────────────────────────────────────────────────────────┐
│ mcwp-core.exe  常驻,Rust,唯一「长期活着」的进程              │
│  tray │ scheduler │ signals │ spec │ library │ ipc │ config  │
└──┬──────────────┬────────────────┬───────────────────────────┘
   │              │                │
┌──▼───────┐ ┌────▼─────────┐ ┌────▼──────────────┐
│ 壁纸宿主  │ │  桌宠宿主     │ │ 面板窗口(同进程)   │
│ WorkerW  │ │ 透明置顶窗口  │ │ Slint             │
│ wgpu     │ │ wgpu 精灵图   │ │ 按需创建 / 关闭析构 │
└──────────┘ └──────────────┘ └───────────────────┘
                     │
       云端 AI 调用(HTTP,核心进程内直连)
             ┌───────▼──────────┐
             │ AI Worker(可选)  │ 仅本地模型 / 文生图时才起,用完退出
             └──────────────────┘
```

核心模块职责:

- **signals**:亮度、前台应用、空闲时长、时间、电源、全屏状态采集(见第四节)
- **spec**:壁纸规格 JSON 的定义、校验、修复、版本迁移
- **library**:SQLite 壁纸库 + 缩略图/缓存文件
- **scheduler**:生成任务队列(T0-T3 分级)、冷却、电源策略、失败重试
- **ipc**:面板/桌宠/渲染器与核心的通信契约
- **pet**:桌宠状态机 + 动画映射 + 交互事件
- **render**:wgpu 场景图与着色器库(预设场景 + 参数化)
- **panel**:Slint 控制面板(同进程,按需建窗;关闭即释放窗口与纹理)

## 三、壁纸怎么「AI 生成」(本项目最核心的设计)

> **2026-10-15 更新:本章 3.1 / 3.2 / 3.6 的主线(模型写 spec、本地渲染)已经推翻。**
> 实测下来模型直接出图好看得多,而"画面的每一处细节都不再由本地代码决定"之后,那些滑杆能调的
> 只剩"像不像原来那个场景",留着反而是误导。现在壁纸**只有一种来源:一张图**。
> 推翻的经过、以及现在长什么样,见 §11.9 与 §11.16;本章原文保留,只作决策记录。

### 3.1 关键决策:不让 AI 直接画图,而是让 AI 写「壁纸规格」

让 LLM 输出一份结构化的 `WallpaperSpec`(JSON),由本地**参数化渲染器**实时渲染。对比:

| 方案 | 出图耗时 | 单张体积 | 可微调 | 花费 | 结论 |
| --- | --- | --- | --- | --- | --- |
| LLM 直接生成图片(文生图) | 3-20 s | 1-5 MB | 只能重画 | 每次都有成本 | 只用在「显式创作」档 |
| **LLM 生成 spec + 本地渲染** | **10-50 ms** | **1-3 KB** | 滑杆随便调 | 近乎为零 | **主力方案** |
| AI 单图 + 2.5D 动效 | 3-20 s | 1-5 MB + 深度图 | 半可调 | 按需 | 作为「高级观感」可选 |

spec 方案的好处是连锁的:毫秒级切换、KB 级存储、可撤销、可分享(一张壁纸就是一个 JSON)、可确定性复现、GPU 开销低、风格统一不容易崩。

### 3.2 三种壁纸形态(按优先级)

- **A. 程序化场景着色器(WGSL)— MVP 主打**
  预设场景库 + 参数调优:雨夜城市、深林晨雾、极简几何、星云、像素房间、流体、粒子场、昼夜光照。
  参数量控制在 20-40 个(调色板、动势、密度、模糊、视差强度、光源方向、噪波尺度…),LLM 只填这些数值,渲染结果就不会难看。
- **B. AI 单图 + 2.5D 动效 — 观感最「AI」**
  文生图得到一张主图 → 轻量深度估计模型(Depth-Anything 小模型 / MiDaS,ONNX 运行)生成深度图 → 视差位移 + 体积光 + 粒子 + 呼吸式缩放。
  一张静态图立刻变成有纵深的动态壁纸,这是差异化卖点。
- **C. Web 壁纸 —— MVP 砍掉(因面板已选 Slint,不引入 WebView2)**
  原设想是 LLM 生成 HTML/Canvas 跑在沙箱 WebView2 里。为了内存与体积,这个形态推迟到 v1.x 再评估,不作为路线图承诺。

### 3.3 生成管线

```
[对话 / 桌面亮度 / 工作状态 / 时间]
        ↓  (提取与压缩,本地)
   情绪 + 意图向量(mood vector)
        ↓  (可选,仅 T2/T3 触发)
   LLM 结构化输出(strict JSON schema)
        ↓
   Schema 校验 → 修复重试 → 与「用户风格档案」合并
        ↓
   wgpu 渲染 → 交叉淡入应用(1.5-3 s)→ 缩略图 + spec 入库
        ↓ 失败 / 信息不足
   环境降级渲染(3.4)
```

### 3.4 信息不足时的四级降级(回答「提不出元素怎么办」)

| 级别 | 条件 | 做法 | 用户感知 |
| --- | --- | --- | --- |
| L0 纯环境 | 完全没有对话输入 | 只按时间/亮度/季节/电源挑预设场景与配色 | 壁纸随昼夜自然变化 |
| L1 局部微调 | 有效信息很少 | 不换场景,只平移调色板/亮度/动势(基于当前壁纸) | 氛围变了,构图没变 |
| L2 档案约束 | 有情绪但无视觉意象 | 用「我的风格档案」(主色、题材偏好、禁用元素),LLM 只输出修饰项 | 仍是用户喜欢的风格 |
| L3 主动询问 | 连续沉默后用户又激活桌宠 | 桌宠气泡问一次「要不要换个氛围?」,最多一次,不追问 | 可选,可永久关闭 |

**原则:LLM 超时(默认 3 s)或失败,直接走 L1/L0,绝不卡住、绝不让壁纸黑屏。**

### 3.5 生成节奏:不是「聊一句生成一次」

| 级别 | 触发条件 | 产物 | 成本 | 频率上限 |
| --- | --- | --- | --- | --- |
| **T0 实时** | 每帧 | 调色板/动势插值 | ≈0 | 连续 |
| **T1 环境** | 亮度/时间/工作状态变化超阈值 | 同一 spec 重渲染 | < 50 ms,纯本地 | 每 5-15 min |
| **T2 指令** | 用户明确下指令:「暗一点」「换冷色调」「别动那么快」 | **只改当前 spec 的参数,不新建库条目** | 1 次 LLM 调用,或纯本地规则匹配 | 冷却 ≥ 30 s |
| **T3 显式创作** | 用户说「替换壁纸 / 生成一张壁纸 / 我要赛博朋克」 | **新 spec → 壁纸库新条目 + 应用** | 1 次 LLM 调用(可选文生图) | 手动,高频时合并请求 |

**核心原则(按你的选择):只有用户明确说「替换 / 生成壁纸」时才产生新壁纸,其余时间壁纸只随工作状态与环境变化。**

- 闲聊与情绪表达**不再触发**新壁纸生成,只更新内部情绪向量(留作以后可选功能),避免"聊两句桌面就变天"。
- 状态驱动的变化走 T1 / 状态主题组(见 3.7),不产生库条目、不调 LLM、也不改文件,随时可回滚。
- T3 应用后一定给**可解释提示**:气泡显示提取到的关键词(如 `雨 / 夜 / 蓝紫`),并提供一键撤销、一键锁定。
- 全屏游戏/会议投屏/电池模式下,自动变化全部静默(只保留亮度跟随),避免投屏时桌面突变。

### 3.6 WallpaperSpec 示例

```json
{
  "schema": 1,
  "id": "auto-20261014-0031",
  "title": "深夜实验室 · 雨",
  "source": "conversation",
  "keywords": ["雨", "夜", "专注", "蓝紫"],
  "mood": { "calm": 0.7, "focus": 0.8, "energy": 0.3 },
  "palette": ["#0B1020", "#1B2A4A", "#4F7CFF", "#9BB8FF", "#E6ECFF"],
  "scene": { "preset": "rainy_window_city", "params": { "rain": 0.7, "blur": 0.35, "parallax": 0.25 } },
  "motion": { "intensity": 0.45, "speed": 0.6 },
  "lighting": { "mode": "auto_ambient", "keyLight": 0.5, "followDesktopBrightness": true },
  "elements": [{ "type": "particles", "count": 120 }, { "type": "grid", "opacity": 0.08 }],
  "overlay": { "clock": true, "quote": "今天先跑通 MVP" },
  "seed": 87123
}
```

要点:`seed` 保证确定性复现;`lighting.followDesktopBrightness` 让壁纸亮度跟随桌面环境;`params` 全部有取值范围与默认值(校验器负责夹紧,LLM 输出越界也不会出事)。

### 3.7 状态主题组(「根据工作状态改变」的具体落地)

不靠 LLM,纯本地配置 + 着色器参数,做到「壁纸跟着状态走」:

- 定义若干**状态槽位**:`专注 / 阅读 / 休闲 / 夜间 / 会议 / 离开`,每个槽位绑定「场景预设 + 参数偏移 + 调色板」。
  - 例:专注 → `rainy_window_city` 冷蓝、低动势、暗背景;阅读 → `minimal_paper` 暖色低饱和、近乎静止;夜间 → 跟随亮度并压暗、减少蓝光;会议 → 极简、低动势、关气泡。
- 状态切换由感知层事件驱动(见第四节),带 1.5-3 s 交叉淡入,并在气泡里说明原因(「检测到你在写代码,已切到专注氛围」),可在设置里关掉提示。
- 每个槽位的场景与参数**全部由用户在面板里改**,并支持「用当前壁纸填充该槽位」;未配置的槽位继承默认表。
- 状态变化只在槽位间切换,**不产生壁纸库条目**;想留住某一刻的状态,面板上有「存为壁纸」按钮,把当前运行时参数快照成一条库记录。
- 亮度联动优先级最高:无论处于哪个槽位,`followDesktopBrightness` 都在生效(见第四节「亮度联动策略」)。
要点:`seed` 保证确定性复现;`lighting.followDesktopBrightness` 让壁纸亮度跟随桌面环境;`params` 全部有取值范围与默认值(校验器负责夹紧,LLM 输出越界也不会出事)。

## 四、感知层:亮度 / 工作状态 / 上下文

| 信号 | 采集方式 | 频率 | 隐私处理 |
| --- | --- | --- | --- |
| **桌面亮度/色调** | DXGI Desktop Duplication 抓帧,降采样到 64×36 求平均亮度、对比度、主色 | 1 fps,变化 > 5% 才处理 | 只保留统计值,原始帧只在内存,不落盘、不上传 |
| 物理亮度(可选) | DDC/CI 读显示器亮度,或环境光传感器 | 30 s | 本地 |
| 工作状态 | 前台窗口**进程名** + 空闲时长(GetLastInputInfo)+ 输入速率 | 1-5 s | 默认不读窗口标题,可选 |
| 时间/季节 | 系统时间 | 60 s | 本地 |
| 电源/全屏 | 电源状态、前台是否全屏独占 | 事件驱动 | 本地 |
| 对话上下文 | 与桌宠的聊天内容 | 事件驱动 | 见第九节 |

用途映射(状态 → 壁纸倾向):

| 状态 | 判定 | 壁纸倾向 |
| --- | --- | --- |
| 深度专注/编码 | 前台为 IDE/编辑器,输入密集 | 低动势、冷色、低对比、暗背景 |
| 阅读/文档 | 浏览器/文档类 | 暖色低饱和、大留白、几乎静止 |
| 影音/休闲 | 播放器类 | 动势可高、色彩丰富 |
| 游戏 | 全屏独占 | **暂停渲染**(省电省 GPU) |
| 会议/投屏 | 摄像头/会议类进程 或 日历 | 静默、极简、低动势,不弹气泡 |
| 离开 | 闲置 > 5 min 或锁屏 | 降帧;锁屏时可选展示「屏保模式」 |
| 夜间 | 22:00 后 | 降蓝光、降亮度,配合 `followDesktopBrightness` |

亮度联动策略(避免「白天瞎、晚上刺眼」):

1. 壁纸整体亮度 = 桌面平均亮度平滑目标值 × 用户强度系数(默认 0.6),用 2-3 s 缓动,不做突变。
2. 只调「明度/对比/光源强度」,不动构图与配色倾向,否则会显得脏。
3. 提供「跟随亮度」总开关与手动基线,敏感用户可关。

## 五、壁纸库设计

- **条目 = spec(JSON,1-3 KB)+ seed + 缩略图(≤512 px WebP)+ 来源标签 + 时间戳 + 收藏/锁定**
- **什么会进库(按已定决策)**:只有 ① 用户显式生成的壁纸 ② 导入的 spec/图片 ③ 收藏 ④ 手动「存为壁纸」的状态快照。状态切换与亮度联动都是**运行时状态,不落库**,所以库不会被自动行为污染。
- 生成的位图只作为**缓存**,可随时重建;spec 才是「真相源」。因此:壁纸库极轻、可导出分享(一个 `.mcwspec` 文件即一张壁纸,换台机器也能复现)。
- SQLite 表:`wallpapers`(spec, hash, source, keywords, created_at)、`tags`、`assets`、`history`(应用记录,支持撤销/回到某天的氛围)、`settings`、`mood_log`。
- 去重:spec 规范化后取 hash,重复则只更新引用与时间,不重复占用空间。
- 缓存回收:LRU,收藏/锁定的条目永久保留。
- 多显示器预留:`wallpapers` 与 `displays` 多对多,同一壁纸可配不同显示器参数。

## 六、桌宠设计:形态、交互与「对话→壁纸」协议

### 6.1 状态机(MVP 用内置精灵图,帧动画 ~200 KB)

`idle / wander / sleep(闲置 > 10 min) / busy(前台是工作类应用) / listening / thinking(生成中) / speak / notify / error`

状态由「感知层 + 调度器」驱动:生成中会真的切到 thinking 动画,壁纸换好再 speak 一句——**桌宠是系统的可视状态机**,不是装饰。

### 6.2 鼠标交互映射(推荐默认,回答「单击还是双击」)

| 操作 | 行为 | 为什么这样设计 |
| --- | --- | --- |
| 悬停 | 眼神/身体跟随鼠标,轻微呼吸 | 有生命感,零打扰 |
| 单击 | 轻交互:打招呼、随机动作、或展示 1 条待办 | 误触成本低,**不弹窗** |
| **双击** | **打开对话面板**(聊天 + 输入框) | 明确意图才开窗,符合桌面软件直觉 |
| 右键 | 上下文菜单:换壁纸 / 撤销 / 锁定 / 暂停 / 设置 / 退出 | 惯例位置 |
| 拖拽 | 移动位置,松手吸附屏幕边缘或任务栏 | |
| 长按(可选) | 语音输入 | |
| 全局热键 | `Alt+Space` 或 `Ctrl+Alt+M` 呼出输入框 | 键盘流用户 |

### 6.3 信息交互的三个层级

1. **气泡(toast)**:非打断,3-5 s 自动消失。用于「已换成偏暖的壁纸」「生成中…」「已撤销」这类状态通知。
2. **对话面板**:完整聊天 + 快捷动作按钮(换一张 / 撤销 / 锁定 / 再冷一点)。可脱离桌宠独立停靠。
3. **控制面板**:设置、壁纸库、创作器(见第七节)。

### 6.4 对话怎么变成壁纸(协议细节)

每条消息先做**意图分类**(本地小模型或规则 + 云端 LLM,几百毫秒):

| 意图 | 例子 | 处理 |
| --- | --- | --- |
| 闲聊 | 「今天好累」 | 只回话,不动壁纸(情绪值可驱动桌宠表情) |
| 情绪表达 | 「有点烦,想静一静」 | 记录情绪 + 回复安慰话术;除非你接着说「换个氛围」,否则不动壁纸 |
| 视觉描述 | 「像雨夜里的霓虹街道」 | 只是描述 → 回应一句「这个意象不错」;带请求语气才走 T3 |
| 指令 | 「换成冷色调」「暗一点」 | **T2**:直接改当前 spec 参数,不新建库条目 |
| 创作请求 | 「替换壁纸」「给我生成一张赛博朋克」 | **T3**:新 spec 入库 + 应用(可含文生图) |

触发规则(已按你的决策收敛):**只有「指令」和「创作请求」会改变壁纸**;闲聊、纯情绪表达、单纯视觉描述一律不动壁纸,只做对话回应。桌宠可以主动建议一句(「要不要换成雨夜?」),但必须等你点头才执行——保留惊喜感,同时不会失控。

## 八、性能与功耗策略

- **遮挡暂停**:壁纸窗口被最大化窗口完全遮挡 → 降到 1 fps 或暂停(比对前台窗口矩形)。
- **全屏/游戏**:暂停渲染;电池供电:降帧或静态化,恢复到交流电时自动恢复。
- **GPU 复用**:单例 device,切换壁纸只重载场景资源,不重建设备;着色器预编译并缓存。
- **资源池化**:精灵图/纹理复用;桌宠与壁纸共用纹理上传队列。
- **启动优化**:托盘先可用,壁纸异步加载;适配器能力探测结果缓存到配置。
- **失败隔离**:渲染子进程看门狗,崩溃 2 次自动降级为静态壁纸并提示用户。

## 九、隐私与合规(必须在 MVP 就定,后面改很贵)

- **屏幕采样**只产出亮度/主色统计量,原始帧不落盘、不上传;设置里可完全关闭。
- **对话内容**:默认「本地提取摘要 + 情绪向量」,云端只发送用于生成壁纸的摘要文本(不含原始聊天记录);提供「全本地模式」(接本地模型)。原始对话是否留档由用户决定,默认不长期保存。
- **素材版权**:不内置任何受版权保护的素材(例如 Wallpaper Engine 创意工坊内容、动漫角色形象);内置壁纸均为自研着色器或明确许可素材;用户导入的素材责任自负,但需在协议里写明。
- **AI 输出合规**:调用云端模型时遵守其内容条款;提供敏感内容过滤开关。

| # | 验证项 | 做法 | 通过标准 |
| --- | --- | --- | --- |
| 1 | 壁纸挂载 | 用 `windows-rs` 向 Progman 发 `0x052C`,找到 `WorkerW` 并把自建窗口 reparent 上去 | 壁纸在桌面图标之下、任务栏之上;重启 explorer 后自动恢复 |
| 2 | 渲染与开销 | `wgpu` 写一个参数化雨夜场景(WGSL),接 30/60 fps 上限与遮挡暂停 | 动画时单核 CPU ≤5%、显存 <100 MB、切换场景无设备重建 |
| 3 | 亮度采样 | DXGI Desktop Duplication 抓帧 → 降采样 64×36 → 算平均亮度,驱动场景亮度参数 | 亮度变化 1-2 s 内平滑跟随,且不拖慢前台应用 |

### 11.1 实测结论(2026-10-14,本机 Win11 25H2 / Intel UHD + RTX 4060 混显)

**结论 1 —— 挂载:发 `0x052C` 已经不够,必须自己按尺寸挑那一层。**
本机桌面结构是 `Progman → SHELLDLL_DefView →(图标层)`,壁纸层是 Progman 那个铺满屏幕的 WorkerW 子窗口;同时系统里还有约 15 个 136×39 的 IME 宿主也叫 WorkerW。所以不能只按类名找,要**按「是否覆盖主屏矩形」过滤**。

| 挂载模式 | 实测结果 |
| --- | --- |
| `auto`(推荐) | 命中 `Progman 背景层 WorkerW`;图标在最上层、两块屏互不影响 |
| `below-defview` / `progman-worker` | 同样可用,作为兜底 |

**结论 2 —— 呈现:必须走 DirectComposition。**
`CreateSwapChainForHwnd`(`DxgiFromHwnd`)在壁纸子窗口上会「Present 成功但上不了屏」;改成 `CreateSwapChainForComposition` + `IDCompositionVisual`(`DxgiFromVisual`)才稳定上屏。A/B 实测工作集 195 MB → 125 MB。

**结论 3 —— 帧延迟等待对象在本机是性能陷阱。**
`Dx12UseFrameLatencyWaitableObject::Wait` 会让每次取帧固定卡满约 1 秒超时(表现 1 fps);改为 `None` 后稳定 59 fps。已写死。

**结论 4 —— 内存:私有工作集 82 MB,总工作集 120 MB。**

口径说明:程序日志里印的「私有」是 `GetProcessMemoryInfo` 的 `PagefileUsage`(私有提交),和任务管理器的「专用工作集」不是一个口径 —— 同一时刻前者约 119 MB、后者约 83 MB。**验收看后者。**

| 阶段 | 工作集 |
| --- | --- |
| 进程启动 | 7 MB |
| 建 wgpu Instance + Surface | 12 MB |
| 选定适配器 | 46 MB |
| 创建设备 + 管线 + 交换链 | 120 MB |

关键发现:wgpu 的 `Adapter::expose` 会**为每一块适配器创建一个临时 D3D12 设备**来查询能力,本机因此同时加载 Intel 与 NVIDIA 两套驱动,光 `request_adapter` 就吃掉约 33 MB。而裸 D3D12 探针(单设备 + 交换链)只要 66 MB。结论:

- **任务管理器口径(私有工作集)82.4 MB,已达成 ≤100 MB 目标**;
- 总工作集 120 MB 的差额主要是两块 GPU 的驱动 DLL(共享页,并非本进程私有);
- 要再往下压只有一条路:**绕开 wgpu、自绘 D3D12 后端**(预估 70~90 MB),代价是失去 WGSL/跨平台,列为 M2 可选优化,不阻塞功能推进。

已落地的三处内存/性能改动:

1. `MemoryHints::Manual { 4 MB..16 MB }` —— 默认 `Performance` 一上来就开 128~256 MB 显存堆;
2. `desired_maximum_frame_latency = 1` —— 交换链缓冲 3 张降到 2 张(1080p 每张约 8 MB);
3. 只在设置 `MCWP_GPU_INDEX` 时才显式 `enumerate_adapters()` —— 否则每块 GPU 多建一套 DXGI/D3D12 工厂对象,多吃约 35 MB。

### 11.3 M1 面板实测(2026-10-14,同一台机器)

Slint 控制面板按「独立线程 + 独立事件循环 + 关窗即释放」实现,面板进程内不开第二个 GPU 设备。实测(Task Manager 口径的专用工作集):

| 状态 | 专用工作集 | 总工作集 |
| --- | --- | --- |
| 无面板(基线) | 83.0 MB | 116.3 MB |
| 面板打开 | **90.9 MB** | 128.3 MB |
| 关窗后 | 85.4 MB | 123.1 MB |

结论:面板净增约 8 MB,关窗后基本回落到基线(残留 ~2 MB 是 Slint/winit 的堆碎片),**常驻 ≤100 MB 的目标仍然达成**。

**踩到的坑:字体是内存杀手,必须内嵌子集字体。**
Slint 的软件渲染器用 `fontdue` 把 fontdb 查到的那个字面**整份**解析成每个字形的轮廓(不是按用到的字符懒加载)。所以「默认字体是哪个」直接决定内存:

| 面板字体 | 实测专用工作集 |
| --- | --- |
| 不指定(回落到系统 Arial,中文全是方框) | 144 MB |
| `SLINT_DEFAULT_FONT=simhei.ttf`(9.3 MB) | 254 MB |
| `SLINT_DEFAULT_FONT=msyh.ttc`(18.8 MB) | 447 MB |
| **内嵌子集字体(135 KB)** | **90.9 MB** |

做法:`tools/subset-panel-font.py` 从 Noto Sans SC(OFL,可自由内嵌;微软雅黑许可不允许)抽出面板用到的字符,子集化成 135 KB 的 ttf(607 字形,族名改成 `MCWP Sans`,避免和用户机器上已装的 Noto 撞名),由 `panel.slint` 的 `import "*.ttf"` + `build.rs` 的 `EmbedFiles` 直接编进 exe,运行时用 `register_font_from_memory()` 注册,并在窗口上设 `default-font-family: "MCWP Sans"`。

两个附带结论:

- `load_system_fonts()` 本身只建元数据,**约 1 MB**,不是元凶;真正吃内存的是 fontdue 对选中字面的解析。
- 面板字体是子集,动态文案(预设名、以后的 AI 生成标题)冒出表外字符会**静默缺字**。所以 Rust 侧加了 `mcwp_ui::missing_chars()`,启动和刷新状态文字时把缺字打 WARN,提醒重跑子集化脚本。

### 11.4 液态玻璃改版(2026-10-14 同日)

面板视觉从第一版的「深色科技风」改成 **iOS 26 液态玻璃**。依据是 Apple HIG 的 *Materials / Liquid Glass* 和 WWDC25 §219《Meet Liquid Glass》,落到 Slint 软件渲染器上只剩三条能做的:

1. **玻璃是「功能层」,浮在内容层上。** 窗口里先铺一整层「环境底」(由当前壁纸调色板推出来的斜向渐变 + 两团彩色光斑),一整块玻璃铺满窗口盖在上面;
2. **没有 backdrop-blur,折射(lensing)只能伪造**:半透明染色 + 顶部镜面高光 + 左右边缘反光 + 底部内缘暗线,拼出「玻璃有厚度」的错觉;
3. **不做 glass on glass**:玻璃内部只用薄填充(卡片)、白纱和发丝线,不再叠第二层玻璃。

实测(任务管理器口径):

| 状态 | 专用工作集 | 总工作集 |
| --- | --- | --- |
| 无面板(基线) | 84.1 MB | 117.2 MB |
| 面板打开 | **92.2 MB** | 129.7 MB |

改版没把面板做大:玻璃铺满窗口换来了一点绘制面积,净增约 8 MB,和改版前(83.0 → 90.9 MB)持平,**≤100 MB 的验收线仍然守住**。

**这次踩到的两个坑,都值得记:**

1. **`import "*.ttf"` 掉了 = 中文整片消失,而且不报错。**
   `default-font-family: "MCWP Sans"` 只是「请求」,字体真正编进 exe 靠的是 `panel.slint` 顶部的 `import "../fonts/*.ttf"`:build.rs 的 `EmbedFiles` 把它变成内嵌资源,再生成初始化代码里的 `register_font_from_memory()`。重写 `panel.slint` 时漏了这两行,现象是**拉丁字母和数字正常、CJK 全部不画**(不是方框,是空白),编译期只有一条极易漏看的告警。同一时刻私有提交还从 121 MB 涨到 144 MB —— 回落系统字体后,软件渲染器会用 fontdue 把选中字面**整份**解析(见 11.3),所以「中文没了 + 内存暴涨」是同一个原因的两张脸。
   补了这条防线:Rust 侧的 `mcwp_ui::missing_chars()` 只查「字符在不在子集里」,查不出「字体压根没注册」,以后改 `panel.slint` 的字体相关行要附带跑一次截图回归。

2. **`Window::window_handle()` 在 `show()` 之后立刻调拿不到 HWND。**
   winit 后端的窗口是**事件循环第一次迭代**才创建的,`show()` 只是把「要显示」排进队列。所以 DWM 圆角和无边框拖动一起静默失效(只留一条 WARN)。做法:在 UI 线程的事件循环里用 `slint::Timer::single_shot` 退避重试取句柄,拿到后缓存起来给拖动逻辑复用。

另外两条设计约束:

- **窗口圆角只能用 DWM 的(约 8px)。** 软件渲染器走 softbuffer(32bpp DIB + BitBlt),窗口没有逐像素 alpha,自己画的圆角只能画在窗口**内部** —— 画得比 DWM 的大,窗口里就会露出一小块背景色拼成的「墙角」。所以面板每一层都对齐 8px,不再追求「28px 窗口圆角」。
- **玻璃极性固定为深色,且环境底的亮度是归一化过的。** 只压不抬的话,深色壁纸(如「雨夜城市」底色 `#0B1020`)会得到一块纯黑面板 —— 玻璃背后没东西可「透」,叠上去就是一片死黑。现在底色 / 亮部 / 暗角各自落到设计亮度档位(0.15 / 0.28 / 0.06),面板的气色跟着壁纸**色相**变,但不跟着壁纸一起沉下去。

**桌面入口(同日):** 图标由 `tools/make-icon.py` 用 Pillow 画(4 倍超采样后 LANCZOS 缩到 16/24/32/48/64/128/256 七档),配色沿用面板的环境底色系,产物两份:`assets/mcwp-icon.ico` 给桌面快捷方式、`assets/mcwp-icon-256.png` 由 `panel.slint` 的 `icon:` 内嵌当窗口图标(任务栏 / Alt-Tab 生效)。`tools/install-shortcut.ps1` 在桌面放一个「MC 壁纸」快捷方式,目标是 `target\release\mcwp-wallpaper.exe --panel`(cargo 产物路径重建后不变,快捷方式不用更新)。exe 文件自身的图标资源需要 `rc.exe` 写资源,本轮没做,列在待办里。

顺带补了**单实例守卫**:桌面快捷方式很容易被连点两下,第二个进程再挂一次壁纸宿主会去抢同一个 WorkerW 把桌面搞花。现在用命名互斥体拦下来,第二个进程只把已运行实例的控制面板叫到前台(`FindWindowW` + `SetForegroundWindow`,跨进程,不需要 IPC)然后退出;`--dump` / `--window` 这类排查参数不挂桌面,不受限制。

### 11.5 面板拖动「不灵敏」的根因与修法(2026-10-14 同日)

现象:拖面板标题栏,窗口跟手一段就**停在原地不再动**(顺原路拖回去还会「跳」一下)。

**根因是 Slint 的 `TouchArea.pressed` 语义,不是窗口句柄、也不是渲染慢。** 原来的标题栏拖动区写的是
`pointer-event(e) => { root.drag-state(drag.pressed); }` —— 而 `pressed` 只在指针**位于这个 TouchArea 的几何范围里**才为真。指针一旦离开标题栏那条 30px 窄带(`i-slint-core` 的 `send_exit_events` 按几何包含关系判 `contains`,**不看鼠标抓取**),TouchArea 立刻把 `pressed` 置 false 并补发一个 `PointerEventKind.Cancel`,同时连内部的 `grabbed` 也清掉 —— 之后**移动、抬起都不再送给它**。Rust 侧收到 false 就把 `WindowDrag` 丢了,拖动到此为止;若指针又回到标题栏,`pressed` 转真,`WindowDrag::begin` 重新记起点,于是「跳一下」而且丢掉中间那段累计位移。
带时间戳的实测(合成鼠标慢速拖 40 步 × 6px / 20ms):窗口位移与光标位移**在事件流动期间是 1:1 的**(光标 +191,+26 时窗口也正好 +191,+26),然后在拖到一半时**事件整段断掉**,窗口停在原地不动 —— 这就是手感上的「不灵敏」。

**修法:把拖动交给 Windows 自己的标题栏模态移动循环** —— `slint` 开 `unstable-winit-030` feature,在 Slint 的回调里 `window.with_winit_window(|w| w.drag_window())`,winit 内部就是 `ReleaseCapture()` + `PostMessageW(WM_NCLBUTTONDOWN, HTCAPTION)`,DefWindowProc 之后接管采样光标。跟手性最好,没有每帧 `SetWindowPos` 的开销,还自带贴边吸附。Slint 侧相应改成**只认左键 `down` / `up` 两个动作**(`drag-start` / `drag-move` / `drag-end` 三条回调),Rust 侧不再依赖「按住」状态,拿不到 winit 窗口时才退回落成手动的 `WindowDrag`(并加了「位置没变就不搬窗口」的节流)。

顺带纠正一个之前的误判:`WM_EXITSIZEMOVE` 里 winit 会补一条 `WM_LBUTTONUP`,所以拖动结束后 Slint 侧的状态是干净的,**连续拖动不会卡在「dragging」里**——这一点也实测过(见下表)。

实测(`tools/drag-probe.ps1` / `drag-probe2.ps1` / `drag-probe3.ps1`,真实 `mouse_event` 注入):

| 用例 | 期望位移 | 实际位移 |
| --- | --- | --- |
| 慢速拖 40 步 × 6px | (240, 80) | **(240, 80)** |
| 连续三次快速拖(每次 25 步 × 4px) | 每次 (100, 50) | **每次 (100, 50)** |
| 甩动 8 步 × 40px / 5ms | (320, 0) | **(320, 0)** |
| 甩到屏幕上边缘 | 不最大化 | 未最大化,位置贴到 y=0,尺寸不变 |

注意:这条路径依赖 winit 的 `drag_window()`,属于 `slint` 的 **unstable API**(`unstable-winit-030`),升级 Slint 时要复验。

### 11.6 托盘 + 面板页签(2026-10-14 同日)

**托盘**(`mcwp-platform::tray`)。关掉面板之后应用就没有任何可见入口了,托盘补的就是这个洞。

- **不引入线程,也不引入第二个消息循环。** 宿主窗口的 `pump_pending()` 用的是
  `PeekMessageW(None, 0, 0, PM_REMOVE)`,取的是**整条线程**的消息队列;托盘窗口只要跟宿主
  建在同一个线程上,它的回调就会被那个循环顺带派发。主循环的节奏一行没改(仍 59 fps)。
- **图标是 `.ico` 里的一条 PNG 码流,不做解码。** `tools/make-icon.py` 出的 `.ico` 每条都是
  PNG 压缩的 32bpp;`load_icon()` 只解析 6 字节文件头 + 16 字节目录项,取出 32×32 那条,
  直接交给 `CreateIconFromResourceEx`(Vista 起支持 PNG 图标)。不用 `ExtractIconW`
  (它按序号取第一张,等于白丢码流),也没为托盘拖进 `image` / `png` 之类的依赖。
- **菜单用 `TPM_RETURNCMD`,不走 `WM_COMMAND` 路由**:返回值本身就是命令 id。弹菜单前后按
  微软文档的固定套路来(`SetForegroundWindow` → `TrackPopupMenu` → 补一条 `WM_NULL`),
  否则菜单点到外面不会自动关。
- **动作只入队,落地在主循环**(`TrayAction`,与面板的 `UiEvent` 同一套路):
  `OpenPanel` / `NextPreset` / `TogglePause` / `ToggleAutostart` / `Quit`。「换一个预设」走的是
  和面板同一条落地路径,并回填面板(`PanelHandle::refresh`)。
- **开机自启**(`mcwp-platform::autostart`)写在 `HKCU\...\CurrentVersion\Run` 的 `MCWallpaper`
  一条字符串值:不需要提权,关掉就是删掉自己那一条,用户在系统的启动项管理里也看得到。
- **暂停**:动画时钟改成按帧累加(`clock += frame_start - last_tick`),而不是取墙钟 ——
  否则暂停十分钟再继续,画面会直接跳十分钟。

实测(托盘菜单逐项点过,逐项对过日志回显 + 截图):

| 菜单项 | 结果 |
| --- | --- |
| 换一个预设 | 日志 `切换到预设:minimal_paper`;面板同步选中「极简纸感」,参数名 / 参数值 / 摘要 / 指纹全部回填 |
| 暂停渲染 | 日志 `暂停渲染`;60 s 统计窗口里的渲染帧数从 ~59 fps 掉到 21 fps(中间那 36 s 一帧没画) |
| 开机自启 | 打勾后 `HKCU\...\Run` 出现 `"G:\MC壁纸\app\target\release\mcwp-wallpaper.exe"`,再点一次清空 |
| 打开控制面板 | 不带 `--panel` 启动时也能开出来,`FindWindowW` 按标题能找到窗口 |
| 退出 | 进程退出;托盘图标消失(溢出区截图前后对比,`NIM_DELETE` 生效) |

已知:Windows 对新出现的托盘图标一律先收进「隐藏的图标」溢出区,要用户拖出来一次才常驻 ——
这是系统行为,不是本程序的缺陷。想强制常驻得改 `HKCU\Control Panel\NotifyIconSettings` 下的
`IsPromoted`,那是动用户的系统设置,本轮没做。

**面板页签**(`ui/panel.slint`):`壁纸 / 库 / 设置`,iOS 分段控件(胶囊凹槽 + 会平移的染色玻璃滑片)。
**这一版页签已在 11.9 被生图界面取代** —— 下面记的是当时的形态和它踩到的坑。
`page` 是纯界面状态(`in-out property <int> page`),不进 Rust。库 / 设置两页**故意只做占位**
(一条标题 + 一行「待接入」),先把信息架构定下来,下一轮再填真内容。

- **踩到的坑:Slint 的 `visible: false` 不省布局。** 编译器把 `visible` 降级成一个 `Clip` 包裹元素
  (`i-slint-compiler/passes/visible.rs`),元素照样参与布局 —— 第一版用 `visible: root.page == 0`
  切页,结果当前页被挤到窗口底部、上面留一大块空白。切页必须写成
  `if root.page == 0 : Rectangle { ... }`,为假时元素**根本不构造**。
- 面板按 940×648 设计,三段页签每段约 300px。
- 回归工具:`tools/panel-probe.ps1 -Actions 'click:470,78','shot:x.png'`,先把面板临时提到最前
  再点击 / 截图(单纯 `SetCursorPos` + `mouse_event` 会点到压在面板上面的窗口上,页面状态就会
  「莫名其妙」没变)。

### 11.7 「构建怎么这么大?」:10.4 GB 的来历与一次特性裁剪(2026-10-14 同日)

起因:第一次推仓库时 `.gitignore` 排掉 `/app/target/`,顺带看到本机这个目录有 **10.4 GB**。
数字本身没错,但它**不是成品**,而是 cargo 的编译中间产物 —— 删掉随时能重建(本机约 80 秒)。

**实测拆解**(`target/` = 10,428 MB / 15,614 文件):

| 目录 | 体积 | 文件数 | 说明 |
| --- | --- | --- | --- |
| `target/debug` | 6,719 MB | 9,439 | 含 21 个 exe;另有 882 MB `incremental/`、525 MB `build/` |
| `target/release` | 3,709 MB | 6,173 | |

按扩展名:`rlib` 5,043 MB / 1,036 个、`rmeta` 2,299 MB / 1,256 个、`pdb` 1,640 MB / 354 个、
`.o` 约 500 MB、`.exe` 合计 317 MB。单个最大的几个文件是
`debug/deps/mcwp_wallpaper.pdb` 121.7 MB、`libwgpu_core-*.rlib` 113.8 MB(4 份)、
`libnaga-*.rlib` 87 MB(2 份)、`release/deps/libwindows-*.rlib` 77.5 MB。

三条主因,按贡献排序:

1. **依赖的中间产物远大于成品**:每个 crate 都留一份 `.rlib` + `.rmeta`(+ debug 的 `.o` / `.pdb`),
   而 `rlib` 是「未做最终链接优化的对象归档」,比 strip 过的 exe 大一个量级。真正的成品
   `mcwp-wallpaper.exe` 只有十几 MB。
2. **同一 crate 存在大量 feature 哈希不同的重复副本**:`libwindows` 20 份、`libmcwp_platform` 16 份、
   `libmcwp_ui` 13 份、`libsyn` 13 份。根因是逐包构建(`-p`)/ 不同 feature 组合各留一份缓存,
   统一 `cargo build --workspace` 能收敛(本轮已全部改用 `--workspace`)。
3. **debug / release / dev-tools 三套产物并存**。其中 `target/debug/build/mcwp-ui-*/` 两个目录
   各 148 MB —— 那是 **Slint 编译器自己**的产物(`libi_slint_compiler` 57.7 MB)。

顺带纠正一个直觉:本项目**自己写的代码**只有 57 个文件 / 0.79 MB,10 GB 里没有一行是我们写的
业务代码,全是依赖树。另外 `libi_slint_compiler` 57.7 MB、`libimage` 21.7 MB、`libravif` 19.4 MB
都是**构建期**依赖(`slint-macros → i-slint-compiler → image` 这条 proc-macro 链),
只占缓存,**不进成品、不影响运行时**。

**这轮实际做的裁剪:关掉 wgpu 用不到的后端**(`app/Cargo.toml` 的 `[workspace.dependencies]`)。
依据是项目在 `crates/mcwp-render/src/lib.rs` 里把后端写死成 `wgpu::Backends::DX12`,
着色器是 WGSL;而 wgpu 默认还开着 `vulkan / gles / metal / webgpu`,其中 vulkan 会把
`ash`(Vulkan 绑定,单是 release rlib 就 68.5 MB)整条拖进依赖树,webgpu 还会给 naga
加一个用不到的 WGSL 输出后端。

```toml
wgpu = { version = "30.0.1", default-features = false, features = ["std", "dx12", "wgsl", "parking_lot"] }
```

实测(在临时目录从零构建,避免污染正式 target):

| 指标 | 裁剪前 | 裁剪后 |
| --- | --- | --- |
| 成品 `mcwp-wallpaper.exe` | 13.3 MB | **11.52 MB** |
| 从零构建后的整个 `target/` | 10,428 MB | **1,566 MB**(3,748 文件) |
| 从零构建耗时 | — | 80 秒 |
| 依赖树里的 `ash` / `glow` / `web_sys` / `wasm_bindgen` | 有 | **全部归零** |

裁剪后重新冒烟: `--attach auto --fps 60` 跑通,`backend: Dx12`、挂载成功、**58.8 fps**;
桌面拖动回归(3 个用例)、面板点击 / 截图、托盘挂载均无回归。

**结论**:10.4 GB 是正常的编译缓存量级,不是「软件很大」;产品真实体积是 **~11.5 MB 单 exe**。
注意 `app/Cargo.toml` 只改了 feature 集,**没动任何代码逻辑**。

### 11.8 圆角不生效的根因 + 滑杆「悬停即改值」(2026-10-14 同日)

**现象**:分段控件的选中滑片是一个**直角矩形的蓝块**,滑杆的旋钮是**方块**、填充条两头也是直的;
但同一块面板上,「当前壁纸」卡片和预设卡片的圆角却是好的。

**根因:软件渲染器只给实色背景画圆角。** `i-slint-core/software_renderer.rs` 的
`process_rectangle_impl` 里,渐变是**单独一条分支**:`Brush::LinearGradient` / `RadialGradient` /
`ConicGradient` 都直接 `processor.process_linear_gradient(act_rect, ..)` 把**整个矩形**刷下去
(`act_rect` 只是个矩形,没有任何 radius 参与),然后返回一个**透明**的 `Color::default()`。
函数末尾那段 `if !radius.is_zero() { process_rounded_rectangle(.. inner_color: color ..) }`
拿到的 inner_color 因此是透明的 —— 该画的圆角什么也没画。

这解释了为什么「有的圆角是好的、有的不是」:实色背景走的是下面
`process_simple_rectangle` + `process_rounded_rectangle` 那条路,圆角正常;只有描边
(`border-color`)是圆的,因为描边一直由 `process_rounded_rectangle` 画 ——
于是表现为「发丝线是圆的、填充是直角」。

**修法**:凡是要圆角的地方一律改用**实色**;渐变只留给圆角不重要的地方(窗口底色、
环境光斑 —— 前者被 DWM 裁、后者的四角本来就是透明的)。液态玻璃的厚度感改由
**发丝高光 + 半透明层**表达。改动点:`SegTabs` 的凹槽与滑片、`GlassSlider` 的凹槽 /
填充 / 旋钮;旋钮里那层「上半部白色弧」镜面被删掉(它在白色旋钮上本来就是白压白看不出来,
又因为是渐变只会画出一个直角浅色块)。文件头的能力边界注释也一并更正。

**顺带抓到的一个真 bug**:滑杆的 `pointer-event` 原本是
`if (e.kind == down || e.kind == move)`。Slint 的 `move` **悬停也会派发**,所以鼠标只是
**从滑杆上划过**(不按键)就会改值 —— 面板上五个滑杆会被一次挥动全部带动。
修法:`down` 保持无条件(它本身就是按下),`move` 加上 `touch.pressed` 这道闸。
实测:悬停横扫「雨量」滑杆,五个值纹丝不动(65/35/25/57/45 → 不变);
按住拖动仍然正常(能从 65% 拖到 100%)。

### 11.9 面板改成生图界面 + 壁纸库改成「从壁纸侧自动获取」(2026-10-15)

**信息架构换掉了。** 面板从「三段页签(壁纸 / 库 / 设置)」改成生图界面:左栏 244px 是历史对话
(顶部「+ 新建对话」,下面是会话列表,底部三个入口),右栏是会话(标题栏 / 消息流 / 输入框)。
参数、库、设置三页的内容没丢,只是从顶部页签挪到左栏底部;`view` 仍是纯界面状态,不进 Rust。

**壁纸库不再写死在面板里,改成从壁纸侧自动获取。** 面板不碰文件系统:`mcwp-wallpaper` 侧扫
`%APPDATA%\MC壁纸\library\*.json`,把每张壁纸的标题 / 关键词 / 指纹 / 主色拼成 `LibraryItem`
整块灌进面板。扫的时机有三个:打开面板、存新壁纸、面板切到库页(回调 `refresh-library`)——
所以手工往库目录里拷 / 删文件也能跟上。库里点一张就是换 spec(`UiEvent::OpenWallpaper`),
和托盘切预设走同一条落地路径。

顺带统一了「一张壁纸的身份」:`library_id()` 把 spec 归一化(source 钉成 snapshot)后取指纹。
存进库时的文件名、库里显示的那串字符、参数页右上角的「指纹」,现在念的是同一个值;坏 JSON
只记一条日志跳过 —— 库目录是用户可写的地方,不能因为一个手工改坏的文件让整块面板打不开。

**字体策略改了(重要)。** 面板上出现了输入框,用户敲什么字都得画得出来,所以:

| 字面 | 覆盖 | 体积 | 用在哪 |
| --- | --- | --- | --- |
| `panel-cjk-regular.ttf` | **GB2312 一级汉字全表 + 面板文案**(3865 字形) | 1088 KB | 一切动态文案:消息、会话名、输入框、壁纸名、状态行 |
| `panel-cjk-bold.ttf` | 只有面板自己的静态文案(759 字形) | 177 KB | 标题 / 标签 / 主按钮 |

**动态文案一律走 regular** 是硬约定:bold 表里没有用户输入的字,`font-weight: 600` 一旦落到
动态文案上就是静默缺字。子集化脚本相应拆成两套字表(`tools/subset-panel-font.py` 的
`charset()` / `static_charset()`),Rust 侧 `missing_chars()` 仍按 regular 的字表查缺字、进日志。

**内存代价**(本机,专用工作集口径,口径说明见 11.3):

| 状态 | 专用工作集 | 总工作集 | 私有提交 |
| --- | --- | --- | --- |
| 无面板(基线) | 84.3 MB | 117.9 MB | 113.2 MB |
| 面板打开(生图界面) | **115.8 MB** | 155.0 MB | 145.4 MB |

对比 11.4 的 92.2 MB,面板净增从约 8 MB 涨到约 31 MB —— 其中约 17 MB 是 regular 那个全字集字面
(fontdue 会把选中的字面**整份**解析进内存,和用到多少字无关;bold 收窄到静态文案就是为了不背
第二个整表)。**常驻(未开面板)仍然达标 ≤100 MB**;「面板打开」这一栏从 90.9 变成 115.8 是生图
界面的必然代价,要压回去只有砍汉字表(常用 1500 字约省 10 MB)—— 见 12.2 待定项 8。

**Slint 布局的第二个坑:`alignment` 只管主轴。**

- `HorizontalLayout` 里写 `alignment: center` 会把**整条内容挤到中间**,横向 stretch 同时失效
  (输入框会塌成文字那么宽并居中)。
- 反过来,HBox 里**定宽高**的元素(胶囊按钮、圆点、色卡)没有「竖直居中」可言,会被摆在行的
  **顶边**;要居中就得套一层 `VerticalLayout { alignment: center; }`(VBox 的主轴才是竖直的)。

现象很典型:「发送」胶囊顶着输入框上沿、右下角戳出胶囊边界;左栏导航的小圆点比文字高 13px。
四处(发送胶囊 / 导航圆点 / 预设卡圆点 / 库页色卡)都已改成套 VBox,规则写进了 `panel.slint`
文件头的踩坑清单。

**这一节写下时还没做的**:AI 那一环。那会儿发消息只在内存里记一条用户消息 + 一条占位回复
(会话落盘见 11.12,模型接入见 11.13)。当初设想的那条管线「文本 → `WallpaperSpec` → 应用」
后来就是照这个走的,面板侧一行都没动 —— 和预期一致。

**回归方式与过程产物**:面板回归一律走「按标题找窗口 → 提到前台 → 按窗口内逻辑坐标点击 / 输入
→ 截图」,本轮三个视图(会话 / 参数 / 库)加「发一条消息」各截了一张。注意:**新起一个进程后的
第一下点击会被焦点激活吃掉**,要在同一个进程里连着点才可靠 —— 否则很容易误判成「那一行点不
动」。截图、日志、一次性探针脚本一律落在仓库外,仓库里只留 `tools/` 下可重跑的脚本;`.gitignore`
补上 `/.shots/` 与 `__pycache__/`,M0 / M1 阶段那批过程产物(`app/shots/`、`.fontcache/`)已经
清出工作区。

### 11.10 面板补上顶部安全区与窗口键(2026-10-15)

**先还一笔债:无边框窗口没有标题栏。** 之前的"标题栏"只是压在玻璃里的一行 30px 内容(左程序名 +
右一颗关闭圆钮),既不成"安全区"也不像系统窗口。现在窗口顶部单独留一条 36px 满宽的**安全区**:
底色 `glass-tint.darker(0.62)` 的实色(比下面那层玻璃暗一档,换壁纸跟着变色),下沿压一条发丝线
分界;右端三颗 46px 宽、满高的窗口键 = 最小化 / 放大·还原 / 关闭,悬停提亮、关闭键悬停变红
`#C42B1C`,图形**全部自己画**(内嵌子集只收面板文案用得上的字形,"最小化""还原"这类符号有没有
全看运气)。整条安全区就是拖动区,双击 = 放大 / 还原(Windows 的老规矩)。玻璃内容层因此让出
`padding-top: 54px`(= 36 + 18)。

**放大不能用 `SW_MAXIMIZE`。** 窗口是 `no-frame`、没有 `WS_THICKFRAME`,系统算"最大化尺寸"的那套
公式(工作区 + 边框)会退化成**整块显示器 —— 放大会连任务栏一起盖住**。所以 `WindowZoom` 自己去量
`MonitorFromWindow(MONITOR_DEFAULTTONEAREST)` 的 `rcWork` 再 `SetWindowPos` 摆过去,顺手把放大前
的矩形记下来当还原点(还原时**不能**带 `SWP_NOSIZE`,宽高要一起写回)。实测:1024×672 @ (114,114)
的窗口点一下放大 → 2560×1528 @ (0,0),正好是任务栏之上那块工作区;再点一下原样摆回。最小化就是
`ShowWindow(SW_MINIMIZE)`(面板窗口本来就有任务栏按钮,能恢复);关闭仍旧走 `close-requested`
(退出面板事件循环即释放)。三颗键都是"点了直接调 Win32",不绕事件循环,面板本身仍然不存业务状态
(`zoom` 那个 `RefCell` 存的是窗口矩形,不是数据)。落点:
`mcwp-platform/src/glass_window.rs`(`minimize` / `WindowZoom`)、`mcwp-ui/src/lib.rs`
(`panel_hwnd` 抽出来给拖动和窗口键共用)、`panel.slint`(`CaptionButton`)。

**第三个布局坑:Window 上写 `width` / `height` 会把根元素钉死。** 这在 Slint 里是**固定约束**
(min = max)。窗口被系统拉大(放大)之后根元素还是 1024×672,内容缩在左上角、右边一大片空玻璃 ——
而 `Window` 的 `background` 照样铺满整窗,所以第一眼不像"没重排",只像"右边多了块底色"。改成
`preferred-width` / `preferred-height` 才是"首选尺寸":初始窗口仍是 1024×672,但窗口拉大时根元素
跟着长。**顺带**:`Window` 的孩子不带 `x` / `y` 会被**居中**摆,不是左上角 —— 铺满整窗的底色看不
出来,一条 36px 的标题栏会直接跑到窗口正中间,贴边的元素一律显式写 `x: 0px; y: 0px;`。

**放大状态下不拖。** Windows 上拖最大化窗口的标题栏 = 还原 + 继续拖,这套我们没做,干脆当成没接住
(否则能把一块铺满屏幕的窗口拖出工作区);双击仍然可以还原。

**回归方式:合成鼠标消息。** 面板回归还是"按标题找窗口 → 按窗口内逻辑坐标点 → 截图",但这轮的
`mouse_event` 点击**打不中**:当时的前台窗口是桌面(`Program Manager`),`SetForegroundWindow` 被前台
锁挡下,**不是前台的窗口收不到合成输入**,现象是"点了跟没点一样",很容易误判成命中测试坏了。换成
`SendMessage(hwnd, WM_LBUTTONDOWN/UP, ..., MAKELPARAM(客户区坐标))` 就都正常了 —— 它绕开前台 /
焦点规则直接进窗口消息队列。两个附带的注意点:客户区坐标要按本机 scale = 1.5 换算;**每次点击前重新
取一次窗口矩形**(放大之后"右上角那颗键"的逻辑坐标已经不是 955 了)。拖动仍旧只能人工验:面板拖动
首选的是 winit 的系统模态移动循环,合成的鼠标消息进不去那个循环。

### 11.11 会话管理:左栏右键菜单(2026-10-15)

**四个动作 + 一份自绘菜单。** 左栏的历史对话行现在支持右键菜单:**重命名 / 置顶 / 标记为未读 / 删除**。
前三个是"行上的状态",第四个是"行的生死",所以列表项(面板侧的 `ConversationItem`)多了 `pinned` /
`unread` 两个字段,行尾让出 34px 画状态标:置顶是两根实色小矩形拼的图钉,未读是一个染色圆点。菜单本身
是**自绘浮层**,不是系统菜单 —— 无边框窗口 + 软件渲染器下弹 Win32 原生菜单要另开线程跑消息循环,而 Slint
侧画一块 176 × 143 的圆角板子只要几十行。代价是尺寸得写两份(面板的 `menu-w` / `menu-h` 与 slint 组件
里的字面量),因为浮层要 clamp 在窗口内就得先知道自己多大。菜单里**不放图标**:内嵌子集只收面板静态
文案,"重命名""置顶"这类符号有没有全看运气(见 11.3)。

**行内注入 `absolute-position` 再发给面板。** `ConversationRow` 是个可复用的行组件,它不知道自己在列表
里的位置,而菜单要贴着鼠标弹。做法是行组件把 `PointerEvent` 的坐标加上自己的 `absolute-position` 得到
**窗口坐标**再回调出去(`menu-requested(x, y)`),面板只负责 clamp(四周留 8px)和显示。右键在 Slint 里
**没有 `clicked` 可用**,必须走 `pointer-event`,判 `e.button == PointerEventButton.right && e.kind ==
PointerEventKind.down`(左键才是 `clicked`)。

**会话的身份从下标改成 `id`。** 之前 `Sessions::active` 存的是下标,一置顶(排序)/ 一删除下标全乱,
"当前会话"会指到别的行上。现在 `Session` 带自增 `id`,`active` 存 id,`active_index()` 现算;对外回调仍
用下标(面板只有下标这一个概念),换算只发生在 `mcwp-wallpaper` 侧。删除的落点规则:**删完空了就补一个
新的空会话**(面板永远至少有 1 行);**删的是当前会话就落到 `index.min(len-1)`**(顶上来的那条),别的
行不动。置顶用 `sort_by_key(|s| !s.pinned)` —— **标准库是稳定排序**,同档位内保持原顺序,连着置顶不会把
先置顶的那条挤到后面。改名先 `trim`:空名字当没改、同名不做任何事。

**面板侧踩的坑:行元素会被 Slint 复用。** 改名输入框的草稿(`draft`)一开始只在 `init` 里从标题灌一次,
于是"置顶重排 / 删掉中间一条"之后,被复用的元素还留着上一次(甚至别的会话)的名字,回车就会把别人的名字
盖过来。修法是盯着 `renaming` 变真时重灌草稿:
`changed renaming => { if (root.renaming) { root.draft = root.heading; } }`。**注意不能在这个 `changed`
里碰 `rename-input`** —— 那个 id 在 `if` 条件块内,块外引用直接 `Cannot access id 'rename-input'`;让输入
框 `text <=> root.draft`,全选和聚焦交给 `init` 就够了。另外输入框必须**声明在行的命中区(`TouchArea`)
之后**(后声明的画在上面、先拿事件),否则刚点开就被行自己的点击抢走并顺手取消掉。

**菜单的三处小坑**:① `Esc` 取消要走 `key-pressed` 判 `e.text == "\u{1b}"`,Slint 里写 `"escape"` 是不
认的;② 浮层里的矩形 `x:` **不能写裸属性名**(会解析成它自己的属性 → 无限递归),要么带前缀要么给常量;
③ 颜色没有 `lighter()`,提亮浅一档是 `brighter(k)`。

**回归方式:合成输入这轮基本不可用。** 合成的 `mouse_event` 点击仍被前台锁挡下(见 11.10),得用
`SendMessage`;合成按键则会被本机中文输入法吞掉字母(候选条会冒出一串 "zzz"),测改名要先 `Ctrl+Space`
切英文,或者干脆只看日志(`RUST_LOG=info,mcwp_wallpaper=debug` 能看到面板发回来的每个事件)。另外那段
"窗口坐标 → 逻辑坐标"的换算系数别再硬编码 1.5 —— 本机 DPI 会漂,改成 `窗口宽 / 1024` 现算。

落点:`mcwp-wallpaper/src/main.rs`(`Session.id` / `pinned` / `unread` + `rename` / `remove` /
`toggle_pin` / `mark_unread`)、`mcwp-ui/src/lib.rs`(四个 `UiEvent` + 转发)、`panel.slint`
(`ConversationMenu` / `MenuRow` / 行尾状态标 / 改名输入框)。

### 11.12 会话落盘(2026-10-15)

**存哪儿 / 存什么。** 会话落到 `%APPDATA%\MC壁纸\sessions.json` —— 和壁纸库同一个目录(方案第五节
早就定了这条)。一个文件装整份:格式版本号、`active`(上次停在哪一条,存的是 id),以及按显示顺序
排好的会话数组;每个会话带 id / 标题 / 置顶 / 未读 / 消息,一条消息是
`{"role": "user" | "assistant", "text": …}`。

**为什么整份一个文件,而不是"一个会话一个文件"。** 列表顺序(置顶组在前)和"停在哪儿"都是这份数据
的属性,拆成多文件就得再引一份清单,两份对不上时最难查;壁纸库那样"一个指纹一个文件"是因为它天生
按内容去重,会话没这个需求。会话是 KB 级文本,整份重写一次也就几毫秒。真长到上千条历史再换
SQLite —— 和壁纸库同一个迁移点(决策 12)。

**写盘:临时文件 + 改名,每帧至多一次。** 直接往 `sessions.json` 上盖,写到一半掉电就只剩半个
JSON,所以先写 `sessions.json.tmp` 再 `rename`(Windows 上 `std::fs::rename` 会覆盖已存在的目标)。
落盘时机不塞进每个动作里,而是改动打个 `dirty` 标记、主循环每帧收一次:一帧里可能连着好几笔改动
(发消息 + 切会话),这样只落最后一次,也不会有哪个动作忘了落。**失败不重试** —— 磁盘满 / 目录只读
这类错每帧重试只会把日志刷满,而改动会在下一次用户操作时整体再落一遍。

**读盘:坏文件只当"这一份读不懂",不当致命错误。** 没文件(第一次跑)= 一份空会话,不报警;
解析失败 = 挪成 `sessions.json.bad` 备份掉、再开一份空的,日志留一笔。**单条消息的 `role` 故意存
字符串而不是枚举**:以后加 `system` 这类新角色时,老版本读到不认识的词不该把整份历史搬进 `.bad`,
认不出的一律当"对方说的"。另外读回来会做两件清理:`title` 全空的补成"新的对话";`id` **一律重新
发号** —— 盘上的 id 只用来找"上次停在哪一条",找完就没用了(手工改过的文件里 id 可能重复、可能
是 0,而内部认人全靠它)。`active` 指不到人时退回第一条。

**验证**(本机,`RUST_LOG=info`):点两次「+ 新建对话」→ 文件立刻出现三个会话、`active` 跟着走;
右键置顶第 1 条、标未读第 2 条 → 文件里 `pinned` / `unread` 同步;杀进程重启 → 面板原样回来
(图钉、未读点、选中的那一条都对得上);把文件写成半截 JSON → `sessions.json.bad` 出现、本次开一份
空的;手写"id 重复 + 空标题 + `active: 999` + `role: "system"`"的文件 → 读回三条、active 退回第一
条,再点一下新建落盘,id 已经重排成 1/2/3/4、空标题补成"新的对话"、认不出的角色当回复;
`"sessions": []` 配 `schema: 9` → 一条"新版本写的"警告 + 一份空会话。**注意本机 `RUST_LOG` 是
`warn`**:info 级的"读回 N 个会话"看不见,验证时得临时把 `RUST_LOG` 设成
`info,mcwp_wallpaper=debug`。

落点:新文件 `mcwp-wallpaper/src/sessions.rs`(会话数据 + 落盘,整体从 `main.rs` 搬出来)、
`main.rs`(`mod sessions`、`Sessions::load()`、每帧与退出前各一次 `flush()`)。

### 11.13 接上模型:一次调用 + 严格 JSON + 本地降级(2026-10-15)

**这一环到底在干什么。** 用户一句话 → 模型返回 `{reply, mode, image_prompt, spec}` → 本地校验 →
换壁纸。**不做"多智能体"**:方案 3.1 已经定了主力是"模型写规格、本地渲染",参数空间被 4 个预设锁死,
再套一层"提示词智能体"只会把成本、延迟、失败点全都翻倍。"先设计提示词、再喂给图像模型"那套是 3.2 的
B 档(文生图)才需要的,而且也得等这一档跑通、发现效果不够之后再上。

**一次调用怎么保证拿到能用的 JSON。** ①system 提示词里塞 `mcwp_spec::presets::catalog()`(预设目录 +
每个参数的范围),把"能填什么"讲死;②明说"只输出一个 JSON 对象,不要解释、不要代码块";③本地提取时先拆
围栏、再取第一个 `{` 到最后一个 `}`,模型开头那句"好的,这是你要的规格:"顺手就被剥掉;④
`WallpaperSpec::parse` + `normalize()` 兜底:越界值夹紧、未知预设拉回默认、非法色值走预设调色板 ——
3.6 那句"模型怎么胡说都不会渲染崩"在这里落地;⑤解析失败就把错误原样丢回去让它重写一遍(比本地"猜着修
JSON"靠谱);⑥两次都不行 → 本地降级:关键词挑预设 + 情绪词调参数(3.4 的 L1),回复里说清楚"模型没接上"。
**`draft()` 永不返回错误**:用户敲了字,桌面必须有反应,不能弹错误框。

**T2 / T3 的区分交给模型自己填。** 同一个 JSON 里多一个 `mode`:`tweak` 只改参数、**不入壁纸库**;
`create` 才是新壁纸 + 入库。少了这个字段,聊两句库里就一堆垃圾(3.5 那条"不是聊一句生成一次"的要求)。

**绝不同步等。** 模型是秒级往返,主循环是 60 fps:发请求丢后台线程,结果从 `ai_rx` 回到主循环落地
(回复进会话、spec 换上去、该入库的入库)。等待时面板显示"正在生成壁纸…";这期间用户切走了会话,回复回来
会**挂个未读点**;把会话删了,那条结果直接丢掉 —— 不然"删了还生效"很怪。超时 45 s(3.4 里那个 3 s 是给
T1 环境联动用的;T3 是用户主动等结果,3 s 太紧)。

**没配模型也得能用。** `ai.json` 不存在时 `Config::load()` 给的是"去哪儿配 + 免费的有哪几家"的人话,
面板把这句话写进会话 —— 而不是弹错误框,也不是发完消息毫无反应。

**配置与试服务商。** 优先级:环境变量(`MCWP_AI_KEY` / `MCWP_AI_BASE_URL` / `MCWP_AI_MODEL` /
`MCWP_AI_THINKING`,给"临时试一家"和自检用) > `%APPDATA%\MC壁纸\ai.json`(日常用,key 不进仓库) >
内置默认(**智谱 GLM-4-Flash**)。全是 OpenAI 兼容的 `/chat/completions`,换服务商只改一行。实测本机
直连可用:智谱 GLM-4-Flash(**免费**,内置默认)、硅基流动(注册送额度)、OpenRouter / Groq(免费档,要能
连外网)、DeepSeek(按量计费);Gemini 的免费档直连不通,得挂代理。

**选型落地:先智谱 GLM-4-Flash(2026-10-15)。** 12.2 待定项 1 到此有了临时答案 —— 免费、国内直连不用
代理、接口就是 OpenAI 那套,先拿它把 T2/T3 跑顺,效果不够再谈付费档。两个具体的坑记在这儿:①模型名
写全 `glm-4-flash-250414`(智谱的定价表、并发表都按这个版本号列,`glm-4-flash` 是别名);②智谱**还有
一个也免费的 `glm-4.7-flash`**,更新更强,但 4.7 系列**默认开深度思考**(官方原话:"GLM-4.7 系列默认
开启 Thinking"),一句"换张壁纸"也要先想十几秒。所以客户端多了一个**可选**的 `thinking` 字段 —— 只在
`ai.json` 里显式写了才序列化进请求体,不写就完全不出现在 body 里;理由和前面不传 `response_format`
一样:别家不认这个字段,传了可能直接 400。至于 4 代的 `glm-4-flash`,它不在支持 thinking 的名单里,
不配这个字段就是最快的那档。

**回归怎么跑(不花钱、不用 key)。** 新增 `tools/fake-ai-server.py` —— 一个假的 OpenAI 兼容服务,专给
这条链路做离线自检,还能演坏:`--mode broken` 先回半截 JSON(验"带错误重试一次",服务端日志里能看到两次
请求)、`--mode bad` 回越界的 spec(验夹紧)、`--mode html` 回一坨 HTML(验报错与降级)、`--mode slow`
慢 3 秒(验等待态)。宿主这侧加了两个入口:`--ai-selftest "…"`(不开窗口,直接打印回复 / 模式 / 指纹 /
完整 spec)和 `--panel --ai-ask "…"`(开面板并替用户把这句话发出去)。后一个是**唯一能整条链路自检的
办法** —— 合成的键盘输入会被本机中文输入法吃掉,打字那条路验不了。

实测(假模型 + 真配置文件两条都跑过):正常一轮 → 回复进会话、spec 换上去、状态行显示"已换壁纸 ·「…」"、
面板玻璃色随新调色板变;`broken` → 两次调用后成功;`bad`(预设名乱写 + 参数 4.2 + 色值 `#GGGGGG`)→
预设拉回 `rainy_window_city`、参数夹到范围内、色值回落到预设调色板;`html` → 降级回复 + 内置预设、
`calls=1`;`mode=create` → 壁纸库多一条(实测 `library\edca2eaf….json`)、`mode=tweak` → 不入库;
没配 key → 一句人话提示。

**顺带修掉的坑**:降级关键词表里原来写了单字"纸" —— 本产品里"壁纸"出现率最高,一个"纸"会把所有请求都
判成极简纸感(假模型自检第一次跑就踩到),Rust 与假模型两边都改成"纸感 / 纸张"。

**真 key 那一轮(2026-10-15 晚):一句都跑不通,根因是"数组写成了字符串"。** 配上真 key 之后第一句
话就降级了。新加的 debug 级"模型原文"日志把真相摆出来了:glm-4-flash 给的整份 spec **只有一处**
不对 —— `"keywords": "雨夜城市"`,契约要的是数组,`from_value` 直接报 `invalid type: string,
expected a sequence`。更要命的是**重试没用**:把错误原样丢回去让它重写,它照抄原来那份(实测两次
一字不差),白等 7 秒还照样降级 —— 也就是说上一个 commit 里"读不懂就让它重写一次"这条,对**形状**
类错误是纯浪费。于是加了 `repair_shape()`:解析前先按"已经踩过"的几种走样就地修一遍(单元素数组写成
裸字符串、单个对象写成裸对象、数字与布尔写成字符串、`scene.params` 的值写成字符串),修完再解析,
并把修了哪几处记进 `info` 日志(3.4 那条"AI 的一切行为都要可见")。同时提示词里写明"凡是「一串
东西」的字段都得写成数组"——**那才是根因**;`repair_shape()` 留着当保险,不再指望它是主路径。

实测:改完连跑三条提示词(`你好?` / `我要赛博朋克的城市夜景` / `把壁纸调冷一点、安静些`)全是
**一次调用、不降级**,6.4~7.8 s(此前是 2 次调用 + 13.8 s + 降级);`mode` 该 create 的 create、
该 tweak 的 tweak,库里因此没有多出垃圾条目。面板里用真 key 走的那一轮(`--panel --ai-ask`)也通了:
回复进气泡、状态行显示换了哪张、玻璃色跟着新调色板变。

一个单测逮到的细节:`repair_shape` 把字符串数字转回来时,`seed` 是 `u32` —— 塞 `20261014.0` 进去
serde 会报 `expected u32`,修形状反而修出个新错。所以整数一律落成整数(`number_value()`)。

落点:`app/crates/mcwp-ai/`(新 crate:配置 + 客户端 + 提示词 + 解析 + 降级;HTTP 用 `ureq` +
native-tls,**不引 reqwest** —— 那会把 tokio 拖进依赖树)、`mcwp-wallpaper/src/main.rs`(后台线程 +
落地用的 `ai_rx` + 两个自检入口)、`tools/fake-ai-server.py`。

### 11.14 模型配置搬进面板设置页 + 保存即生效(2026-10-15)

**这一页为什么非做不可。** 11.13 接上模型之后,"配一次"的动作还是"自己摸到 `%APPDATA%` 手写一份
JSON" —— 开发时自己写没问题,给别人用就是劝退。设置页于是从占位文案换成真表单:接口地址 / 模型名 /
API Key / 「深度思考」三档 + 保存,一屏之内说完"怎么让生图能用"。

**保存之后不用重启程序,这条是硬要求。** 面板是核心进程内的一个窗口(见 11.6),配置落盘之后就地
`Client::new` 换掉主循环里那个 `Option<Client>`,下一句话就走新配置 —— "配完还得重启"是这类设置页最容易
挨骂的地方。写盘失败则**保留旧客户端**:配置没写成,已经有的能力不该跟着一起消失(状态行照实报错)。
另外三种收尾各有各的话,因为用户看到的"没反应"其实是三件事:落盘成功但没填 key → "已保存 · 还没填
API Key"(**不算错误**,先存地址回头补 key 是正常用法);环境变量在生效 → "已写入 ai.json · 但环境变量
在生效,实际用的是它们";真失败 → "保存失败:<原因>"。

**设置页的状态故意不进 `PanelState`。** `refresh()` 会在换壁纸、切会话、改参数时随时整块回填面板,而
设置页那几个输入框里可能就是用户**敲到一半**的 key —— 塞进 `PanelState` 等于每次别处的动静都可能把
正在敲的字冲掉。所以它单独走 `PanelHandle::refresh_ai()`,只在「面板刚打开」和「保存成功」两个时刻灌
一次(`AiConfigState` 的注释里写了理由)。这个是"整块回填"这套投影式 UI 的固有陷阱,和 11.9 里
"切视图必须用 `if`"是同一类问题。

**`Stored` 从私有 `ConfigFile` 提成公开类型。** 面板要回填输入框时多半**还没配 key**,而
`Config::load()` 那种情形直接报错(它是"能不能用",不是"盘上写着什么"),回填不了。于是把落盘的字段
单独定义成 `Stored`,读写共用一份定义免得两边漂移;`Config::stored()` 给回填用(空字段补内置默认,
**故意不合并环境变量** —— 界面显示的是"这份文件的内容",改了才写得回去),环境变量盖没盖住由
`Config::env_override()` 单独告诉界面,页面上就此多一行提醒。落盘沿用会话那套"临时文件 + 改名" +
带缩进输出(见 11.12):这份文件里存着 key,写坏最难查,而用户自己打开看 / 手改也要好看。

**「深度思考」是三档而不是一个开关。** `None`(**字段根本不落、请求体里也不带**)和 `Some(false)`
(发 `disabled`)是两个不同的请求体:不认 `thinking` 的服务商只能走前者,而智谱 4.7 系列想显式关掉它。
一个布尔开关表达不了这三件事,所以界面上是一排小胶囊(`不发` / `开启` / `关闭`),面板传下标、
Rust 侧 `ThinkingChoice` 认不出的按「不发」兜底。

**两个踩在渲染器上的坑(都是静默的)。** ①API Key 这个框**不能用** `input-type: password`:Slint 的打码
字符是 `●`(U+25CF),内嵌子集字体里没有这个字形(见 11.9),缺字是静默不画 —— 用户看到的是一排空框,
比明文还糟(会以为没填进去),所以这里保持明文。②状态行原来写 `height: 14px` 配 11px 的字,**软件渲染器
会把整行裁掉**(不是截断,是一个像素都不画),状态文字于是静默消失 —— 改成 20px 才画出来。

落点:`mcwp-ai/src/lib.rs`(`Stored` / `stored()` / `save()` / `env_override()` / `read_stored()`)、
`mcwp-ui/ui/panel.slint`(新增 `FieldRow` / `ChoiceRow` 两个组件;TextInput 没有 placeholder 属性,
灰字占位得自己补一层,且必须声明在输入框**之前**,否则那层灰字会盖住输入框吃不到点击)、
`mcwp-ui/src/lib.rs`(`AiConfigState` / `ThinkingChoice` / `refresh_ai()`)、
`mcwp-wallpaper/src/main.rs`(`ai_config_state()` / `save_ai_config()`,后者负责落盘 + 就地换客户端)。
实测:空配置打开 → 地址与模型名已填好、API Key 是灰字占位;点保存 → `ai.json` 按默认写出来、状态行
"已保存 · 还没填 API Key";三档挨个保存 → 文件里依次是**无 `thinking` 字段 / `false` / `true`**;
把地址指向本机假服务(8788)保存 → **不重启**下一句就走新服务商,状态行回显新地址与模型名。

### 11.15 对话改成左右交互 + 「暂停 / 继续」这一轮(2026-10-15)

**左右分栏那个 bug 值得记一笔。** `MessageRow` 是 `HorizontalLayout`:靠左的气泡要在气泡**后面**垫一个
`horizontal-stretch: 1` 的填充块,靠右的气泡要把填充块垫在**前面**。原来两个分支的填充块都写在气泡
之前,于是"往左推"和"往右推"同时生效 —— AI 的回复也被顶到了右边,看起来像双方都说在了同一个人的位置。

**「暂停」停的是这一轮,不是整个界面。** 输入区的按钮是三态(`run-state`:0 闲着 / 1 正在跑 / 2 已暂停):
闲时是「发送」胶囊,跑的时候换成一颗**圆钮**(自绘的深色方块),暂停之后变成「继续」胶囊。外层固定
76px 宽,三态切换时按钮不左右跳。

**HTTP 请求掐不断,所以"暂停"只能是"回来就丢"。** `ureq` 没有取消接口,后台线程照样跑完那几秒;于是
Rust 侧把这一轮做成一份可重放的记录 `Mission { session, text }` + 一个自增 `run_id`:

- 发送 / 继续都 `run_id += 1`,结果回来时**认轮次**,对不上直接扔(日志"丢掉过期的一轮");
- 暂停 = `Running` 换成 `Paused`,请求不作废、但结果注定认不上;
- 继续 = 拿那份 `Mission` **原地重跑**,并且**不重新往会话里塞用户那句话**(它已经在会话里了,再塞一遍
  就变成两条 —— 实测确认);会话在暂停期间被删掉就不续了,状态行照实说"这条会话已经删掉了";
- 暂停期间用户又发新消息:按钮先变回「发送」(`draft` 一非空就切),发送即**取代**上一轮,不是排队。

**钉到底部:三个 Slint 坑,全是静默的。**

1. `viewport-y` 是**滚动偏移,往下滚是负值**,"到底"的位置是 `height - viewport-height`。写成正数会被
   Flickable 自己夹回 0(合法区间是 `[height - viewport-height, 0]`,见 `i-slint-core` 的
   `ensure_in_bound`),表现就是"列表永远停在顶部,最新那条得手动滚"。
2. 消息数组变的那一刻布局还没重算,这时候读 `viewport-height`(绑着 `msg-list.preferred-height`)拿到
   的是旧值,算出来的偏移量差一条。而"内容高度一变就去写 `viewport-y`"这条更直接的路会 panic
   (`Recursion detected`,那个通知正好从布局求值中间发出来),绕一层本地属性也一样;`init` 里直接读 / 写
   这两个属性同样 panic。
3. 所以钉底部改成一个 `16ms × 8` 的短命定时器:每次 tick 重新读一遍高度、重钉一次,总有一次读到的是
   布局重算之后的值。停的条件**只能是次数** —— 写"钉到位了没"会让它拿旧值判断,第一次就把自己停掉。

另外:需要图标就自绘(矩形 / 圆),别指望字体字形,也别用 `Path` —— Slint 软件渲染器里 `draw_path` 是
空实现,三角之类会**静默不画**(本来想用三角表示「继续」,实测踩过,最后改用文字胶囊)。

落点:`mcwp-ui/ui/panel.slint`(`MessageRow` 的左右分栏、`RunButton`、输入区三态按钮、`Flickable` 的钉底
逻辑)、`mcwp-ui/src/lib.rs`(`UiEvent::PauseRun` / `ResumeRun`、`RunState` / `set_run_state()`)、
`mcwp-wallpaper/src/main.rs`(`Run` 状态机、`start_run()` / `run_mission()`、`AiOutcome.run`)、
`mcwp-wallpaper/src/sessions.rs`(`exists()`:暂停期间会话被删的判断)。
实测(`--ai-ask` 起一轮,再点圆钮 / 点「继续」):点暂停 → 圆钮变「继续」+ 状态行"已暂停 · 点继续接着跑这
一句";点继续 → 回到圆钮,旧请求落地时被丢掉、新请求正常落壁纸;全程会话里那句话只有一条。
### 11.16 生图真正落地:预设清零 + 从桌面壁纸自动取图(2026-10-15)

**预设清零,是连那条路一起拆掉。** 早期「画面由本地着色器现算」那套(`WallpaperSpec` / `Preset` /
`scene.wgsl` / `mcwp_ai::Client::draft()`)整条退场:现在壁纸**只有一种来源 —— 一张图**。
`mcwp-spec` 只剩 `Photo`;渲染器只剩"画照片"一条管线,`Renderer::render()` 只吃 `PhotoParams`;
`mcwp-spec/presets.rs` 和 `scene.wgsl` 直接删掉。留着那套的代价不是那几百行代码,而是**每一个下游
都得写一遍"这是哪条路"的判断** —— 那才是它会一直收费的地方。

**一条链路:GLM-4-Flash 写提示词 → cogview-3-flash 出图 → 入库 → 上屏。** `chat.plan_photo()`
把用户那句中文改写成生图提示词 + 动效配方(推近 / 平移 / 速度 / 效果层),`Images::generate()`
出图并**当场把图下下来** —— 服务商返回的 URL 只有 7 天有效期,存 URL 等于存一张过期就没了的东西。
整轮 9~16 s,全在后台线程里跑,主进程照旧 60fps 不掉帧(`AiOutcome` 那条通道)。

**库换了个形状:一个目录、三个平铺文件。** `%APPDATA%\MC壁纸\photos\` 下,每张壁纸是
`<id>.json`(元数据)+ `<id>.png|jpg|bin`(生图接口原样返回的字节,**永不重新编码**)+
`<id>.thumb.png`(缩略图)。三条规矩:

- **元数据是"这张壁纸存在"的唯一标志**:扫库只认 `.json`,没有配套图片的条目跳过。
- 写入顺序**先图后元数据**:反过来的话中途挂掉会在库里留一个指向空气的条目。
- **缩略图入库时就生成**:面板刷一次库是几十张,现场解 1080p 原图再缩就是每张 100 ms 起步。

旧目录叫 `library`(里面是 `WallpaperSpec` JSON),**直接换目录名而不是兼容旧格式** —— 那批文件
永远配不上图片,同处一目录只会让每次扫库都刷一串"找不到图片"的警告。

**从桌面壁纸自动取图(这一轮的主角)。** `mcwp_platform::wallpaper::current_image_path()` 走
`SPI_GETDESKWALLPAPER` 把用户现在那张壁纸的文件路径读出来,三条理由让它值得存在:

1. 生图要花钱、要等十几秒,而用户机器上本来就压着一张静态壁纸 —— 抬进管线当场就得到一张
   「会动的」壁纸(静帧呼吸 + Ken Burns 推拉),不必先等模型;
2. 我们的窗口是盖在桌面上的,**库空着时什么都不画就是一屏占位色**;把用户原来那张抬上来,
   看不出接缝;
3. 所以「库空着就自动抬」是**第一次启动的兜底**,不用用户动手也不用生图。`--adopt` 和面板库页
   那颗「用当前壁纸」是"再抬一次"的显式入口(换过桌面壁纸之后想把它收进来)。

三个坑,全是静默的:

- **从「设置」里选的壁纸,返回的是转码件 `…\Themes\TranscodedWallpaper`,它没有扩展名。**
  所以解码只能"按文件头认格式"(任何按扩展名猜的实现到这里都失效),标题也不能拿文件名充数 ——
  不特殊处理的话,库里每一张抬进来的壁纸都会叫「TranscodedWallpaper」。实测:本机就返回这个。
- **有些机器上存的是带环境变量(``%SystemRoot%\web\wallpaper\…``)的路径**,Windows 原样给你。
  `is_file()` 拿到 `%…%` 只会返回 false,而"文件不见了"和"路径没展开"在调用方看是同一个症状 ——
  所以这里自己展开一次(`expand_vars()`,认不出的变量原样留着)。
- **纯色背景 / 幻灯片 / 被组策略接管时返回空串 —— 那不是错误,是"没有图"**,所以返回 `None` 而不是
  `Err`,调用方少一层错误分支。另外 4K/8K 的图可能大过 GPU 纹理上限,上屏前先缩一份(落盘的仍是原图)。

**反复抬同一张不该在库里堆副本。** 抬进来的 id 按**源文件路径**定(`adopted_id()`),不按时间:
按时间生成的话,点两次「用当前壁纸」、`--adopt` 又跑一遍,每次都是一条新记录。实测踩过 —— 调试时
点了八下,库里就多了八张长得一模一样的副本。撞上同一个 id 就先 `photos::remove()` 再存(删而不是
覆盖:画面文件的扩展名可能变,`save` 只写新的那份,旧的那份会变成谁也认不出来的孤儿)。

**面板:库页是缩略图网格 + 右键菜单,设置页分成两组。** 库页 4 列一屏,**自己算坐标**而不是用
`GridLayout`(Slint 的 GridLayout 不支持 `for`:`'if' or 'for' expressions are not currently
supported in grid layouts`);列数要在运行期按张数折行,所以 `x: Math.mod(i, 4) * 178px` ——
**Slint 没有 `%` 运算符,必须写 `Math.mod`**。右键一张弹「换上这一张 / 删除这一张」。设置页拆成
**对话模型**(把一句话写成提示词)和**生图模型**(拿提示词出图)两组,生图那组**留空就跟着上面那组走**。

**Slint 坑:一个布局里两个都带 `vertical-stretch` 的 `if` 分支,空白会被各分一份。** 这是本轮最像
"位置不对"的那个 bug:库页原来写成"空态一个撑开的 `Rectangle` + 有货一个撑开的 `Flickable`"两个
`if` 分支,结果网格被压到卡片中部以下、头上空一大块。修法不是调数值,而是**只留一个撑开的元素** ——
把空态那句说明画进同一个 `Flickable` 的网格里(网格高度再和视口取大,空态才谈得上居中)。同类问题
在会话页也存在,只是那边两个分支的真实高度差得不多,肉眼看不出来。

落点:`mcwp-platform/src/wallpaper.rs`(`current_image_path()` / `expand_vars()`,新增 crate
依赖零)、`mcwp-image/`(新 crate:`Bitmap` 的解码 / 缩放 / `encode_png`)、
`mcwp-spec/src/photo.rs` + `lib.rs`(删 `presets.rs`/`WallpaperSpec`,`fnv1a64` 改成 `pub` 给 id 用)、
`mcwp-render/src/photo.wgsl` + `lib.rs`(删 `scene.wgsl`,只留照片管线)、

### 11.17 动态壁纸:两个智能体 + 图生视频 + Media Foundation 播放(2026-10-16)

**「动态壁纸」= 一段 mp4,不是渲染出来的动画。** 生图那条路给的是「一张图」,这一轮补上第二种形态:
复用已有的构图与交换链,画面帧照旧从 CPU 上传,只是这次每 1/31 秒换一帧。

**两个智能体,各说一句话。** 用户输入的是「想看到什么」(静态描述),视频接口要的是「它该怎么动」(运镜、
镜头外的变化)—— 这两件事不是一回事,而后者**没人写过**。于是拆成两步:

1. **智能体一(对话模型,`Client::plan_motion`)**:看着画面本身写「它该怎么动」那一句;
2. **智能体二(视频模型,`Videos::animate`)**:拿原图 + 那句话出片。

`plan_motion` **永不返回 Err**:没配模型 / 超时 / 回一句空话,一律退化成 `fallback_motion_prompt()` 那句通用
运镜。这条链路的失败点已经够多了(出片一分钟起步、成片链接 24 小时过期),不该再多一个「提示词没写出来就不做了」。

**接口是异步任务制,坑都静默:**

- 提交只拿到 `task_status: PROCESSING`,还要再轮询 `async-result/{id}`;
- **轮询会回 HTTP 400,body 里却是正常状态** —— 判成功必须看 body 的 `task_status`,按 HTTP 码 `?` 早退
  会把成功的任务丢掉;
- **成片链接只有 24 小时有效期**(生图那批是 7 天):拿到 URL 当场下载,存 URL 等于存一个明天就没了的东西;
- `cogvideox-flash` 实测一直回 429 / 1305(「该模型当前访问量过大」),默认改用 `cogvideox-3` ——
  `1728×1080 · 31fps · 5.1s`,一次 61~167 s(带水印)。

**条件图用 base64 内联,不走 URL。** 接口吃的 `image_url` 也收 `data:image/png;base64,...`(实测 2 MB 请求体
被接受),于是**库里任意一张图都能直接做视频**。理由:我们的图是本地文件,没有公网 URL 可给,而「先传图床再引用」
要多一个依赖、多一个会过期的中间物。`image_data_url` 加一个手写的 `base64()`(十几行,不引依赖)就是为它写的。

**播放:Media Foundation 解到 CPU,再 `write_texture`。** 这是 §12.2 待定项 7 的落地结论 —— 那里原建议
「解到 DXGI surface」,但那要一整套 D3D11 / 共享纹理互操作,而我们的交换链是 `DxgiFromVisual`,
`write_texture` 这条路已经为静图跑了很久。`mcwp-video` 用 `IMFSourceReader` 把帧解成 `MFVideoFormat_RGB32`
(`MF_SOURCE_READER_ENABLE_ADVANCED_VIDEO_PROCESSING` **必须在 `MFCreateSourceReaderFromURL` 时通过
attributes 传**,读者起来之后没有 `GetAttributes` 可以补),缩放一并交给它。

三个坑,同样静默:

- **stride 要从 `MF_MT_DEFAULT_STRIDE` 读,而且可能是负数**(自下而上):负数不翻行,画面上下颠倒,但没人会
  报错 —— 所以 `copy_bgra_to_rgba` 抽成独立函数并单测(红蓝对调、上下翻转各测一遍);
- `MFVideoFormat_RGB32` 的内存是 **B,G,R,X**,渲染器要 RGBA8:红蓝对调是最容易犯、也最容易被当成
  「服务商给的视频就长这样」的错误;
- 取帧缓冲**先 `Unlock` 再报错**:`?` 提前返回会把缓冲锁死,下一次 `Lock` 直接失败(症状是全黑)。

**播放器是「拉模式」,而且落后就丢帧。** 壁纸刷新率 60、视频帧率 31,谁快谁慢还不一定,让任一方驱动另一方都会
出错 —— 于是主循环每帧问播放器「该换下一帧了吗」,由它按视频自己的帧率回答。暂停一阵再继续时 `delta` 很大,欠下的
帧数**夹住不追**:卡一下没人看得出来,但一口气解十帧会把「卡一下」变成「卡一秒」。放完 `rewind` 从头再来 ——
五秒的片段循环播放才像壁纸。

**入库是四件套,而且新 id 必须重新生成。** `<id>.mp4` + `<id>.png`(封面 = 第一帧,也是缩略图的来源)+
`<id>.thumb.png` + `<id>.json`。id 接着用原图那个的话,这条视频的封面**会把原图那张画面文件盖掉**,库里就再也
找不到那张静图了。所以「是不是视频」以 **`<id>.mp4` 在不在**为唯一真相(json 里的 `kind` 与之不一致时打警告并
就地掰正)。入库失败(库目录只读)就把 mp4 落到 `%TEMP%` 照常上屏:用户等了一分钟,不能因为库写不进去就什么都不给。

**面板上多了四处:** 库格右上角的「动」标、格子右键菜单(静图三项 / 视频两项 —— 视频不画「做成动态壁纸」,
它已经是动态的了)、库页工具栏的「做成动态壁纸」、设置页的「视频模型名」。

**自检入口是两个命令行参数**(都只给开发用):`--animate <库里 id>` 跑完整条链路并上屏;
`--video-selftest <mp4 路径>` 只解一段文件、打印帧数与采样均值就退出(不建窗口、不占桌面)——
解码器坏了和库坏了是两件事,分开测。

**内存:静图 158 MB → 视频 386 MB(本机实测)。** 多出来的 ~230 MB 是 MF 的解码 / 转换池,跑几分钟不涨(不是
泄漏)。这个数字要如实记下来:视频壁纸的内存代价不在我们这边,而在「CPU 侧解码」这条路上 —— 真想压下去就得走
D3D11 互操作,那是另一件活。

**顺带修了两个验证工具(它们自己就是坑):** `shot-panel.ps1` 是 DPI 感知的、`click-panel.ps1` 不是,150% 缩放
下两边坐标系差 1.5 倍,点哪儿都不对 —— 两个都得设 `PER_MONITOR_AWARE_V2`;`raise-window.ps1` 用 `SW_SHOW`
拉不回最小化的窗口,得用 `SW_RESTORE`。
### 11.18 库页四问:入库看不见、排版乱、预览断链、导入删除没入口(2026-10-16)

这一轮用户提了四件事,查完的结论是:**只有一件是真的坏了,而且不在用户以为的地方。**

**「壁纸库怎么不保存生成的壁纸」——入库链路本来就是通的。** 实测 `--panel --ai-ask "清晨安静的雪山湖面"`,日志一路是
`生图完成:1808×1136 · 126 KB` → `新壁纸已入库:…\photos\6ad1ca3fd8ac1aa9.json` → `已换上新壁纸:晨光雪山湖`,库里也确实多了一格。
真正的问题是**看不见**,由两件小事叠出来:

- 会话里只留一句「已为你生成…的壁纸」,图在库页里,这句回复和那张图**之间没有任何联系**;
- 库页在面板打开期间**不会自己重刷**,不切页就看不到新入库的那一格。

所以这一轮补的是"说不清楚"的那部分,而不是往管线里再加一段。

**消息只存配图 id,不存路径。** `StoredMessage` 加 `photo: Option<String>`,写进去的是**库里的 id**。为什么不是路径:
库目录是唯一真相,路径会随改名 / 迁移失效;而"这张还在不在"应该由库说了算 —— 文件被删掉之后,旧消息要能显示成
「这张已经不在壁纸库里了」,而不是留一个点开是黑框的死链。字段带 `skip_serializing_if = "Option::is_none"`,对老会话文件
是零成本:加字段不用动 schema 版本,老文件读回来正好是 `None`,那一轮历史消息就是"没有配图"。

**缩略图索引只能待在面板线程。** `slint::Image` **不是 `Send`**,能跨线程搬的只有 id,所以 `ChatMessage` 里走 id,
面板线程内再挂一份 `thread_local THUMBS: HashMap<id, Image>`,灌库列表时顺手填(存的是同一个句柄,clone 不额外占内存)。
**`apply_library` 必须排在 `apply_session` 之前**:反过来的话,面板第一次打开时消息要查的那张缩略图还没进缓存,
历史消息会**全都**显示成"已不在库里"。顺手也删掉了 `PanelHandle::refresh_library` —— 它和 `apply_state` 是两个入口,
谁先谁后决定配图认不认得出,这种"用错就悄悄坏"的函数不该留在 API 里,统一走 `refresh(panel_state(…))`。

**看大图是面板自己的浮层,不是系统看图器。** `image-fit: contain`,点任意处关闭;关掉之后 Rust 侧把那张 RGBA 也换成
`Image::default()` —— 不换的话几 MB 的位图会一直挂在常驻窗口上。

**「排版很有问题」的真凶是 Slint 的 `/` 是浮点除。** 库格坐标原先是这么算的:

```slint
x: (i - (i / cols) * cols) * (cell-w + cell-gap);
y: (i / cols) * (cell-h + cell-gap);
```

`i / cols` 看着像整数除,写出来却是 `0 / 0.25 / 0.5 / 0.75` —— Slint 里**两个 int 相除也会先抬成 float**
(`i-slint-compiler` 的 `passes/resolving.rs` 里就写着 `(false, false) => Type::Float32`)。于是 4 张图全落在第 0 列、
只差几十像素地摞在一起,行数还按 1.75 行算 —— 截图里"几张图压成一团"就是这么来的。修法是行号统一写
`Math.floor(i / cols)`,列号再用"序号 − 行首序号"减出来,行数用 `Math.ceil(张数 / cols)`。这里用浮点是安全的:
两个 int 相除只要除得尽,结果在二进制里一定精确(`1.0 / 2.0` 这种),`floor` 不会少一。

**导入 / 删除补上明确入口。** 原来只有格子右键,用户找不到。现在库页工具栏是四颗钮:`导入图片` / `删除` /
`做成动态壁纸` / `用当前壁纸`;`删除` **只在有选中项时可点**,点下去弹二次确认(文案写明「文件不会进回收站」——
这个误会比误删常见得多),格子右键菜单保留。导入走 Win32 `GetOpenFileNameW`
(`OFN_FILEMUSTEXIST | OFN_PATHMUSTEXIST | OFN_NOCHANGEDIR`,只列 PNG / JPEG,因为我们的解码器也只认这俩),
导入条目复用"按路径算 id"的 `adopted_id()`,所以同一张图反复导入只有一条记录。**坑:模态对话框会阻塞主循环**,
弹着的时候面板完全静止 —— 无人值守的自动化里不要点这颗钮。导入 / 删除之后都**整块回填**,不必等下次切页;
空态那句也改成了「…或者点上面的「导入图片」把本机图片收进来」,不然"库是空的"和"没入口"会互相强化。

### 11.19 「面板为什么总在最上层」:验证工具把窗口钉成了 TOPMOST(2026-10-16)

用户报:**面板总是置顶在最上层,遮盖其他应用。**

查下来**不是面板自己干的**:面板侧所有 `SetWindowPos` 都带 `SWP_NOZORDER`,`mcwp-ui` 里只有一处 `ui.show()`
(建窗那一下),Slint 侧没有 `always-on-top`,启动路径也没有任何"提到最前"。真凶在我们自己的验证工具上:
`tools\raise-window.ps1`(还有更早的 `panel-probe.ps1`)为了让截图 / 点击不被打断,调的是
`SetWindowPos(hwnd, HWND_TOPMOST, …)`。`HWND_TOPMOST` 不是"提一下",它给窗口加的是**持久样式 `WS_EX_TOPMOST`** ——
脚本退出、进程还在,样式就还在。这天里为了截图跑了好几次,面板于是从"临时提到最前"变成了"永久压在所有应用上面"。

**实测证据**(命令行读 `GWL_EXSTYLE`):现场那个面板 `0x40118` → 清掉之后 `0x40110`,差的那一位就是 `WS_EX_TOPMOST`。
解开用的是 `SetWindowPos(hwnd, HWND_NOTOPMOST, …, SWP_NOACTIVATE)`,**没重启进程**。

修法两条,都在工具侧:

- 提窗口改用 `HWND_TOP`:"这一次排到 z 序最前"就够了,用户点别的窗口照样能盖住它;
- 工具**开头先 `HWND_NOTOPMOST` 一次**,把老版本脚本留下的钉住状态解开 —— 谁踩出来的坑谁填;
- 顺手让工具在**发现**窗口是被钉住的说一句 `注意:这个窗口原来被钉成了 TOPMOST(WS_EX_TOPMOST),正在解开`:
  悄悄治好等于把线索一起删了,下次再有人写 `HWND_TOPMOST`,现象还是"面板总在最上层",却没人知道是谁钉的。

教训一句话:**验证工具只该改"这一刻谁在前",不该改窗口的样式**;凡是"把窗口提一下"的脚本,写 `HWND_TOP`。

### 11.20 「怎么生成的都是雪山湖面」:提示词被当前壁纸带跑了(2026-10-16)

用户连着要几张,不管说什么,出来的都是雪山湖。会话文件里那三条摆在一起就很清楚:

| 用户说 | 模型给的提示词 |
| --- | --- |
| 清晨安静的雪山湖面 | 画清晨安静雪山湖面倒映蓝天白云 |
| 我要看二次元美女 | 画**雪山湖**倒影里的二次元少女 |
| 生成一张 windows 系统的壁纸 | 画**雪山湖面**倒映薄雾蓝天的清新壁纸 |

**这不是"模型笨",是题目出歪了。** `photo_request` 把两块信息平铺在一起:【当前壁纸】的标题 / 提示词
(90 字、有主体有光线有色调),后面跟一句光秃秃的【用户说】。小模型会把这种写法读成"要改的东西 + 一句要求",
而两块的信息量差着一个数量级 —— 它当然照着大的那块抄。用户那句"你需要根据用户消息补全之后生成",说的正是这里。

改的三处都在**提示词**里,不在代码逻辑里:

- **题材只认「用户说」**:系统提示词第一段讲清楚当前壁纸**只是"他现在屏幕上是什么"** ——
  只有用户说"换成 / 改成 / 再 / 更…"这类**相对说法**时才当参照;用户没提到的题材(尤其是当前壁纸里那些)
  **一律不许出现**;
- **教它"补全"**:用户的话常常又短又笼统,要求模型**替他补全画面**(主体怎么摆、什么光线、什么色调、什么构图),
  并配一个例子:"生成一张 windows 系统的壁纸" = 一张**用在 Windows 上**的舒心壁纸,不是去画 Windows 的窗口和徽标。
  核心那句是**"补全是把话说完,不是换题材"**;
- 两块标题改成【当前壁纸】(仅供参考,不是这次的题材)/【用户说】(以这句为准) ——
  把"谁说了算"直接写进标题,比在代码里猜用户是不是"想改一改"可靠。

**顺带补了 `--plan <一句话>`**:只跑提示词那一步,把**发给模型的请求**和**模型给的计划**一起打出来
(`--plan-current <库 id>` 顺带带上"现在屏幕上那张")。原来只有 `--images-selftest`(整条链路,一次十几秒、
还要落一份预览图),调提示词太慢,而"画歪了"十有八九是**提示词先歪了**。实测(同一句话、同一个当前壁纸):

| 用户说 | 修之前 | 修之后 |
| --- | --- | --- |
| 生成一张 windows 系统的壁纸 | 画雪山湖面倒映薄雾蓝天的清新壁纸 | 森林月夜 / 都市夜景黄昏 |
| 我要看二次元美女 | 画雪山湖倒影里的二次元少女 | 二次元美女生动壁纸(室内窗边) |
| 把雪山换成樱花,其他不变 | — | 二次元樱花湖(**湖留着、雪换成樱花**,相对说法照旧吃当前壁纸) |
| 画一只趴在窗台上的橘猫 | — | 窗台橘猫(确认不会又被带跑) |

端到端在面板里跑了一遍同一句话:`--panel --ai-ask "生成一张windows系统的壁纸"` → 回复「好,给你画一张都市夜景的黄昏」
+ 一张都市黄昏的照片,和上一轮那张雪山湖并排放在同一条会话里,一眼前后对比。

**同日还有两处工具上的收尾**(接 §11.19):

- `raise-window.ps1` 补 `AttachThreadInput`:单用 `SetForegroundWindow` 会被**前台锁**拒掉(表现是脚本说
  "raised"、截图里还是别的窗口盖着),而"能稳定提上来"恰恰是老版本改用 `HWND_TOPMOST` 的动机。挂到当前前台
  窗口的线程上再提,既能提上来、又**不碰窗口样式**;
- `shot-panel.ps1` 改用 **`PrintWindow(PW_RENDERFULLCONTENT)` 抓窗口自己的内容**:截图从此跟 z 序无关,
  根本**不需要再提窗口** —— 那条"为了截图把窗口钉在最上面"的路子,从源头上没了。不加 `PW_RENDERFULLCONTENT`
  只能拿到标题栏加一块空白(面板内容由 DWM 合成,老式 PrintWindow 抓不到)。

### 11.21 生图不再自动换桌面 + 预览图右键「设为壁纸」(2026-10-16)

用户两句原话:**「生成完不要自动设为壁纸,需要放进壁纸库」**、**「在对应的对话界面右击刚生成的壁纸会显示是否设置为壁纸的」**。
合起来是一件事:生图那一步只负责**把图拿出来**,用不用由用户说。

**为什么改。** 生图原来落回 `adopt_photo`(写库 + 顺手换桌面)。问题不是"多做了",是**做错了主**:
"这回画出来的要不要用"是用户的决定,自动换上不但替他决定了,还会把他正看着的那张顶下去 ——
而他想回头用上一张,得先去库页翻。所以改成只入库,入口只留一个:回复下面的预览图**右键 →「设为壁纸」**。

| | 改之前 | 改之后 |
| --- | --- | --- |
| 生图落地 | `adopt_photo`:入库 **+ 换桌面** | `save_generated_photo`:**只入库**,`active` 一个字不动 |
| 状态栏 | 「已换上…」 | 「已画好「X」放进壁纸库 · 右键预览图可设为壁纸」 |
| 想用这张 | (已经换上了) | 预览图右键 →「设为壁纸」 |

- `save_generated_photo`(main.rs 588 行)是生图那条路的落地点:只 `photos::save` + `scan_library`;
  `adopt_photo` 原样留着 —— `--gen` / `--ai-ask` 这些**一次性入口**照旧直接上屏,那些本来就是"我让你换"的语气。
- **入库失败是唯一的例外**:那一刻这张图只存在于内存里,什么都不做等于让用户白等十几秒,所以退回老行为
  (照常挂上)并在状态栏写「库写不进去,先直接挂上了」。库写不进去(只读盘、盘满)本来就罕见,真碰上时
  "图还在"比"库里干净"重要。日志里也把这个例外单独标出来:`自动上屏=否` / `是(库写不进去)`。

右键菜单(`ShotMenu`,176 × 82,两项:**看大图** / **设为壁纸**)复用库格那套写法,三个细节:

- **菜单里存 id,不存行号**。行号是**打开菜单那一刻**的,而菜单开着的时候用户照样能发消息、删会话 ——
  存行号会让「设为壁纸」指到另一张图上。这种错最坏:它不报错,只是换了张不相干的壁纸。
- **配图已经不在库里就不弹**(`photo-gone` 为真直接返回)。两项都要去库里找这张图,弹出来只会点了就失败;
  那一行文字已经写着「这张已经不在壁纸库里了」。
- 顺带补了个老问题:库页那层菜单原来**不判 `view`**,切到会话页之后它还会压在新页面上;现在两边都带上
  `&& root.view == N`。两块菜单的高度在面板侧各存了一份(`lib-menu-h` / `shot-menu-h`)——**改项数要两边一起改**。

「设为壁纸」落在 `UiEvent::SetWallpaper(id)`:在 `library` 里按 id 找下标 → 走 `switch_to_photo`,
和库页点一张**是同一条路**。两件事本来就是同一件 ——"把库里第 N 张换到桌面上",只是这次的 N 不是用户点出来的。
找不到那张就说「这张已经不在壁纸库里了」,不静默吞掉。

实测(日志 + 抓屏):

本轮出图:紫色花海与小木屋 | 提示词调用=1 | 降级=false | 自动上屏=否     ← 桌面没动

抓两次 `PrintWindow`,PNG **字节完全相同**(544837 字节),而同一时刻的桌面抓屏显示内容早就变了。

所以**右键菜单这类交互只能靠全屏抓屏(`shot.ps1`)确认**,`shot-panel.ps1` 只适合"窗口自己长什么样"的静态核对。
当时还有一层干扰:用户自己正点着面板 —— "合成鼠标去验证"和"用户正在用"撞在一起,画面随时会变,点下去的东西
也可能不是你以为的那个。规则:**先提窗口(`raise-window.ps1`)、再单独抓一次屏确认当前视图,别一条命令连着点两下。**
### 11.22 动态壁纸的元素级动效 + 「播放完接不回开头」的收尾(2026-10-16)

**问题(用户原话)**

> 动态壁纸需要实现的是,首先是需要对画面元素进行分析,同时需要处理元素对应的属性,比如说一张城市壁纸…哪里灯光该亮需要亮,车流的运动,天上的云是要流动的,或者是天上飞的鸟…人物壁纸…衣服在动…再就是动态壁纸播放完和播放前是需要连在一起的,现在是不连的。

拆开是两件事:**①** 动效提示词太粗 —— 只有「镜头缓缓推近」这类整图运镜,画面里的灯、云、车没被点到名,出来就是"一张图在慢慢放大";**②** 循环是**硬切**:播放到末帧 `rewind()` 回第一帧,末帧和首帧对不上就跳一下。

**方案 A:先看图,再写元素清单(免费)**

用 `glm-4v-flash`(**免费**、支持图像理解)把照片看一遍,产出结构化的 `MotionPlan`:

- `camera`:固定机位 / 缓慢推近 / 缓慢拉远 / 缓慢平移;
- `elements`:最多 5 个 `{ kind 元素名, area 位置, action 怎么动 }`。

都市夜景黄昏实测:`动效方案:镜头=固定机位 · 2个元素` →「全图灯光逐个亮灭闪烁;左上云朵向右缓慢飘移」。拼进视频提示词后带上固定收尾句:「整体缓慢平稳,结尾回到起始画面,镜头与光线回到原位。」

- **area 用九宫格**(左上 / 上中 / 右上 / 左中 / 正中 / 右中 / 左下 / 下中 / 右下 / 全图),**不用像素框**:视觉模型给不出可靠的像素坐标,给了也是编的;九宫格它答得准,「左上」这种说法视频模型也听得懂。
- **action ≤12 字、不许重复元素名**:小模型爱写「灯光发出闪烁的灯光效果」这类车轱辘话,重复的部分在拼提示词时被 `trim_repeated_prefix` 削掉(按**字符边界**削,不是按字节,否则会切碎汉字)。
- 这一步**只看图、不碰视频模型**,所以免费;**失败 / 超时 / JSON 读不懂都只 warn 不报错**,退回老的通用运镜 —— 动效写不好不该让整条生视频链路失败。
- 老照片没这个字段,`#[serde(default)]` 自动补空方案,库文件零迁移。

**方案 B:两头闭环 + 播放侧的环形混合**

- 提交侧:`cogvideox-3` 支持**首尾帧**(`image_url: [首帧, 尾帧]`),**首尾都传同一张静图**,等于告诉模型「从这里出发,回到这里」;首尾帧这条路不被受理就**退回单图重提一次**(不让一次尝试失败掉整条链路)。
- 播放侧:首尾帧也只是"尽量"闭环,帧间压缩误差还在,所以接缝处再做 **0.8 秒环形混合**:末帧与首帧之间按 smoothstep 混 RGB,亮度跳变就看不出来了。短片按 `duration / 4` 收窄窗口,免得 5 秒的片子有一半时间在淡化。
- 混合只在**长度一致**时才做(尺寸变了就原样贴帧),不然会读到越界像素。

**免费 / 收费的分布**

| 步骤 | 模型 | 花费 |
| --- | --- | --- |
| 看图写元素清单 | `glm-4v-flash` | 免费 |
| 对话补全提示词 | `glm-4-flash` | 免费 |
| 图生视频 | `cogvideox-3` | 1 元/次(5 秒与 10 秒**同价**) |

`cogvideox-flash` 免费档实测一直回 429,所以「用免费模型试提示词」这条路不成立 —— **视频侧每验证一次就是 1 元**。因此专门留了两个入口(**都不建窗口**):

- `mcwp-wallpaper --plan-motion <库 id>`:只跑看图 + 拼提示词,**免费**,反复调提示词就用它;
- `mcwp-wallpaper --animate-save <库 id>`:跑完整链路(**花钱**)并入库,**不上屏、不建窗** —— 面板开着时单实例锁会被抢,这条路让「后台出一片」和「看着面板」能同时进行。

**成片分辨率**:CogVideo 短边 1080,拉到 2560 屏宽会软;4K 同价但更慢更易失败,先按 1080 档。

**还没做的 C(元素级程序化动效)**:灯光在 shader 里真的逐个亮灭、车流走视差、云层单独流动、飞鸟 —— **免费、必然无缝、分辨率跟屏幕走**,城市夜景最能出效果。前提是渲染器先做**多纹理 / 多 pass** 重构(现在只有一张照片纹理,`from_video` 还会把 zoom / pan / effect 全关掉,因为视频自己会动)。`MotionPlan` 已经按能被 GPU 消费的形状存好了,到时候直接喂进去。 **→ 2026-10-16 更正:不用多 pass,做出来了,又被同一个需求否掉 —— 见 11.23。**

**实测(2026-10-16,同一条「都市夜景黄昏」,两轮都是 1 元)**

| 轮次 | 动效提示词 | 结果 |
| --- | --- | --- |
| 第 1 轮 | 全图灯光**逐个**亮灭闪烁;左上云朵向右缓慢飘移 | 出片 10.35 s / 1718×1080 / 31 fps |
| 第 2 轮 | 全图灯光**一明一暗地**闪烁;左上云朵**缓缓飘来飘去** + "亮度、色彩和构图保持稳定" | 同上,接缝差见下 |

第 1 轮验出一件要紧的事:**末帧比首帧整体亮了 10%**(采样均值 93.3 → 103.2),
**首帧↔末帧平均差 14.22,比"首帧↔中点那帧"的 8.05 还大** —— 画面不是"没动过",
而是**一路往一个方向走**:模型把"灯光逐个亮起"理解成了"一盏盏点亮"的累积过程。
两条结论因此落地:

- **"首尾帧都传同一张图"不足以闭环。** 模型是照字面"尽量"绕回去的,而它对我们那句话的
  理解更要紧 —— 所以动作必须写成**来回**的,提示词里还得明说"亮度、色彩和构图保持稳定"。
- **播放侧那 0.8 秒淡回只能收尾,不能救场。** 接缝差 14.2 时它把差异摊成 0.8 秒的
  "画面往回并":比硬切好看,但不是无缝。差多少、要不要重写提示词,得先看得见数。

顺带修掉一处**真会咬人的截断**:拼提示词原来是"整句拼完再截断",而截断砍的是尾巴 ——
元素一多,被砍掉的那句恰好是"结尾回到起始画面"。现在先给收尾留位置,再拿剩下的长度装元素
(`truncate` 切断时会补一个省略号,预算还得再减一,这条是被测试逼出来的)。

**`--video-selftest` 现在会把接缝量出来**:首帧↔末帧 vs 首帧↔中点,外加首 / 中 / 末三帧的
采样均值。"播放完那一下跳不跳"原本只能盯着桌面等十秒、还得靠眼力,现在是个数,
而且一眼能分清是"整体亮度在漂"(提示词和校正能压)还是"构图真跑了"(只能重出片)。

**超时那件事:钱不能白扔。** 第 1 轮的任务客户端等到 6 分钟就报超时收手,回头查服务端状态
**还是 PROCESSING** —— 钱已经花了、任务还在跑,结果却没人取。两手都补上:

- 等待上限 6 → **30 分钟**(实测同一条 10 秒片:闲时 61 s,高峰 7 分钟还没完;`quality` 档出现 16 分 49 秒才成功);
- 新增 `--video-fetch <任务号> <库 id>`:照任务号把**已经提交过**的那条取回来入库,
  **不提交、不再花钱**;超时的报错里直接把这条命令写出来。第 1 轮的片子就是这么捡回来的。

**C(元素级程序化动效)** 那条路看着不受这些影响(它在 shader 里做,天生无缝),**但试过之后撤了 —— 见 11.23。**
**第 2 轮的片子还量出两件事,都已经落进代码:**

**① 接缝那点差,拆开看是两笔账。** 把末帧整体乘一个系数、跟首帧的亮度对齐之后再量:
两条 10 秒片都从 **13.5 / 14.2 掉到 9.5**,而"首帧↔中点那帧"的基线是 8.1 / 8.9 ——
也就是说,**大约三分之一是"整段在变亮"(曝光在飘),三分之二是构图真的走了**。
于是分两块处理:

- 曝光那笔账:**按帧校正**。入库时把整段解一遍,量出首帧与末帧的平均亮度,比值存进
  `Photo.seam_gain`(老记录缺省 1.0 = 不校);播放时每帧把这个增益从 1.0 线性走到它,
  接缝两边就正好对平。**摊在整段而不是只在最后那一小段**:0.8 秒里补 10% 的亮度,
  那 0.8 秒自己就会忽明忽暗;摊到十秒,每帧只差千分之几,看不出来。
  换算有一个坑:着色器里是 `color * (0.45 + 0.85 * brightness)`,**不是**直接乘 brightness ——
  增益要先把这个偏移解出来(`exposure_brightness`),不然"校了但好像没效果"。
- 构图那笔账:**救不了**。乘系数不会让画面回到起点,只能靠接缝那 0.8 秒淡回盖住。
  真无缝只有两条路:把片子**正放再倒放**(需要能倒着解,现在这条解码路只有 `rewind()`),
  或者走 C(本地元素层,天生无缝)—— 而 C 已经试过并否掉,见 11.23:那条路换来的"无缝"是拿画面的真实感买的。

**② 动效方案的主人是谁,原来记错了。** 方案只写进了**成片**那条记录,而它说的其实是
"**这张图**该怎么动" —— 于是"库里已经存过一份就直接用"那个分支一次都没走到过(死代码),
`--video-fetch` 捡回来的那条记录的方案也是空的。现在方案**写回原图那一份**
(`photos::save_motion_plan`,成片那份同时留着当痕迹)。

**顺带验证**:挂上桌面后主屏(1920×1080)三秒内画面平均差 5.14(在动),
副屏用户自己那张纹丝不动(平均差 0)—— "先单屏、只动主屏"这条没被破坏。
### 11.23 本地元素层:做出来了,又撤了 —— 一次越权的教训(2026-10-16)

`11.22` 收尾时留下两条路:倒放那条要重写解码,元素级这条**免费、天生无缝、分辨率跟屏幕走**,
所以先做了这条,提交也推了(`bd933e1`)。**然后用户看了一眼,把它否掉了。**

用户的原话是两个问题:**画质是生图那边的设置问题**,而且
**「动效需要根据图片中来的、写在生成视频的提示词里,而不是在本地的渲染层上面修改」**。

**为什么这次是用户对**

这一层干的事,本质是**在画面上盖一层「看起来在动」的东西**:灯闪着、云飘着,而画面里那些像素
原本长什么样,一个都没变。视频那条路走的是另一件事 —— 让**画面自己**动起来。前者是模拟,
后者是生成。差别在实测里看得很清楚:

| 量(同一张城市夜景,主屏截图) | 只做 Ken Burns 采样 | 开着元素层 |
| --- | --- | --- |
| 对比度 σ/μ | 0.540 | **0.821** |
| 平均绝对拉普拉斯(细节) | 16.92 | **12.6** |

元素层把对比度推高了 52%、把细节砍掉四分之一 —— **画面又软又假**。同一批截图里还盖着一层
18×18 的方块(下面「马赛克」那节说它是怎么来的)。这还只是「看得见的代价」;看不见的那半是
方向本身错了:一张壁纸的「活」,应该是**它本来就有的东西**在动,而不是我再叠一层动的东西上去。

**撤掉了什么**

- `mcwp-render/src/photo.wgsl`:`Params.elements` 字段、整个元素层段(171 行)、`fs_main` 里两处调用;
- `mcwp-render/src/lib.rs`:`PhotoParams.elements`、`ELEMENT_SLOTS`、`from_photo` 的互斥清零、`from_video` 的清零;
- `mcwp-spec/src/photo.rs`:`ElementVisual`(十二种)、`ElementSlot`、`element_visual`、`area_code`、
  `direction_code`、`default_direction`、`rate_from`、`DIRECTION_NONE`,以及配套的三条测试。

**留下了什么**

- `MotionPlan` / `MotionElement` —— 它们本来就是照着「给提示词的一句话」写的,**现在只剩一个消费者**:
  `mcwp_ai::video_prompt`。文档里「两个消费者」那句跟着改了,「程序化动效层」不再是消费者之一。
- `AREA_NAMES`(九宫格 + 全图):不再喂渲染器,只当**那份看图清单的锚** ——
  `VISION_SYSTEM_PROMPT` 里列的就是这十个,顺序必须一致,有条测试拿它去核。
- 一条更正,它不取决于元素层留不留:**不需要多纹理、不需要多 pass**。当时的判断是「元素层要单独一层、
  所以渲染器得先做多 pass 重构」,真去看代码才发现雪、雨、雾、云影、光晕、水波这六个效果
  **本来就都在同一个 fragment shader 里** —— 差点为一个不存在的前提做重构。

**教训**

- **「让画面动起来」有两个解**:把画面改活(生成),或者在画面上盖一层动的(模拟)。
  选后者之前先问一句:**我想加的那层东西,在真实画面里存在吗?** 灯在闪、云在飘当然存在,
  但要让「照片里本来那盏灯」闪,不是在它上面再画一盏灯。
- 同一把尺子也适用于别的「本地补一层」:凡是模型或素材**本来就能给出**的东西,
  本地再模拟一遍都是负债。
- 一条仍然成立的实现细节:**shader 里让一个区域「整块同亮同暗」,就等于画了一个方框**。
  第一版灯按 `floor(uv * 18)` 分格定相位,上屏是一层 18×18 的马赛克(一格约 107×60 像素,
  一眼就看得出来)。要空间上连续 / 成团(`fbm` 两个频段,相邻像素只差一点相位),并且只提亮
  画面里本来就亮的地方。这条对以后任何「在 shader 里按区域做事」的写法都成立。

### 11.24 「为什么这么糊」:请求体里根本没有画质这一项(2026-10-16)

用户的原话是「为什么这么糊?」。我顺着**上屏路径**查:显示器缩放、Ken Burns 的采样、
纹理过滤、`fit_size` 把 2560×1600 缩成 1808×1136 之后的放大 —— 全是下游。
用户直接把方向点掉:**「是生图的时候画质设置的问题」**。查下去,根因在源头:

**`ImageRequest` 的请求体里从来没有 `quality` 这个字段。** 没发,服务商就按它自己的默认档出图 ——
一般就是 standard。**这条生图路跑了一整天,每一张都是低画质。**

**实测(同一句提示词、同样 1920×1088,免费档)**

| 请求 | 高频细节(平均绝对拉普拉斯) | 文件 |
| --- | --- | --- |
| 不传(等效 standard) | 20.9 | 413 KB |
| `quality=hd` | **29.6(+41%)** | 440 KB |
| `quality=standard` | 21.5 | 399 KB |

两件事记在这儿:

- **取值只有 `hd` / `standard`,`4k` 会被直接 400 拒掉。**「把值写得更大看起来更好」在这儿不成立;
  合法取值是**探出来**的,不是猜出来的。
- **量它要同句提示词 + 同尺寸。** 换了题材、换了尺寸,数就不在同一根尺子上了 ——
  「感觉清楚了」这种判断在 40% 的差距面前没有用;要下结论就固定其余变量,拿拉普拉斯这种
  高频细节度量(工具留在 `$env:TEMP\mcwp-sharp*.ps1`,改个图路径就能跑)。

**同一件事在程序自己这条线上再测一遍(每种 3 张,同句提示词、同尺寸 1920×1088,只有画质不同)**

| 档位 | 逐张(拉普拉斯) | 平均 | 体积(平均) |
| --- | --- | --- | --- |
| `standard` | 15.9 / 27.6 / 19.2 | **20.9** | 409 KB |
| `hd` | 37.1 / 22.0 / 30.9 | **30.0(+43%)** | 482 KB(+18%) |

同档之内逐张差到 1.7 倍,说明**只测一张根本下不了结论** —— 内容本身就带着噪声,`hd` 那 +43%
是站在这个噪声之上的。也正因为有这个起伏,"看着好像清楚了"不能当验收标准;要验收就固定
提示词和尺寸,每种多跑几张看平均。

进图那一步现在也把画质写进日志(`生图:open.bigmodel.cn · cogview-3-flash · hd`),出图那行同样带
(`生图完成:1920×1088 · hd · 498 KB · …`)—— 现场再有人说"糊",第一眼就能分清是
**"没按 hd 出图"**还是**"出图是 hd、上屏又糊了一道"**。

**一条折旧(当天补测):`hd` 的好处不是到处都有**

换一个"低细节"的题再量一遍(橘猫 + 虚化背景,同样 1920×1088,每种 2 张,1:1 逐张):
`hd` 5.14 / 3.91,`standard` 4.67 / 5.55 —— **差别落回噪声里**。两批数据连起来看更像这样:
`hd` 多出来的细节出现在**高频密的地方**(霓虹、线缆、雨丝),而平坦毛发和大片虚化本来就没有
可补的东西。所以"默认 hd"这条结论不变(不花钱,dense 场景明显受益),但**别把它当成
"什么题都会更清楚"**;要复核就挑一张信息密的图,并且每种至少两张。

**还有一笔账没结:我们一直在要"屏那么大的图",而那个尺寸可能超过免费档模型的原生分辨率**

同一句提示词、同一组参数,只换 `size`:`1024×1024`(1.05M 像素)出来是干净的;
`1920×1088`(2.09M 像素,正好顶在服务商 2²¹ 的天花板上)在 **1:1** 下整幅都有一层细密的斑纹
(两张样本都有,不是偶发)。怀疑是"模型按更小的尺寸渲染、服务商再拉大"。

但这层斑纹**没法定量**:拉普拉斯、3×3 与 5×5 均值差、相邻像素同值率,三种指标我都试了,
**读数全被画面内容本身盖住**(同一批图散在 3.7~10.7),所以**没能证明**因果。要定这件事得跑一张
对照矩阵(2 个题 × 2 个尺寸 × 2 档画质 × 每种 2~3 张,全部归一化到屏幕尺寸再比),**还没做** ——
在那之前 `fit_size` 保持"按屏幕要图"不动,这条只是记在这儿。
**→ 2026-10-16 当天就翻篇了:换了模型(见 11.26),`fit_size` 改成从推荐尺寸里挑,
这批 16 的倍数(1808×1136 / 1600×896)在新模型上**全都不合法**了。**
**→→ 同一天又翻了一次:推荐档只活了半个下午,傍晚就改回"按屏幕算"了(用户一句「屏幕多大就要多大」),
见 11.27。**
**落进代码**

- `mcwp_ai::DEFAULT_IMAGE_QUALITY = "hd"` + `Stored.image_quality` + `ImagesConfig.quality`;
- `ImageRequest` 带上 `quality`,请求体里终于有这一项了;
- 环境变量 `MCWP_IMAGE_QUALITY` 可覆盖,手写 `ai.json` 也行;
- 面板「设置 → 生图画质」两档(标准 / 高清),保存即生效;
- **认不出的取值一律当高清** —— 用户拼错、或者以后服务商改了档位名,宁可给好的那一档
  (出图成本一样,而差距是 +41% 的高频细节);
- 生图日志带上画质(`生图完成:1808×1136 · hd · 440 KB`),否则「这张到底是不是高清」事后无从分辨。

**另一件顺带查实的事(别和上面那笔账混起来)**

`fit_size(2560, 1600) == (1808, 1136)`,而库里**所有**生成图都是这个尺寸 —— 说明它们全部出自
2560×1600 那台机器(它是主屏;1920×1080 是副屏,`primary_monitor_rect()` 没取错)。
服务商的总像素上限是 2²¹,所以 2560 宽的屏上生图**必然短边不足**,上屏还得放大 1.26 倍。
之前量过:源图与屏上(只做 Ken Burns 采样、无元素层)σ/μ 0.605 → 0.540、
拉普拉斯 19.96 → 16.92 —— 约 15% 的细节损失来自这一步放大。

**这是硬天花板,和画质是两笔账**:画质补的是「源头本来就软」,天花板是「上屏还得再糊一次」。
要彻底解决只有两条:换一家支持更大尺寸的生图服务,或者生图之后做一次超分。**都还没评估。**
### 11.25 关掉「AI生成」角标:一个字段,加一条"没签就被拒"的兜底(2026-10-16)

用户把官方那两行说明贴了过来:`watermark_enabled` —— `true` 是显式角标 + 隐式数字水印,
`false` 全关,但**只有签过免责声明的账号能这么传**(个人中心 → 安全管理 → 去水印管理),
用户已经签了。

**先探参数,再动代码**(实测 2026-10-16,同一句提示词、同样 1024×1024):

| `watermark_enabled` | HTTP | 结果 |
| --- | --- | --- |
| `true` | 200 | 右下角一枚「AI生成」(约 9% × 5%),和一直以来的那些图一样 |
| `false` | 200 | 干干净净 |

两次都是 200,也就是说这个开关在用户这个账号上**是通的**,不用为它换服务商。

**以前是怎么糊弄过去的(顺带更正一句老注释)**

`DEFAULT_IMAGE_BASE_URL` 那段注释原来写着"把 UV 往左上挪一点点就把它推出画面了" ——
那是错的:渲染侧从头到尾**没有一行是为水印写的**。真实情况是构图那条 `cover_uv` **居中等量**
裁掉两头,而 1920×1080 的屏配 1808×1136 的图**碰巧**上下各裁掉 5% 左右,把那枚 5% 高的角标
带出了画面;换成屏比图窄的比例,它就会原样露在右下角。**靠裁切躲水印是运气,不是设计。**

**落进代码**

- `mcwp_ai::DEFAULT_IMAGE_WATERMARK = false`,请求体里**显式**带上 `watermark_enabled`
  (和 `quality` 同一条规矩:不写就是 `true`,所以必须写出来);
- `Stored.image_watermark` 用 `Option<bool>`:空 = 用内置默认(和 `thinking` 同一套写法,
  没设过就连字段都不落盘);
- 环境变量 `MCWP_IMAGE_WATERMARK`;`parse_bool` 只认 `1/true/on/yes` 与 `0/false/off/no`,
  **认不出就继续往下走**,而不是替用户挑一个(写成 `unwrap_or(false)` 会让 `=0off` 这种手滑静默生效);
- 面板「设置 → 生图水印」两档(不加 / 加),保存即落盘、就地重建客户端;
- 日志和 `describe()` 都写水印状态:`生图:open.bigmodel.cn · cogview-3-flash · hd · 无水印`,
  `生图完成:1920×1088 · hd · 无水印 · 164 KB · …`。
- `GeneratedImage` 多一个 `watermarked`:它说的是**这一张实际带不带角标**,而不是"配置里
  怎么写的" —— 兜底重发过的那种图会带着 `true` 一路上到面板,状态行明说
  "这张带「AI生成」角标:账号还没签去水印声明"。用户看到一个自己关过的角标,
  总得知道它是哪儿来的、去哪儿关。

**兜底:没签的账号不能因此"生不了图"**

`false` 被拒时(4xx 且**正文提到** watermark / 水印)退回带水印重发一次,日志里说明
"多半是账号还没签去水印声明"。判断条件为什么收这么紧:兜底重发是"换一组参数再发一次",
放宽了就会把欠费、参数不合法、模型下线这些 400 也重发一遍 —— 轻则白等一轮,重则在按张计费的
服务商那边多花一次钱。所以 `is_watermark_refusal` 只认那一种,认不出就照原样报错
(有一条测试专门钉这件事:401 / 参数 400 / 5xx 都不许触发重发)。

**哪一部分没被真机验证过**:兜底重发这条路**没跑过一次真的** —— 用户这个账号签过了,
服务商不会拒,也就没有那个 4xx 可以触发它。现在钉住它的只有 `is_watermark_refusal` 的单元测试
(认得出 / 认不出各三例)。要有把握只能等真遇到那种账号,或者临时把签名撤掉再试一次 ——
后者不值当。**知道"这条闸是测出来的、那条路是推出来的",比两边都说成"已验证"有用。**
### 11.26 换模型:`glm-image`,以及"尺寸规则跟着换了"这个坑(2026-10-16)

用户点了名:生图模型换成 **`glm-image`**,尺寸用官方那七档推荐
(1280×1280 / 1568×1056 / 1056×1568 / 1472×1088 / 1088×1472 / 1728×960 / 960×1728),
自定义的话长宽 512~2048、且都是 32 的倍数。

**先探参数,再动代码**

| 探的 | 结果 |
| --- | --- |
| `glm-image` + 1472×1088 | HTTP 200,**37.4 s / 72.4 s** 两次(同样参数,抖动比 cogview 大得多) |
| 再带上 `quality: hd` | HTTP 200 —— 收这个字段,但**效果没验**(见文末) |
| `watermark_enabled: false` | 角标干净(和 cogview 一样有效) |
| `1920×1080` | **HTTP 400**,正文原文:`size的长宽均需满足512px-2880px之间,且为32整数倍,并保证最大像素数不超过2^22px` |
| 2560×1600 / 2048×2048 | 没报错,但 120 s 都没回来(越大越慢) |

**注意这里的两个出入**(以接口那行正文为准,不以我们的印象为准):

- 用户给的区间是 **512~2048**,接口说 **512~2880**;总像素上限是 **2²²**(CogView 是 2²¹)。
- 所以 `2560×1600` 现在是**合法**的(2560/32 = 80、1600/32 = 50、4.096M ≤ 4.19M)。
  这一条直接改写 §11.24 里那句"2560 宽的屏上必然短边不足" —— 那条是 CogView 时代的天花板。

**真正的坑是:尺寸规则跟着模型一起换了**

CogView 那阵子是"**16** 的倍数、2²¹",库里那批图全是按这个算出来的
(`1600×896`、`1808×1136`、`1920×1088`)。换到 `glm-image` 之后:

- `1808/32 = 56.5`、`1088/32 = 34` —— **一半的旧尺寸会被 400 直接拒掉**;
- 而 400 不是降级:那一轮是"用户等一分钟、什么也没拿到"。

所以 `fit_size` 不再"按屏幕算一个"(算出来的尺寸要同时压住"32 的倍数"和"总像素 ≤ 2²²"
两条边,贴到上界时确实会超,算错一次就是白等),改成**从七档推荐里挑**

- **比比例,不比像素**:16:9 的屏要 1728×960,不是"像素最多的 1280×1280" —— 比例差得远,
  画面会被 cover 裁掉一大块,构图就废了;
- 距离取**比值的对数**:2 倍和 0.5 倍算一样远,不然竖屏会被偏袒到大尺寸那一头;
- 同比例取面积大的那个。

于是 2560×1600 的屏拿到 **1568×1056**(3:2 那档,比 16:10 更近),1920×1080 拿到 1728×960。
「挑出来的尺寸合法」这件事不是靠人盯:七个候选逐个过 `size_is_legal`,而 `fit_size` 收尾还有
一记 `debug_assert` —— 以后谁往清单里塞一个 1600×900(900 不是 32 的倍数),当场就炸。

**上屏放大这笔账:当天傍晚就结了(见 11.27)**

2560×1600 的屏配 1568×1056:要放大 **1.63 倍**才铺满。而接口现在允许直接要 2560×1600
(4.1M 像素)。**更大的请求是不是更清楚,没验** —— §11.24 末尾那层"斑纹"还没定性,
在定性之前不敢拿它当理由改尺寸。先按推荐的来(用户也是这么说的),效果上屏见。

**→ 几个小时后,用户一句「屏幕多大就要多大」把这块摆平了:推荐档只活了半个下午,`fit_size`
改回"按屏幕算"(2560×1600 就直接要 2560×1600)。见 11.27。**

**实测(1920×1080 那条路,1728×960)**

| | 一张要多久 |
| --- | --- |
| `cogview-3-flash` | 10~16 s |
| `glm-image` | **85~92 s**(含提示词那一步的 5 s 左右) |

慢五六倍,所以生图那条路的超时从 **180 s 抬到 300 s**:这条超时的代价不是"重试一下",
是**钱已经花了、图却没拿到**。慢归慢,画质是另一个量级 —— cogview 那张整幅带一层斑纹,
glm-image 这张(同尺寸)霓虹上的字、楼体的线脚都立得住。

**两个还没验的点(写在这儿免得当成已验证)**

- `quality: hd / standard` 在 glm-image 上**认但不验**:它未必有这两档,那 41% 是 cogview 量的;
- 生图**计费**:这个模型是不是免费档我没查,账单在用户那边。

**配置那一层也得改**:这台机器的 `ai.json` 里钉着 `"image_model": "cogview-3-flash"`,
**改代码里的默认值对已经配过的机器一个字都不算** —— 第一次跑完还是 cogview 出的图,日志写得
明明白白。所以这次是默认值(`DEFAULT_IMAGE_MODEL`)和配置**一起**改的:默认值管新装的机器,
配置管这一台。
### 11.27 「屏幕多大就要多大」:尺寸改回按屏幕算,以及首尾帧那条路第一次留下日志(2026-10-16)

用户两句话:**「屏幕多大就要多大」**、**「现在的视频模型支持首尾帧生成」**。第一句是**推翻上一轮** ——
11.26 刚落地的"从官方七档推荐里挑"只活了半个下午。

**为什么上一轮的做法立刻就该翻**

推荐档换来的是"稳",代价是一眼能看见的:

| 屏 | 推荐档给的 | 要放大几倍才铺满 |
| --- | --- | --- |
| 1920×1080(这台机器) | 1728×960 | 1.13 倍 |
| 2560×1600 | 1568×1056 | **1.63 倍** |

而接口本来就允许更大的:`2560×1600` 满足"512~2880、32 的倍数、4.096M ≤ 2²²"三条(11.26 实测过)。
11.24 末尾量过,源图到屏上这一道放大要吃掉**约 15% 的细节**(σ/μ 0.605 → 0.540、
拉普拉斯 19.96 → 16.92)。说白了:推荐档是"用一个我们自己造的损(放大)去换一个假想的险(怕算错被 400)"。

**新的 `fit_size`:四条规则,全程等比**

| 步 | 干什么 | 为什么不是别的写法 |
| --- | --- | --- |
| ① | 就近对齐到 32 的倍数:**1920×1080 → 1920×1088** | 和 16 倍数那版同一笔账:多补几行比裁掉好 |
| ② | 长边超 2880 → **等比**缩 | 单独夹长边会把 3840×2176 变成 2880×2176(1.77 → 1.32),比例毁了比小一圈更难看 |
| ③ | 总像素超 2²² → 同样等比缩 | 同上;4K 就是这两条一起撞 |
| ④ | 短边低于 512 → 等比放大 | 512 是接口自己的下限,小屏 / 窄窗口才会走到 |
| ⑤ | 落地到 32 的倍数:四舍五入,顶破天花板再等比退一次 | 见下面那个坑 |

三个直接能对照的数(都钉在测试里):

- `1920×1080 → 1920×1088`(**这台机器**,真机验过,见下);
- `2560×1600 → 2560×1600`:屏幕本身,一个像素都不用放大;
- `3840×2160 → 2720×1536`:两条天花板一起撞,等比缩完仍留在 16:9 上。

**踩到的坑(写下来免得再踩)**:⑤ 第一版写的是向下取整。3440×1440 经 ② 正好落在 2880×1200,
而 **1200 根本不是 32 的倍数**(1200/32 = 37.5),浮点里 `1200.0 / 32` 是 37.500000000000004,
`floor` 把它砍成 37 → 1184,白丢 16 像素、比例也跟着歪。而且取整方向没法靠"某条舍入规则"定:
1184 那边是 2.43、1216 那边是 2.37,原比例 2.389 —— 1216 才对。所以 ⑤ 就是普通的四舍五入。

**验收与红线**:`--images-selftest "雪山日出"` → `生图完成:1920×1088 · hd · 无水印 · 299 KB`,
落下来的预览图确实是 1920×1088、右下角干净(对照 11.25)。合法性靠 `size_is_legal` 过滤 +
`fit_size` 收尾那记 `debug_assert`,另有一条测试把 17 种屏幕(含 1×1、32:9、竖屏)逐个过一遍,
断言"合法 + 比例漂移 < 3%"(实测最差 2.67%,是 3840×1080 那种 32:9 的,32 的粒度到头了)。

**注意 `--images-selftest` 验的是什么**:它把屏幕**写死成 1920×1080**(`main.rs` 里那两行有注释),
因为这条路不建窗口、拿不到 DPI 感知后的真屏幕。所以它验的是"折出来的尺寸对不对 + 服务商收不收",
**不是**"你这台机器的屏到底多大" —— 真机那一份只能在面板里生一张、再读日志。

**哪一部分没被真机验证过**:

- 2560×1600 / 4K / 32:9 那几档**只有单元测试**,这台机器没有那种屏(2560×1600 在 11.26 提交过、
  服务商收下了,但当时没等出图);
- **"更大的请求是不是更清楚"仍然没量** —— 11.24 末尾那层"斑纹"还没定性。这一轮改变的是
  "不再多放大一道",不是"证明了更大的请求更清楚"。

**首尾帧:确认它一直在用,并给日志留一句话**

「现在的视频模型支持首尾帧生成」这句值得查一遍。翻代码的结论是:**这条路当天早些时候就已经在用** ——
`animate_photo` 走的是 `Videos::animate_looped`,提交的是 `image_url: [图, 图]`(首帧尾帧同一张,
画面才绕得回起点),不认这个形状就退回单图重提一次(见 11.22 / 决策 34)。所以这一轮**没改行为**。

改的是**能不能看出来**:提交成功后补一行 `首尾帧被受理(首尾都给同一张图 → 画面绕回起点)`。
原来只有降级会打 warn,于是"库里这一段到底是不是按闭环提交的"事后无从分辨 —— 现在两头都有话说。

实测(2026-10-16,`--animate-save 6ad2004aa6f55d38`,1 元/次):
两轮都跑通了提交,结果一个失败一个成功(每轮 1 元):

| 试的 | 提交 | 结果 |
| --- | --- | --- |
| `6ad2004aa6f55d38`「二次元少女」 | 200,任务 `20261016203251e2ea8b4ac7884bec` | **FAIL** |
| `6ad1d49019fb816c`「都市夜景黄昏」 | 200,任务 `202610162045227b73f498346942d3` | **10.4 s / 1718×1080 / 12.3 MB**,取回来了 |

第一轮那条 FAIL **没给任何原因**:正文里只有 `task_status: FAIL` 和一个空 message。
顺手拿坏图探了一次形状(单图 / 首尾帧各一条):**两种形状都是 200 + PROCESSING**,随后都是同样一个
"没有任何解释"的 FAIL —— 也就是说服务商这个 FAIL 分不清"形状不认"还是"图不行",从客户端这一侧
**查不出为什么**。这条得记着:以后看到 FAIL 别先怀疑自己的请求体。

第二轮才是重点,它一次撞出两个真问题:

**① `ureq` 默认只让读 10 MB 的 body,而这条片子是 12.3 MB。**

最先报的错是 `读视频字节失败:the response body is larger than request limit: 10485760` ——
**视频已经生成完、钱也已经花了**,死在最后一步"取回来"上,而且报错看着像网络问题,一点看不出是
本地那道闸。修法:下载时显式把上限抬到 **128 MB**(`MAX_DOWNLOAD_BYTES`;生图那份也一起抬了,
它现在是 2 MB 上下,属于顺手加固)。

能补回来是因为**任务号在报错里**:`--video-fetch 202610162045227b73f498346942d3 6ad1d49019fb816c`
不提交、不再花钱,0.7 s 把那条取了回来(12.3 MB,`1718×1080 @ 31fps · 10.4s`)。
11.22 那条"超时 / 失败也别重提、照号取回"的设计,今天第二次救场。

**② 首尾帧收下了,但没闭环。** 取回来的片子用 `--video-selftest` 量(免费):

| | 首帧 | 中点 | 末帧 |
| --- | --- | --- | --- |
| 采样均值(亮度) | 91.9 | 96.2 | **103.3**(+12.4%) |

接缝:首↔末 平均差 **16.02**,而"首帧↔中点那帧"是 7.23 —— **头尾比半途还远**,工具自己那行结论
写的就是"闭环没生效"。这跟 11.22 那次(14.22 vs 8.05、亮度差 10%)是同一个病,而且这次更重。

所以结论得说清楚:**接口收下首尾帧 ≠ 模型真会绕回起点**(它也可能只是把第二张丢掉了 ——
这两件事从返回里**分不出来**)。因此播放侧那两笔兜底**不能撤**:曝光差照旧按 `seam_gain` 摊在整段
(`seam_gain = 0.75`,这一条是入库时自动量出来的),接缝靠 0.8 秒环形混合。

**③ 顺手补的一处:FAIL 的报错里带上任务号**(`服务商说这条视频没生成出来(任务 xxx,他们没给原因)`)。
他们不给原因,那我们至少得让用户手里有个号可查、有依据去要回那 1 元。

**顺带记一笔环境坑**:诊断入口的日志级别走 `RUST_LOG`(`EnvFilter::try_from_default_env`),
而这台机器的环境里钉着 `RUST_LOG=warn` —— 于是"明明加了 info 日志、跑完一行都没有",
排查的时候先 `RUST_LOG=info` 再跑。

### 11.28 会话里的「生成动图」入口,以及"点完什么都没发生"(2026-10-16)

用户两句话:**「现在生成动图可以在生成的图片下面点击生成」**、**「生成的时候需要显示一下正在生成,
现在的交互感很差」**。

**这一轮要治的病:入口在别处 + 点完没有任何回声**

两件事其实是一件事的两半。入口原来只在**库页**(格子的右键菜单、工具栏那颗钮),而"把这张做成动态
壁纸"这个念头是**盯着那条回复里的图**的时候冒出来的 —— 让用户跑一趟库页、在几十格里认出同一张,
是白白多出来的一步,而且认得对不对还得他自己负责。第二半更贵:这一步**要几分钟、还要 1 元**,
点完之后按钮一点变化都没有,用户很自然会以为没点上,然后再点一次 —— 第二次只会被告知
"正在做上一段动态壁纸,等它出来再说"。**没有反馈的动作会被重复执行**,而这一次重复执行是要花钱的。

**做法**

| # | 定的东西 | 为什么 |
| --- | --- | --- |
| 1 | 每条回复的配图下面挂一颗 22px 的小胶囊「生成动图」 | 它跟着"正看着的那张图"走;`Pill` 加了 `box-height` / `ink-size` 两个参数,默认值不动,别处那颗 34px 胶囊一个字没变 |
| 2 | 点了就地换成「正在生成动图」+ 每 400ms 走一格的省略号 | "正在做"必须是**看得见**的;点子在跳,用户就知道点上了、得等;这一步的宽度写死 96px,免得点一变长整行跟着抖 |
| 3 | **已经做成动图的不画按钮**,只留一句「已是动图」 | 再点一次是**再花一次钱**买同一张图的另一段片子,而画面几乎没变 —— 这种事得让界面挡住,不能只靠提示语 |
| 4 | "正在做的是哪一张"由壁纸侧 `PanelHandle::set_animating(id)` 单向灌进来 | 任务在壁纸那一侧跑,面板自己"记着我点过没有"一定会漂。它和 `run-state` 一个路数:是**当前动作的投影**,不是会话数据 —— 所以走单独一条通道,**不进 `PanelState`**(那条路要重传几十张缩略图的裸像素,为了一个 id 不值当) |
| 5 | 递的是**图的 id**,不是行号 | 行号在消息增删 / 切会话之后会指到别处(和预览图那个右键菜单同一个道理) |
| 6 | 三个入口(库格右键 / 库页工具栏 / 会话里这颗钮)共用一个 `start_video_run_visible` | "起跑"和"点亮面板"是同一件事的两半,**判据必须一致**:被拦下来时(库空 / 已经是视频 / 已经有一条在跑)那颗钮要原样熄灭,散在三处抄三遍就一定会有一处漂 |

**真机撞出来的第一个坑:出片之后「已是动图」不亮(按钮又回来了)**

第一遍跑完(假服务,见下)面板上那行照旧画着「生成动图」。原因不在 UI,在**两个 id 对不上**:
成片入库时**必须重新生成 id** —— 沿用原图那个 id 的话,成片的封面(`<id>.png`)会把原图那张
画面文件盖掉(库里就再也找不到那张静图了,这句话 `video_payload_from_bytes` 里本来就写着)。
于是"会话里那条回复(挂的是**静图**的 id)"和"做出来的那段片子(**新 id** 的另一条记录)"
是两条互不相识的库记录,那句「已是动图」永远不会亮 —— 而且它是**静默**的:按钮只是原样留在那儿。

修法:给 `Photo` 加一个 **`origin_id`**(成片记下"我是从哪张做出来的";静图 / 抬进来的 / 导入的
都是空串)。它带 `#[serde(default)]`,老记录读出来就是空串 —— 空串在这里是**有意义的值**
("不知道出处"),不能靠"缺字段就报错"来发现,扫库是一条条读的,一条读炸了整个库都打不开
(已加一条测试钉住)。面板侧那份索引(`VIDEOS`)从此装**两种 id**:视频自己那条,以及它的出处。

代价**说清楚**:改动之前入库的那些片子没有 `origin_id`,对应的回复**照样画着按钮**(第一次
真机验证撞上的就是这条老记录)。历史片子要重做一遍才会显示「已是动图」—— 这一条**没修**,
因为修它只能靠"看标题像不像"那种一撞就错的猜法。

**真机撞出来的第二个坑:换文字时整页跳 8px,于是"点钮的位置"落到了图上**

胶囊 22px、那一行 10px 的文字只有 14px —— 状态从「生成动图」翻成「已是动图」时,这一行矮了 8px,
而消息列表是**贴着底滚动**的,所以整页内容跟着跳。实测后果很具体:在"刚才那颗钮"的同一个窗口内
坐标(498,266)上再点一下,弹出来的是**大图预览**(那个点是那张预览图了),而不是"什么都不发生"。
修法:那两段文字 `height: 22px`,把这一行的高度钉死。
**这条是点出来的、不是看出来的** —— 只有把面板真的点一遍才会露出这种"错位一像素级、后果一整步"的事。

**验证方式:给这条链路配一个不用花钱的对端**

出片一次 **1 元**,而且服务商排队能从一分钟拉到十几分钟,按钮这种"点一下要立刻有反应"的交互
既不能靠花钱、也不能靠等运气来回归。所以加了 `tools/fake-video-server.py`:

    python tools/fake-video-server.py --port 8799 --running 3
    # 环境变量覆盖 ai.json(别动用户的真配置):
    $env:MCWP_VIDEO_BASE_URL = "http://127.0.0.1:8799/v1"

`--running 3` 是"先说三次还在跑再出片":真链路的轮询间隔是 8 秒(`VIDEO_POLL_INTERVAL`),
所以"正在生成动图…"会**稳稳停住 24 秒**,够截两张图看清点子有没有在跳。`--hold` 是永远不出片
(专门把那个状态钉住),`--video <mp4>` 指定出片给哪一段(默认拿本机壁纸库里第一段现成的)。
出片那一步走的是**真 mp4**,所以"主线程解封面 → 写进库 → 刷新面板"这一整段都是真的在跑。

实测(2026-10-16,零成本,三条都跑通了):

| 环节 | 实测 |
| --- | --- |
| 提交 | `submit /v1/videos/generations bytes=295777 → fake-1`(请求体里那张图的 base64 有 289 KB) |
| 轮询 | `poll #1..#3 RUNNING → #4 SUCCESS`,应用侧 `图生视频完成:1563 KB · 耗时 24.0s` |
| 落地 | `新动态壁纸已入库:photos\6ad223b8953432f9.json`,`origin_id: 6ad1d17f953432f9` 写进了元数据 |
| 面板 | 点钮 → 那一行变「正在生成动图」(两张相隔 700ms 的截图里点子的个数不同)→ 落地后变「已是动图」 |
| 再点同一个位置 | 假服务日志**一行都没有**,面板也不弹预览 —— 既没有第二次起跑,也没有误触 |

**顺带记一笔语义**:会话里这颗钮和库里那两处一样,**起跑成功就会把成片上屏**(`adopt_video` 里
`active = Some(photo)`,状态行写的是"已换上动态壁纸「…」")。这和 11.21 的"生图只入库、不自动换桌面"
**不一样**,是这条链路从 11.17 起就有的老行为 —— 这一轮**没改**,但"做成动态壁纸"到底该不该顺手换上屏,
值得单独拍一次(见 §12.2)。

**哪一部分没被真机验证过**:

- 真服务商那条路这一轮**一次都没花钱跑**(1 元/次)。跑通的是"提交 → 轮询 → 下载 → 落地 → 面板"
  这条客户端链路,服务商那一侧只有 11.27 的旧记录;首尾帧、闭环、`seam_gain` 都是原样带过去的。
- 「已是动图」验的是**从会话里点起来**的那一条。库里另外两个入口(格子右键 / 工具栏钮)走的是
  同一个 `start_video_run_visible` 和同一个 `video_payload_from_bytes`,**推断**行为一致,但**没单独点过**。
- 重启之后还亮,这一点验过(靠落盘的 `origin_id`,重启后那条回复仍然是「已是动图」);
  但**改动前入库的老片子不会亮**,前面那段已经说明。
- 多屏 / 缩放的坐标没重验(这颗钮的点击都在主屏 100% 缩放上做的)。
- 三段状态(按钮 / 正在生成 / 已是动图)的**宽度**只在这台机器的会话宽度下看过:提示语那一行
  在"正在生成"(96px)时会省略到「右键可设为…」,这是 `overflow: elide` 的本意,但更窄的面板上
  会更早进入省略。

### 11.29 图生视频「某些比例必死」:尺寸得自己报一档(2026-10-16)

用户的话:**「是不是因为传上去的图片的尺寸超出了视频模型的尺寸?」**,后面贴的是服务商那段说明 ——
不指定 `size` 时默认"短边 1080、长边按原图比例推",最高支持 4K,可选七档:`1280x720` / `720x1280` /
`1024x1024` / `1920x1080` / `1080x1920` / `2048x1080` / `3840x2160`。

**用户猜的方向对了一半:不是"超出上限",是"这一档本来就该自己算"**

先排除掉"超上限":库里挂掉的那两张是 `1920×1088`,长边 1920 离 4K 差得远,上限这条站不住。

真正的证据是**已有记录的对照**(全在库里,没花钱):

| 原图 | 服务商自己推的长边 | 结果 |
| --- | --- | --- |
| `1808×1136`「清新晨光雪山湖」 | `1080 × 1808/1136 = 1718.87` → **1718** | 出片,成片就是 `1718×1080` |
| `1808×1136`「都市夜景黄昏」 | 同上 | 出片,`1718×1080` |
| `1920×1088`「二次元少女」 | `1080 × 1920/1088 = 1905.88` → **1905** | **FAIL**(20:32) |
| `1920×1088`「森林小径黄昏」 | 同上 | **FAIL**(21:35) |

两件事因此能定下来:

1. **它是向下取整的** —— 说"按原图比例推"不算错,但落下来的数就是 `1718` / `1905`,不是 `1719` / `1906`。
   这一条不是猜的:`1718` 就是成片元数据里那个宽度。
2. **奇数长边是必死的** —— `1718` 是偶数,编得出来;`1905` 是奇数,而 H.264 的宽高都得是偶数,
   编码器根本编不出这一帧。两次 FAIL 相隔一小时、内容毫不相干(一张二次元少女、一张森林小径),
   唯一的共同点就是这个尺寸。

也就是说:**`size` 空着这条路对某些比例是必死,而且死得一声不吭** —— FAIL 的正文里只有
`task_status: FAIL` 和一个**空的 assistant 消息**(`{"role":"assistant"}`,一个字都没有)。
11.27 末尾那两句"两种形状都是 200 + PROCESSING、随后同样一个没有解释的 FAIL"因此有了下文:
那两个 FAIL 里至少有一个就是这么来的。

顺带认一笔自己的账:`1920×1088` 是 **11.27「屏幕多大就要多大」改出来的**(1080 向上对齐 32 的倍数)。
那条改动本身没错,但它把库里**全部新图**都推到了 `1905` 这条必死线上。

**做法:显式报一档,就从服务商给的那七档里挑**

- `VIDEO_SIZES` —— 七档照抄清单,不自己造尺寸;
- `video_size_for(screen)` —— 挑法三条:①屏幕本身就在清单里(1920×1080 / 1080×1920 / 4K)就直接用,
  一个像素都不用放大;②否则在**横竖方向一致**的档位里挑比例最接近的;③一样近时优先"面积不超过
  屏幕"的、其中取大的(一档都装不下就取最小的,放大得最少)。② 那个横竖过滤不是讲究:`800×600`
  这种 4:3 的屏,`1280x720` 和 `720x1280` 的比例距离**相等**,不拦一下就会给一块横屏塞一档竖屏尺寸;
- `submit_image` 里 `size` 不再是空的;提交日志跟着补一句 `图生视频任务已提交:…(要 1920x1080)`,
  免得下次还得靠抓包才知道报的是哪一档。

**这个"七档"只管视频**:生图那条路(11.27)仍然是"按屏幕算 + 向上对齐 32 的倍数"(`1920×1088`)。
两者现在是两套规则,别互相借 —— 生图接口收 1088,视频接口的清单里没有它。

**验证一:零成本那条(真机 + 假服务)**

`tools/fake-video-server.py` 原来"不解析请求体",这一轮给它加了一行:把 `size` 抠出来记进日志。
它排在一大坨 base64 **后面**(`VideoRequest` 的字段顺序是 model / prompt / image_url / size / …),
所以只能扫全文;判断依据是 JSON 字符串里的引号一定是转义的、base64 的字母表里压根没有引号,
所以第一个 `"size"` 就是那个真字段 —— 这一点单独测过(提示词里就写着 `"size":"999x999"` 这种文字时,
抠出来的仍然是 `1920x1080`)。抠不到会**打印一行告警**,不让"没报"静默过去。

实测(2026-10-16,面板 + 假服务,点一次会话里那颗钮):

| 环节 | 实测 |
| --- | --- |
| 提交 | `submit /v1/videos/generations bytes=1350402 size=1920x1080 -> fake-1` |
| 轮询 | `#1..#3 RUNNING → #4 SUCCESS` |
| 取片 | `serve video bytes=1600929` |
| 落地 | `photos\6ad22e4e9aec26e1.json`,`origin_id: 6ad2281f9aec26e1`(就是那张挂过的森林小径) |
| 面板 | 那行「生成动图」→「正在生成动图」→「已是动图」,状态行「已换上动态壁纸「森林小径黄昏」(5.1 秒,循环播放)」 |

假服务造出来的那条记录**验完就从库里删掉了**(它的 mp4 和库里另一段字节完全相同,是彻头彻尾的测试产物),
桌面也跟着还原回原来那张静图。

**验证二:单元测试**。`1920×1080 → 自己`、`1080×1920 → 自己`、`3840×2160 → 自己`、
`2560×1600 → 1920×1080`、`1366×768 → 1280×720`、`5120×1440 → 2048×1080`、`800×600` 必须挑横屏;
另一条把 9 种屏幕逐个断言"挑出来的在清单里、两边都是偶数"。

**哪一部分没被真机验证过**:

- **服务商到底收不收 `1920x1080` 这一档,只有真花一次钱才知道**(1 元/次)。这一轮**一分钱没花** ——
  跑通的是"提交里带着 size"这条客户端链路,服务商那一侧从 11.27 之后就没有新记录。
- 那张真正挂过的图(`6ad2281f9aec26e1`「森林小径黄昏」)现在还能不能出片,**没验**。验它的入口是
  `--animate-save 6ad2281f9aec26e1`,成功的标志是"不再 FAIL"且成片尺寸对得上;万一失败**别重提**,
  拿任务号 `--video-fetch <任务号> 6ad2281f9aec26e1` 免费取回。
- 挑档规则只在单元测试里过(9 种屏幕);真机上只走过 `1920×1080` 这一个落点,而它恰好是唯一一个
  "屏幕本身就在清单里"的情形 —— 换句话说,**真机走的是第 ① 条,第 ②③ 条没走过**。
- 副屏 2560×1600 会挑到 `1920×1080`(第 ② 条),但当前实现只认主屏,所以那个落点也还没有真机路径。
### 11.30 「奇数长边」那条诊断被自己推翻了 —— 病根在服务商侧(2026-10-17)

用户原话:**「还是不行啊,你直接打一次测就行了」**,紧接着一句**「不要用免费的啊」**。

**先做了一件不花钱的事:把 FAIL 的正文看全**

原来报错里贴的是 `truncate(&raw, 200)`,那段正文正好在 200 字处被截断 —— 也就是说 11.27 / 11.29
反复写的"服务商一个字都不解释",其实一直**没被完整验证过**。改成一到 FAIL 就把**全文**打进 WARN,
再用 `--video-fetch`(只轮询、不提交、不计费)把那两条挂掉的任务各问了一遍,两条正文一模一样:

```
{"choices":[{"finish_reason":"stop","index":0,"message":{"role":"assistant"}}],
 "created":1792161305,"id":"...","model":"cogvideox-3","task_status":"FAIL",
 "usage":{"completion_tokens":0,"prompt_tokens":0,"total_tokens":0}}
```

`usage` 全 0、message 是空壳。**这次是真的**:服务商连一个字都没给。

**然后按 11.29 的推断改了一版,花了 1 元,没救活**

11.29 的推断是"服务商按原图比例推出奇数长边,编不出来"。于是提交前把条件图**裁成 16:9**:
`1920×1088 → 1920×1080`(上下各丢 4 行),推出来必然是 `1920`(偶数)。实测(01:30,1 元):

```
条件图裁成 1920×1080(原 1920×1088;不裁的话服务商会推 1905×1080,长边奇数就 FAIL)
图生视频任务已提交:20261017093045fc0ff5fc922f4a20(要 1920x1080)
首尾帧被受理(首尾都给同一张图 → 画面绕回起点)
…… 10 分 05 秒后 ……
图生视频 FAIL(任务 20261017093045fc0ff5fc922f4a20)完整正文:{… task_status:"FAIL", usage 全 0 …}
```

**裁了也照挂**,而且**熬了 10 分钟**才挂 —— 而 11.27 那次成功只用了 **10.4 秒**。

**决定性的一步:同一份请求,15 分钟后成功了**

01:45 把**一模一样的请求**(同一张图、同样裁成 `1920×1080`、同样 `size=1920x1080`、同样首尾帧)
再提交一次:

```
图生视频完成:27215 KB · 耗时 476.9s
打开视频:1920×1080 @ 31fps · 10.4s
出片并入库:photos\6ad2d51e9aec26e1.json(origin_id = 6ad2281f9aec26e1)
```

**同一份请求,隔 15 分钟,一次 FAIL 一次 SUCCESS** —— 请求体这个方向可以结案了。
中途还拿另一个视频模型探了同一张图(免费档,只用来探路,**不是**要换模型),提交当场被挡:

```
429 {"error":{"code":"1305","message":"该模型当前访问量过大，请您稍后再试"}}
```

三条拼起来:

| 现象 | 说明 |
| --- | --- |
| 成功那次 | 10.4 秒出片(11.27),或 477 秒出片(今天,对面正忙) |
| 失败那几次 | 熬 10 分钟、`usage` 全 0、正文空 |
| 同一份请求再发 | 前一次 FAIL、后一次 SUCCESS |
| 同时段换模型探 | 429 · code 1305「访问量过大」 |

结论:**11.29 的"奇数长边"认错了锅**。它不是那几次 FAIL 的原因(裁成偶数照样挂)。
真正的病根在对面:模型过载时,提交**照样回 200 + PROCESSING**,任务在队列里耗到超时、
无声无息地 FAIL,`usage` 全 0。裁图那条留着,但它只是**便宜的保险**(H.264 的宽高确实都得是偶数,
裁一刀只丢几行像素),不是解药。

**这一轮真正改的:遇到对面忙的时候怎么办**

| # | 改了什么 | 为什么 |
| --- | --- | --- |
| 1 | 提交遇 **429 自动退避重提**(5 s / 15 s / 45 s,最多三次) | 429 是**没受理、没计费**的拒绝,重提是安全的;面板上那颗钮不该因为对面忙就直接变成"失败" |
| 2 | 三次都被挡时,报错写清"这单没受理、不花钱,过一会儿再点" | 让用户知道自己没被扣钱 |
| 3 | FAIL 的报错带上**等了多久**,并提示"拖这么久多半是排队/过载,别重提,拿任务号免费取回" | 10 分钟和 10 秒是两种完全不同的病,不该让用户去猜 |
| 4 | FAIL 时把**完整正文**打进 WARN | 上一次就是被 200 字截断,导致三轮排查都在猜 |
| 5 | 裁图那条**保留**,注释改成"便宜的保险,不是病根" | 事实是它没救活那张图;留着是因为无害,而且偶数确实对编码器友好 |

**验证**

- 退避重提:给 `tools/fake-video-server.py` 加了 `--busy N`(先回 N 次 429,响应的形状照抄真实的
  `code 1305`),零成本跑通:`429 → 5 秒后重提第 1 次 → fake-1 → SUCCESS → 入库`;
- 真模型:01:45 那次**出片了**(1 元,1920×1080 / 10.4 s / 26.6 MB),`origin_id` 正确写回库里;
- 单测 66 条全绿(新增 5 条:推出来的尺寸对齐实测、只在奇数时才裁、官方七档自己推出来都是偶数、
  裁完是精确比例、裁完能编出合法 JPEG)。

**哪一部分没被真机验证过**

- **"过载过去了就能出片"仍然取决于对面**:同一条请求 01:30 挂、01:45 成 —— 出片与否现在**不可控**,
  这一轮只是把"不可控"变得**能看懂、不白花钱**(429 不重提、失败别重提、任务号能免费取回);
- 429 的处理只覆盖**提交**。轮询阶段如果回 429,现在仍当普通错误往上抛(会直接失败);
  没改,因为没抓到过轮询 429 的样本;
- `--busy` 那个假服务只回 429,没有模拟"接下了、熬十分钟再 FAIL"那种 —— 那个要真等十分钟,
  不适合做回归;
- 裁图**到底有没有用**,这一轮证明不了:裁完那次挂了、不裁的那次也挂过,同一份请求后来又成了。
  它现在只是"不会更差"的一步。
### 11.31 图生视频只会光影变化 —— 根因不是一句提示词，而是“首尾同图 + speed 档 + 弱动作”(2026-10-17)

用户原话：**「还是有问题，生成的动图怎么只是光影变化了？？提示词需要修改，先去网上搜这类动态壁纸生成的提示词是什么」**。

**先查官方怎么写**

- CogVideoX 仓库 `inference/convert_demo.py` 的图生视频系统提示词（`sys_prompt_i2v`）：
  “Give a highly descriptive video caption based on input image ... include appropriate dynamic information ...
  The input image is the first frame ... Don't contain camera transitions / screen switching / perspective shifts”。
- 仓库 README 明确写：模型是在**长提示词**下训练的，官方画廊样例都是完整句子
  （butterflies flutter / fountain cascades / willow branches sway / swans glide leaving ripples）。
- 智谱接口文档：`prompt` 上限 512 字符；`quality` **默认为 `speed`**，可选 `quality`（质量优先）；
  `watermark_enabled` 默认为 `true`，已签免责声明可传 `false`。
- 结论：官方要的是“高描述性的完整画面 + 明确动态信息”，而我们之前既没传 `quality`，又把动作写成了短清单。

**根因一：首尾帧同一张图会把运动锁死**

这是这次最关键、也最反直觉的一条。同一张图做了多轮对照（**提示词都要求草/树叶实体运动，
但不是严格单一变量**——单图两轮用了更强的动作描述）：

| 提交形状 / 档位 | 任务号 | 光流均值 | 结果 |
| --- | --- | --- | --- |
| 首帧=尾帧=同一张图 / speed | `20261017104141c791b397dca44556` | `0.06` | 五帧几乎完全一样，只剩轻微明暗/压缩变化 |
| 只发首帧 / quality / 端到端自动提示词 | `202610171116087d47c4136a9646ae` | `2.92` | 前景局部运动明显高于天空；仍有轻微镜头漂移 |
| 只发首帧 / speed / 强动作提示词 | `2026101710513492b8c4391eb04357` | `8.79` | 运动量最大，但速度档下变成了明显的镜头前推 |

不是说“单图一定就完美”，而是**首尾同图这条约束本身会强烈抑制运动**：模型只要把画面保持住，
就能同时满足首帧和尾帧；即使提示词明确要求草叶摆动，实测也只有 `0.06`。
为什么以前偶尔能看出一点动作：提示词里有 “The sun sets on the horizon”，模型用太阳/整体亮度变化
交了差，正好就是用户说的“只是光影变化”。

**现在的提交方式**

- 壁纸只把原图当**首帧**提交（`Videos::animate`），不再发尾帧；
- 循环接缝交给播放器已有的 `LOOP_FADE_SECS = 0.8`：最后 0.8 秒淡回第一帧，再用 `seam_gain` 校曝光；
- `animate_looped` / `submit_looped` 保留仅作接口兼容和诊断，文档里明确写了“不要拿它做壁纸”。

**根因二：一直用的是 speed 档**

`VideoRequest` 以前没有 `quality` 字段，服务商默认 `speed`。现在显式提交：

```json
{ "quality": "quality", "watermark_enabled": false }
```

- `quality`：质量优先，出片更慢（端到端实测 16 分 49 秒），但镜头更稳、动作更听提示词；
- `watermark_enabled: false`：用户已签去水印声明；若账号被拒，`submit_image` 会像生图一样退回带水印重提一次。

**根因三：提示词把动作写成了“光影呼吸”**

旧版 `VISION_SYSTEM_PROMPT` 是中文 JSON 清单：动作限 12 字、只挑 2~5 个、还要求“所有动作必须来回”
“亮度稳定不要越来越亮”。同一张森林图只给出：

```
镜头固定机位。画面里:全图阳光一明一暗地闪烁;全图树影缓慢摇摆。
```

现在三层一起改：

| 层 | 规则 |
| --- | --- |
| 看图模型 | `scene` 12~24 个英文词（地点 + 地形 + 前景/中景/天空实体）；4~5 个元素、至少 3 个实体；**太阳/夕阳/光线/光晕/阴影/曝光/亮度/色彩变化不算实体**；元素顺序前景优先；每句必须有方向或幅度（back and forth / deeply / strongly / continuously / across the frame） |
| 本地拼装 | 按 `foreground → midground → sky` **强制排序**；丢掉 `Sunset / Sunlight / Glow / Shadow` 这类光影元素；清掉 `English` 前缀和 `at dusk / at sunset / warm sunlight` 等时间光线短语；弱动作短语换强：`bends rhythmically → bends deeply`、`sway steadily → sway strongly`、`drift slowly → stream steadily`、`rustle steadily → rustle continuously` |
| 收尾句 | 固定为 `Each motion completes one full visible cycle and returns to its starting pose; no camera movement, zoom, pan or orbit, and exposure and color stay fixed.` —— 先留收尾位置，512 字超了宁可少写一个元素，也不截半句 |

**同一张森林图，最终自动生成的提示词（453 字）**

```text
A dense forest with a winding dirt path, thick ferns and tall trees on both sides. The camera remains locked off. Grass bends deeply under the weight of the wind. Ferns ripple in visible waves along the path. Leaves shake and rustle continuously in the breeze. Clouds stream steadily across the sky. Each motion completes one full visible cycle and returns to its starting pose; no camera movement, zoom, pan or orbit, and exposure and color stay fixed.
```

**真实出片对照**

- 首尾同图 + 旧提示词：任务 `2026101710184194d9fd09fa1149f9`，成片 `6ad2dce89aec26e1`；
  运动热力图 3×3 均值 `0.55~1.27`，主要动在太阳/天空，前景草几乎不动；
- 首尾同图 + 前景提示词：任务 `20261017102817f72ca8206baa4e7d`，排队 604 秒后 FAIL
  （服务商过载，空正文；见 §11.30）；
- 首尾同图 + 新提示词 + 旧 speed 档：任务 `20261017104141c791b397dca44556`，成片 `6ad2e2599aec26e1`；
  光流均值 `0.06`，五帧几乎一样 —— 这是“首尾同图锁运动”的直接证据；
- 单图 + 强动作 + speed 档：任务 `2026101710513492b8c4391eb04357`；光流均值 `8.79`，但全局单应变换接近镜头前推，
  不是我们要的“元素自己动”；
- 单图 + 强动作 + quality 档：任务 `202610171059320f361f2442f649c8`；光流均值 `0.35`，
  但全局单应缩放 `1.00`、位移 `1~2 px`，前景残差 `25~31`、天空 `12~16` —— 镜头基本锁住，前景草叶有局部运动；
- 端到端（新的自动提示词 + 单图 + quality）：任务 `202610171116087d47c4136a9646ae`，成片 `6ad2ec7e9aec26e1`；
  光流均值 `2.92`，前景 3×3 均值 `6.89 / 2.89 / 6.13`、天空 `1.38 / 0.80 / 1.79`，前景局部运动明显高于天空；
  全局单应缩放约 `1.02`、位移 `20~40 px`，说明模型仍带一点镜头漂移，但已经不是“只动光影”；
  这条任务耗时 16 分 49 秒，刚好超过应用 15 分钟等待上限，成片用 `--video-fetch` 免费取回入库
  （这是等待上限该调大的实测依据，详见 §11.30 的超时策略）。

**数据结构**

- `MotionPlan` 新增 `scene`、`caption`（老 JSON 缺字段 = 空串，向后兼容）；
- `MotionElement` 新增 `sentence`（完整英文动作句）；`action` 保留给诊断和兜底；
- `has_caption()` 把“有 scene + elements”也算可复用；**老资产只有 elements 的旧方案不复用**，
  `animate_photo` 会重新看图 —— 否则修好的提示词永远轮不到旧图。

**测试**

- `mcwp-ai` 41 条全绿（新增：scene+元素拼装、完整句优先、caption 优先、缺相机/闭环补齐、
  超长按句子收口、通用兜底写实体、有无 caption 决定复用、光影元素过滤、前景排序、场景清洗、弱动作换强）；
- workspace 78 条全绿。

**剩余风险**

- quality 档更听“别运镜”，但动作幅度比 speed 档小；如果某张图仍然几乎不动，优先增强动作词/换一张更适合动态的图，
  而不是重新加回调尾帧；
- `glm-4v-flash` 仍可能漏元素或写弱词；本地只能保证“给出的元素不丢、顺序和动作被加强”，不能保证“该有的元素一定被看见”；
- 服务商排队/过载仍可能 FAIL，任务号必须保留，用 `--video-fetch` 免费取回，别重提。

| 46 | 图生视频怎么提交、提示词怎么写 | **只发单图首帧 + `quality:"quality"` + 结构化英文长描述**：视觉模型给 12~24 词 `scene` 和 4~5 个实体动作句；本地过滤光影、按前景→中景→天空排序、强化弱动作，再拼 512 字内描述 | 三个根因一起修：①首尾同图会强烈抑制运动（同一张图多轮对照：首尾帧 0.06，单图 quality 2.92 / speed 8.79）；②`quality` 不传默认是 `speed`；③旧中文短清单把实体动作压成“阳光一明一暗”。官方 CogVideoX `convert_demo.py` 要 highly descriptive caption + dynamic information、图像是首帧、不要镜头切换；README 说长提示词训练。循环改由播放器 0.8 秒淡回第一帧，不再用尾帧。见 11.31 |
